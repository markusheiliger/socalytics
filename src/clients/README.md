# Clients

## Purpose

This area owns SocAlytics user-facing client applications.

## Ownership

The boundary is the React Web UI, a Progressive Web App on a single origin. It serves every workflow, including coach workflows and the later offline mode for coaches; there is no second client application. The Web UI foundation, including its installable PWA shell and service worker, is implemented in [`web/`](web/) as development evidence.

## Exclusions

Platform API implementation, server runtime composition, agent runtimes, and Analyst execution software do not belong here. No offline mode with local data or deployment configuration exists yet; the only container image is the Web UI image described below.

## Current Status

`web/` is a React, TypeScript, and Vite application with React Router, TanStack Query, MUI, and i18next. Its API client is generated by Kiota into the ignored `web/src/generated/` folder from the committed OpenAPI snapshot `src/platform/SocAlytics.Platform.Api/openapi/v1.json` and is used only behind local adapters. It includes the Analyst Manager views: the pairing page and a Registrar's own requests, and for Club Admins the fleet with its filters, the approval and rejection decision, and revocation by typing the host label, with the pending count in the navigation. The claimed application profile is not shown until Managers report it. It also includes the Analyst Registry administration for Club Admins (online only, under `/registry`): the default workflow, registered images, profile versions, and workflow versions as readable lists, image registration by digest, profile version creation, approval, and retirement, workflow version definition as node and edge lists, and the default workflow change, each with confirmation where it changes analysis and with the platform's refusals explained; it offers no deletion, image building, or graphical editing. The sign-in page shows one button per configured external OpenID Connect provider below the local form (the browser is sent to the provider and returns through the API callback; a failure shows the generic sign-in failure), and the public `/link-account` page redeems a Club Admin's link code by signing in at the provider; Club Admins issue link credentials when creating a member or from the member screen and unlink identities there. It also includes the connected match workflow and recording upload: match list, create, edit, and detail views for team members with the right roles, recording uploads through a dedicated upload worker (parts hashed and sent directly to object storage with per-part grants, a member-scoped resume journal in worker-owned IndexedDB that holds identifiers and progress only and is purged on sign-out), timeline mapping, finalization, and recording-set lineage with analysis run states, including the confirmed cancel action (optional reason) for Club Admins and Coaches of the owning team on requested and running runs and cancelled runs with who, when, and why. Uploads stay connected-only. It also includes the connected match triage conversations: from a match with a completed run, Club Admins and Coaches of the owning team start a conversation bound to that run, add enabled Specialist Agents, and ask them questions (submission with a reusable idempotency key and conditional polling), and members read their own conversations with advice attribution, AI disclosure, and lineage; Viewers read without controls, and everything stays online only with content, drafts, and keys in memory. Analysis review, Coach Agent conversations, and consultations are not implemented. The account page lets a member set, verify, and remove an email address and choose notification preferences, a confirmation page verifies an address on one explicit click, and the member detail view lets Club Admins manage a member's address. The `platform` browser tests read messages from the AppHost's Mailpit.

The Web UI is an installable PWA: a manifest with icons and a hand-written service worker (`web/src/serviceWorker/`) that precaches only the integrity-verified application shell of one release and passes all API, session, upload, and media traffic to the network, so it holds no user data. Install it from the browser's install action (Chromium-based browsers; installation on Edge and Chrome is a manual check). An open Web UI checks for a new release at start, on focus, and periodically, and shows a non-blocking update notice with an "Update" action that reloads every window. The platform sends the minimum Web UI version it requires in the `SocAlytics-Minimum-Web-Version` response header, set by the platform option `WebUi:MinimumVersion` (empty by default, shape `YYYY.MMDD.HHMMSS`); an older Web UI stops sending requests, shows the blocking update text, and reloads (or asks for a reload after 30 seconds without a newer worker), and the platform never refuses requests by client version. Without a network, the installed PWA opens the shell with the connection-required state and no data. Offline mode with local data does not exist yet: nothing is stored or queued offline. This is development evidence, not production readiness.

## Commands

Prerequisites: Node.js 24, the Kiota 1.36.0 CLI on `PATH` (`dotnet tool install --global Microsoft.OpenApi.Kiota --version 1.36.0`), and the Playwright Chromium browser (`npx playwright@1.63.0 install chromium`). Docker is needed for the `platform` browser tests and the AppHost. Run from `src/clients/web/`:

```powershell
npm ci
npm run build      # Kiota generation, type checking, production build with Subresource Integrity
npm test           # Vitest unit tests
npm run test:e2e   # Playwright, both projects
```

Browser-test projects:

- `simulated` runs against `vite preview` with a simulated API and a fake object store (`tests/e2e/support/fakeObjectStorage.mjs`) for the direct part uploads, and needs no Docker (`npm run test:e2e -- --project simulated`).
- `platform` runs one spec after another through chained projects against the real platform, which the Playwright web server starts through the AppHost in e2e mode (`npm run test:e2e -- --project platform`). The `manager-fleet` spec there drives a scripted Manager (`tests/e2e/support/scriptedManager.ts`) through pairing, activation, status reports, and revocation; the `matches` and `upload-flow` specs use the real platform with RustFS (the AppHost allows the Web UI origin in its development CORS configuration).

The AppHost (`dotnet run --project src/platform/SocAlytics.Platform.AppHost`) also starts the Web UI on one origin with the API. After API changes, refresh the OpenAPI snapshot as described in the root [README](../../README.md#web-ui).

## Container Image

`web/Dockerfile` builds the cloud-neutral Web UI image from the repository root; it needs the arguments `SOCALYTICS_REVISION` and `SOCALYTICS_VERSION` (the same release values as the platform images):

```powershell
docker build -f src/clients/web/Dockerfile --build-arg SOCALYTICS_REVISION=$revision --build-arg SOCALYTICS_VERSION=$version -t socalytics-web:local .
```

The image serves the built files byte for byte (so every file matches the integrity in `shell-manifest.json`) as the non-root numeric user `101` on port `8080` (TLS terminates outside the image), with a read-only root filesystem and a writable tmpfs at `/tmp`. Configuration is read from environment variables only:

| Variable | Required | Meaning |
| --- | --- | --- |
| `SOCALYTICS_API_UPSTREAM` | yes | Base URL of the platform API container, for example `http://api:8080` |
| `SOCALYTICS_OBJECT_STORAGE_ORIGIN` | no | Origin added to the `connect-src` of the Content Security Policy for direct uploads |

The image serves the Web UI and the platform API on one origin: `/api`, `/api/**`, and `/alive` are forwarded to `SOCALYTICS_API_UPSTREAM` with method, path, query, headers (including `SocAlytics-Minimum-Web-Version` in responses), and body unchanged, streamed without buffering, and answered with `502` when the API is unreachable while static files and client routes keep working. The image is not deployment support or production readiness; its evidence is `dotnet test src/platform/Tests/SocAlytics.Platform.Images.Tests` (Docker required).
