## Authority Boundaries

- `docs/architecture/` is authoritative for the coherent current system design, and at merge it must describe the implemented state (constitution Principle I): every plan has an `## Architecture Updates` section (or `None` with a reason), and each feature's documentation task corrects every architecture statement it makes false, including planned, future-tense, or unimplemented wording outside its own sections.
- Component-local executable contracts and implementation guidance belong with the component that owns and validates them.
- Preserve unresolved decisions explicitly. Do not present provisional values, target-state descriptions, or missing production evidence as adopted facts.

## Spec Kit

- Feature work follows GitHub Spec Kit `1.0.13` in GitHub Copilot skills mode: `/speckit-specify`, optional `/speckit-clarify`, `/speckit-plan`, `/speckit-tasks`, optional `/speckit-analyze`, `/speckit-implement`, and `/speckit-converge`.
- `/speckit-gha-author [architecture section | folders | feature idea | "the N logical next specs"]` is the client-side entry point for new specs: it runs the Spec Kit skills in Copilot Chat in their order (`/speckit-specify`, `/speckit-clarify`, `/speckit-plan`, optional `/speckit-checklist`, `/speckit-tasks` with its refine hook, `/speckit-analyze`), creates every artifact, checks the spec is ready to publish (`node .github/scripts/speckit-author.mjs status <folder>`), and ends with the decision to commit and push. Without input it proposes the next logical spec from the architecture, the existing specs, and the code; with a count it finds that many next specs and authors them one after another. Interactively it pauses for the user after each stage; in autopilot (the Copilot session mode the user sets, not a command flag) it answers every decision, including clarification questions and analysis remediation, with the recommended choice and ends with the specs ready to commit, committing and pushing only when the input asks for it. It never changes spec artifacts outside the Spec Kit skills and never requests implementation.
- [`.specify/memory/constitution.md`](.specify/memory/constitution.md) governs every spec, plan, and task list. Amend it with `/speckit-constitution` and keep it consistent with this file.
- Feature artifacts live in `specs/<YYYYMMDD-HHMMSS>-<short-name>/` folders created by `/speckit-specify` (`feature_numbering` is `timestamp` to avoid collisions between developers). The prefix MUST be the current UTC time; Spec Kit's helper scripts use local time, so run them with `TZ=UTC`. The prefix carries no dependency meaning: spec twin issue dependencies define the automation order. `specs/README.md` is a stable authoring guide that lists no specs; the spec twin issues (label `speckit:spec`) are the index, so never add a row per spec there.
- Implemented specs are archived to `specs/archive/<folder>` (same folder name) in the commit that merges their implementation, so the base branch never has broken links: the implementation automation does it in its merge (job `Archive the spec before the merge`), and local or manual merges use `/speckit-gha-archive` (`node .github/scripts/speckit-archive.mjs <folder>`), which also rewrites Markdown links and plain-text `specs/<folder>` mentions. Never move a spec folder by hand, and link to archived specs under `specs/archive/`.
- The helper scripts are Python (`.specify/scripts/python/`) and run as `python` from the repository root.
- `.github/skills/speckit-*` and everything under `.specify/` except the constitution and `.specify/extension-src/` are managed by the `specify` CLI. Do not hand-edit them; refresh them through the `specify` CLI upgrade flow.
- `.specify/extension-src/gha/` is the source of the repository-local Spec Kit extension `gha`. After changing it, reinstall with `specify extension add .specify/extension-src/gha --dev --force`, replace any generated `.github/skills/speckit-gha-*/SKILL.md` symbolic links with regular files as described in its README, and commit the source together with the generated `.specify/extensions/`, `.specify/extensions.yml`, and skill files.
- Do not run `/speckit-taskstoissues`. Features, not tasks, are mirrored to GitHub as spec twins by `.github/workflows/speckit-prepare.yml`.
- `/speckit-tasks` ends with the `gha` extension's mandatory `after_tasks` hook `/speckit-gha-refine`, which makes the `[P]` groups of `tasks.md` safe: consecutive unchecked `[P]` tasks under one heading run in parallel, so their predicted file changes (including registrations, project files, and shared configuration) must not overlap. It changes only `tasks.md`, separates groups with `###` or `####` headings (never `##`, which starts a phase), and for a spec already being implemented only fixes conflicting groups without moving or renumbering tasks. `node .github/scripts/speckit-tasks-groups.mjs <folder>` prints the task order as the workflow plans it.
- `/speckit-plan` ends with the `gha` extension's mandatory `after_plan` hook `/speckit-gha-architecture`, which writes the `## Architecture Updates` section of `plan.md` (affected narratives, design updates applied now, status statements to correct at merge) and requires an outcome-based documentation task; `speckit-author.mjs status` refuses to publish without the section, or, unless it says `None`, without a task that references `docs/architecture/`. `/speckit-converge` starts with the mandatory `before_converge` hook `/speckit-gha-drift`, a read-only check of `docs/architecture/` against the implementation whose findings become convergence tasks. Implementation branches created before a hook existed get it when the chain next merges the base branch (before a phase, the convergence, or the merge). Diagnosis amendments never edit `docs/architecture/`; they carry a changed design decision into an unchecked documentation task.

## Spec Twins

- The goal of the workflow automation is to get pull requests merged by giving people the best guidance to reach that goal. Every handoff to a person must prominently recommend exactly one concrete next action, explain why it is the best way forward and what it triggers, and identify the target pull request. Provide a ready-to-paste comment or `/speckit` command with actual guidance (no placeholders) when that is the action; explicitly recommend review and merge when the pull request is ready. Keep alternatives collapsed. Findings that automation can correct must trigger correction, not just a report; while automation is running, say what it is doing and that no action is needed yet. Never recommend merging on a failed or missing analysis, or bypassing required verification to reach the goal.
- `/speckit sync [guidance]` is a required synchronization barrier: it merges the latest PR base branch regardless of `SPECKIT_SYNC_BASE` or earlier best-effort skips and stops for attention on failure instead of continuing on the old base, preserving checked tasks, pending repair scope, and repair attempt limits. Automatic diagnoses replace the removed `diagnose` and `resume` commands. A diagnosis for a fix already on the base branch classifies it as `outside` and recommends `sync`; inconsistent diagnosis recommendations are rejected at publication, and a recommended command that already failed the same way on the unchanged branch (`repeatedFailure`) is moved to the other options with `/speckit specify` as the fallback. When a diagnosis recommends `/speckit retry` (category `retry`, confidence medium or high) or `/speckit sync` (category `outside`), the tooling posts that command itself, at most once after each action of a person and never for a repeated failure (marker `speckit-implement:auto-continue`; repository variable `SPECKIT_AUTO_CONTINUE=false` turns it off). The verification reruns failing .NET tests once (at most 10) and Playwright tests once; a test that passes on the rerun is reported as flaky (marker `speckit-implement:flaky`), and a test flaky in `SPECKIT_FLAKY_THRESHOLD` (default 3) pull requests within 14 days gets one `/speckit specify` run that does not block the implementation it is started on. Guidance only steers the next agent prompt; [Where AI runs and where guidance applies](.github/workflows/README.md#where-ai-runs-and-where-guidance-applies) lists every place. [Comment commands](.github/workflows/README.md#comment-commands) in the workflows README is the canonical description of every command, its flags, and its guidance; its table is generated from `PR_COMMANDS`.

- Each feature folder under `specs/` or `specs/archive/` on the default branch has one twin issue labelled `speckit:spec`; twins of archived specs are closed as completed, labelled `implemented`, and link to the archive. Its generated `**Spec**` link line is its identity; the workflow regenerates the title and description, so change the spec, never the twin body.
- Twins are pointers, not trackers. The repository is authoritative for spec content; native GitHub issue dependencies between twins are authoritative for the order in which GitHub automation may implement features, and do not constrain local work.
- `speckit:deps-pending` marks twins whose dependencies Copilot CLI has not yet inferred. Inference runs once per new twin; after that, humans maintain the dependencies on GitHub.
- `speckit:stage:*` labels (`specified`, `planned`, `tasked`, `implement`, `implementing`, `implemented`, `discarded`) are generated from the files on the default branch and the implementation request, and only the GitHub bot sets or removes them: `Spec Kit prepare` restores any stage label a person adds or removes and explains it once in a comment. The `**Status**` line in `spec.md` is not maintained or used.
- Implementation is requested only with the comment command `/speckit implement` on the spec twin issue (people with write access), which also documents who requested it: every non-archived twin ends with a copyable `/speckit implement` code block. The command is accepted only for an open twin whose computed stage is `tasked` and whose checklists are all checked on the default branch; it posts a record comment (who and when) and the bot sets `speckit:stage:implement`, a "ready to act" request for the `Spec Kit orchestrate` workflow. `/speckit-gha-request` and choosing GitHub when `/speckit-implement` asks (the `gha` extension's `before_implement` hook) post that comment with the user's token. A hand-set `implement` label is removed with a comment recommending the command. Open blockers do not invalidate the request; the workflow waits for them. Requested twins move through `implement` (waiting to start) >> `implementing` (set by `Spec Kit orchestrate` once the implementation pull request is open) >> `implemented` (merged). `Spec Kit prepare` keeps a valid `implementing` stage like the request and revokes either one when its conditions no longer hold; who requested it and when comes from the record comment (the label history for requests made before the command existed). `implementing` is also the computed stage of a folder whose tasks are partly checked on the default branch (local implementation), which is not an implementation request.
- When running `/speckit-implement` without a person to answer the routing question, set `SPECKIT_IMPLEMENT_MODE=local` or `SPECKIT_IMPLEMENT_MODE=remote`; inside GitHub Actions the hook always implements locally.
- `Spec Kit orchestrate` owns the `speckit/<folder>` branches and their draft pull requests. Each draft pull request closes its twin when merged, carries the task list as checkboxes, and reports status through the `Spec Kit implementation` check run and progress through comments. An open pull request means the spec is in progress; closing it without merging returns the twin to its computed stage. Do not push to `speckit/**` branches or edit those pull requests by hand unless you take over the implementation or resolve a problem the automation asked for; such a push continues the implementation automatically.
- `Spec Kit orchestrate` is the scheduler: it starts implementations (at most `SPECKIT_MAX_ACTIVE_SPECS` at a time) and continues a broken chain. Each spec is implemented by its own chain of `Spec Kit implement spec` runs: every run decides what comes next, implements one phase through the reusable `Spec Kit implement phase`, whose serialized units call `Spec Kit implement group` and whose groups call `Spec Kit implement task` once per task, applies writer-approved post-landing verification repairs through `Spec Kit implement repair`, runs `/speckit-converge` through the reusable `Spec Kit implement convergence` as the acceptance gate once all tasks are checked, resolves merge conflicts through the reusable `Spec Kit implement conflict resolution`, or archives, verifies, and lands through the reusable `Spec Kit implement merge`, and then starts the next run. A task workflow alone ticks its task: its land job checks the box after the verification passed, so the agent does not edit `tasks.md` (its own correct tick is still accepted). Multi-task groups are verified together only when a landing had to merge a sibling's edits to the same files three-way (the landing names those files in its commit message): then the affected tests of the group's changes run, and on failure the landed tasks remain checked while durable repair state blocks later work until diagnosis guidance is approved and the repair passes reverification. Without combined edits, each task's own verification and the phase verification cover the group. Every run first pulls the base branch through its job `sync` ("Merge the base branch") when the next work is a phase that has not started, the convergence, or the merge (repository variable `SPECKIT_SYNC_BASE`, default `true`); retries and other continuations of a started phase preserve that phase's base; a conflict is resolved by the Copilot CLI conflict resolution in the same run. Before a phase or the convergence that is best effort and never stops the implementation (refused merges, conflicts in protected paths, and resolutions that fail twice are left to the final merge); before the merge it is required. Agents only run in read-only jobs; a separate job that never executes agent-written code validates, commits, and pushes. When working on tasks there, implement only the named task, leave `tasks.md` alone (the land job ticks the task), and do not change `.github/`, `.specify/`, or other files under `specs/` (the environment action folders are the only exception, and only in environment specs); repair changes already-landed code without changing `tasks.md`, convergence may only append a convergence section to `tasks.md`, and conflict resolution may only change the conflicted files, the files the implementation branch changed itself, and new files (so it can fix clashes without a textual conflict, such as two migrations with the same number), plus, when the merged result needs it, the smallest change to other files of the base branch (never deleting them or weakening a test), which the land job records on the pull request and which hold the final merge for a person's review. Conflicts under `specs/` that the archive's reference rewrites cause are resolved by the archive script (`resolveSpecConflicts`) before any agent, so they never wait for a person; conflicts in the implementation's own spec artifacts that remain go to the conflict resolution, which must keep every task and checked box, and hold the final merge for review. Outside its own spec folder an implementation may change `specs/` only by reference rewrites of the archive (`referenceOnlySpecChanges`, checked by the merge verification). Other changes fail the attempt. Each task, convergence, conflict resolution, and merge gets at most two failed attempts (`MAX_TASK_ATTEMPTS`), counted from the attempt markers in the pull request comments (merges from their check runs), before the person who requested the implementation is asked; every failed repair attempt stops for a person, and every restart gets a fresh repair attempt. A stop is reported once.
- Verified, converged implementations are squash-merged into their base branch (the implementation pull request's base, the branch `speckit/<folder>` was created from; currently always the default branch) without human review unless the repository variable `SPECKIT_AUTO_MERGE` is `false`; people are only asked when automation cannot continue, and a push by them to the implementation branch continues it.
- Implementation, amendment, and authored spec pull requests that wait for a person (stopped without a running diagnosis, a diagnosis or authored spec outcome to decide on, presented for review, or held for review) carry GitHub's default `help wanted` label (`ATTENTION_LABEL` in `.github/scripts/speckit-implement-core.mjs`); the tooling removes it once a person's action puts automation back to work or the pull request is merged or closed. Never rely on it instead of the check runs and comments.
- Every label the tooling puts on a pull request comes with a comment that explains it: `help wanted` only with a comment that recommends exactly one next step (never while a diagnosis runs), and the custom `blocked` label (`BLOCKED_LABEL`, set through `setBlocked` with an explanation) only with a **Blocked** comment that names what the implementation waits for and how it is unblocked. A blocked implementation never carries `help wanted`, and the scheduler does not continue its chain while it waits.
- When an implementation stops for a person, the `Spec Kit diagnose` agentic workflow (`.github/workflows/speckit-diagnose.md`, GitHub Agentic Workflows) diagnoses it automatically whenever the implementation stops; the stop links to the diagnosis workflow while it runs. It follows the `/speckit-gha-diagnose` skill: classify the stop (`artifacts`, `retry`, `outside`, `decision`, `unknown`), never weaken requirements or tests, and propose an amendment of the spec artifacts only when they are the cause, as a draft pull request `speckit-amend/<folder>` → `speckit/<folder>` that may only change the spec folder (`specs/<folder>/`, or `specs/archive/<folder>/` once the branch archived it for the merge) and never check a task. `Spec Kit analyze` (`speckit-analyze.md`) checks every amendment with an independent, read-only `/speckit-analyze` of the whole folder; findings of every severity, LOW included, lead to correction rounds that continue while they resolve previous findings (at most 3 rounds without progress, 10 in total; once only LOW findings remain, a round that resolves none of them ends the correction, and LOW findings never make an amendment inconsistent) before the amendment is handed to the requester for review. People merge the amendment pull request to apply it, comment or review it (*Comment* or *Request changes*) to have it reworked, or close it to discard it; amendments only merge into their implementation branch, and Spec Kit pull requests are never stacked (a guard resets the base and dissolves stacks); on the implementation pull request they use the comment commands `/speckit retry` (restarts with a fresh attempt count while preserving the current phase base), `/speckit specify`, and `/speckit help` (writers only), handled by `Spec Kit commands`. While the implementation is stopped, `retry` is refused after 2 restarts in a row that left the implementation branch at the same commit, so nobody restarts the same failure endlessly; a push, diagnosis-guided retry, or `/speckit specify` changes something first, and `/speckit retry --force` insists. Every comment that waits for a person recommends exactly one command that fits the diagnosis category and can be posted as it is (no placeholders), says why it helps and what it does, and lists the other options collapsed; `node .github/scripts/speckit-diagnose.mjs check-report <report.json>` checks a diagnosis report the same way. `PR_COMMANDS` in `.github/scripts/speckit-implement-core.mjs` is the single source for the commands: the command router and `/speckit help`, which commands a diagnosis may recommend and for which categories, and the "Commands you can recommend" reference in every diagnosis' evidence (`node .github/scripts/speckit-diagnose.mjs commands` prints it) are derived from it. Add, change, or remove a command only there; the diagnose drift tests then require the diagnose skill (`.specify/extension-src/gha/commands/speckit.gha.diagnose.md`, reinstalled into the gha extension) to name every recommendable command and flag and no unknown one. Fix artifact defects through this flow, not with code patches around them. A cause outside the stopped spec (another feature's code or tests on the base branch, or the environment actions) is fixed through an ordinary new spec: `/speckit specify [guidance]` has the `Spec Kit specify` agentic workflow (`speckit-specify.md`) run `/speckit-gha-author` non-interactively (every recommended choice) to author a complete spec in `specs/<UTC timestamp>-<short-name>/`, proposed as a draft pull request `speckit-spec/<folder>` → the default branch that may only change that folder and `docs/architecture/` (legacy `speckit-fix/<folder>` pull requests keep working). One cause gets one spec: when an open or merged spec already removes the cause, the agent writes nothing and the implementation depends on that spec instead (`reuse`). It is assigned to the person who posted the command, and its description keeps no HTML comments from the agent or gh-aw. It goes through the same analysis and correction rounds as an amendment; once consistent it is merged automatically, unless it changes `docs/architecture/` (then it explains each design decision in a **Design decisions** comment and waits for a person's review) or a person pushed to it. Once merged it is an ordinary spec twin with ordinary dependency inference, and the stopped twin is made to depend on it (never creating a cycle); nothing requests its implementation automatically. Blocking is generic: a running implementation whose twin has open blocked-by twins (from `/speckit specify`, inference, or a person) gets the `blocked` label, is not continued, and retries by itself with a fresh attempt count once the last blocker is implemented; its **Blocked** comment recommends `/speckit implement` on each blocker that is not requested yet. Every requested twin that blocks a running implementation starts ahead of `SPECKIT_MAX_ACTIVE_SPECS`. Merges dispatch `Spec Kit orchestrate`, which lifts the blocks (events of the workflow token start no workflows, so the merge and every dispatched Spec Kit prepare run dispatch orchestrate; its schedule is a fallback only). After editing `speckit-diagnose.md`, `speckit-analyze.md`, or `speckit-specify.md`, recompile with `gh aw compile`; never edit the generated `.lock.yml` files.
- Every pull request comment command has the form `/speckit <command> [flags] [guidance]`: flags start with `--`, directly follow the command, and are declared per command in `PR_COMMANDS` (`.github/scripts/speckit-implement-core.mjs`, parsed by `parseCommandArguments`; case and trailing punctuation such as `--force;` are tolerated, and a bare `--` ends the flags). A flag the command does not support refuses the command instead of becoming guidance. Currently only `retry` has a flag, `--force`.
- Writer-supplied text after `/speckit retry`, `/speckit sync`, or `/speckit specify` and their flags is called guidance: normalized, capped at 4,000 characters, and applied only to the first continued work (see [Guidance](.github/workflows/README.md#guidance)).
- Solution-specific setup and verification for Spec Kit implementation belong in the optional composite actions `.github/actions/environment-setup` and `.github/actions/environment-verify`, not in the Spec Kit workflows or scripts. Keep both actions in line with the documented build and test commands.
- New frameworks, SDKs, or tools reach these actions only through a standalone environment spec: a spec whose implementation changes nothing but the two action folders (plus its own `tasks.md` ticks). Agents may change the action folders only in such a spec; mixing them with other changes fails the task. Environment specs are always held for a person's review, and the merge first self-tests the changed actions. Specs that need the new tooling must name the environment spec as a dependency, so they start only after it is merged. Checks added to `environment-verify` add their paths to `COVERED` only when their project exists and skip while it does not exist yet.
- Changed files that no check covers are listed in the task comments and hold the pull request for review instead of an automatic merge. So do changes a conflict resolution made to files that only the base branch owns.
- All Spec Kit workflows refuse to run from branches other than the default branch. The tooling never assumes the default branch is named `main`: workflows pass it as `SPECKIT_DEFAULT_BRANCH`, local scripts ask GitHub, and every merge, comparison, and link of an implementation uses the pull request's base branch instead. Keep that guard, the `pull_request_target` trigger, and the separate tooling checkout when changing them, and never give a job that runs agent-written code a token that can write.
- Tooling lives in `.github/scripts/speckit-*.mjs`. Run `node --test .github/scripts/speckit-*.test.mjs` after changing it, and keep a readable `name:` on every workflow job and step.
- Every Copilot CLI run in the Spec Kit workflows goes through the composite action `.github/actions/speckit-copilot`, loaded from the trusted tooling checkout. Callers pass a strength level (`light`, `standard`, `strong`); `.github/actions/speckit-copilot/models.json` is the only place to change models or add a level (see `.github/workflows/README.md`, "Copilot CLI and model levels"). Do not call `copilot` directly in a workflow.

- Use the .NET 10 SDK selected by `src/platform/global.json` for platform work.

  dotnet restore src/platform/SocAlytics.Platform.slnx

- The Web UI lives in `src/clients/web` (Node.js 24, Kiota 1.36.0 on `PATH`, Playwright 1.63.0 Chromium). Run `npm ci`, `npm run build`, `npm test`, and `npm run test:e2e` there (`--project simulated` needs no Docker; the `platform` projects start the AppHost in e2e mode). After API changes, refresh the committed OpenAPI snapshot with `SOCALYTICS_UPDATE_OPENAPI_SNAPSHOT=1 dotnet test src/platform/Tests/SocAlytics.Platform.Host.Tests --filter OpenApiSnapshotTests`, never in the verification environment.

Linux Manager tests need SoftHSM2; Windows and macOS key-store tests are skipped elsewhere and verified manually.

- A running Docker-compatible container runtime is required for the AppHost, the Host and Integration tests (`dotnet test`), NATS in the AppHost and in tests, and the Migrator against a local PostgreSQL. Tests must never target developer or production databases; they use disposable containers and fail visibly when Docker is unavailable.

Every new table without `version` gets an entry in `src/platform/Tests/SocAlytics.Platform.Integration.Tests/Structure/PersistedTableClassifications.cs`. State changes run inside `IUnitOfWork` scopes.

Do not infer deployment support or production readiness from successful local restore, build, test, Markdown validation, or AppHost execution.
