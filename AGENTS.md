## Authority Boundaries

- `docs/architecture/` is authoritative for the coherent current system design, and at merge it must describe the implemented state (constitution Principle I): every plan has an `## Architecture Updates` section (or `None` with a reason), and each feature's documentation task corrects every architecture statement it makes false, including planned, future-tense, or unimplemented wording outside its own sections.
- Component-local executable contracts and implementation guidance belong with the component that owns and validates them.
- Preserve unresolved decisions explicitly. Do not present provisional values, target-state descriptions, or missing production evidence as adopted facts.

## Spec Kit

- Feature work follows GitHub Spec Kit `1.0.13` in GitHub Copilot skills mode: `/speckit-specify`, optional `/speckit-clarify`, `/speckit-plan`, `/speckit-tasks`, optional `/speckit-analyze`, `/speckit-implement`, and `/speckit-converge`.
- `/speckit-gha-author [--repeat <n>] [feature idea | spec folder]` (the `gha` extension command [`speckit.gha.author.md`](.specify/extension-src/gha/commands/speckit.gha.author.md)) is the client-side entry point for new specs in Copilot Chat. It only operates the Spec Kit workflow `author` (below): it starts the run with an empty standard input, so every gate pauses the run, reads what the run waits for with `node .github/scripts/speckit-author-flow.mjs pending --run <run>`, asks the person in Chat, and resumes with `specify workflow resume <run> -i <input>=<choice>`; it never runs a Spec Kit skill, edits a spec, or runs git itself. The publish gate is where it shows the spec, plan, and tasks for review and offers `revise` (nothing is committed, and a new run reworks the chosen stage with `stage` and `feedback`). In autopilot it runs the workflow with `mode=unattended` and `publish=push`, so the spec is committed and pushed without a prompt word; interactively the publish gate decides. `--repeat <n>` (only without a feature idea or folder) authors `n` proposed specs one after another, one run each: in autopilot every run commits its spec and the last one pushes them all (a committed spec that only waits for its push is not continued as the active spec, so the next run proposes a new one); it stops at the first run that fails.
- The Spec Kit workflow `author`, shipped by the `gha` extension (source [`.specify/extension-src/gha/workflows/author/workflow.yml`](.specify/extension-src/gha/workflows/author/workflow.yml)), authors one spec to ready-to-implement; in a terminal its gates ask directly: `$env:TZ='UTC'; specify workflow run author -i feature="<feature idea | spec folder>"` (POSIX: `TZ=UTC specify workflow run author …`). An empty `feature` offers to continue the unpublished spec of `.specify/feature.json`, otherwise fetches the remote, lists the spec twins with `gh` (best effort), and proposes the next logical spec from `docs/architecture/`, the existing specs, the twins, and the code; a folder without `spec.md` is refused. It runs one spec through `/speckit-specify`, `/speckit-clarify` (an agent step writes the questions, a gate asks each one, at most three rounds, and questions a final scan still finds stop the run), `/speckit-plan` (with the mandatory `## Architecture Updates` repaired through `/speckit-gha-architecture` and an environment check that never holds an environment spec itself), `/speckit-tasks` (a missing `docs/architecture/` documentation task is added by a second `/speckit-tasks` pass, `[P]` group warnings are repaired through `/speckit-gha-refine`, then a strict check), and up to three `/speckit-analyze` rounds whose remediation a gate per fixable finding approves (up to five per round, the most severe first), then a formatting-only agent step for Markdown findings and the publish checks, and ends by committing the spec folder together with its changed `docs/architecture/` files as `Spec: <title>` and pushing it (a gate asks and warns when the checkout is not on the default branch; input `publish` is `ask`, `push`, `commit`, or `none`). Every decision comes from [`.github/scripts/speckit-author-flow.mjs`](.github/scripts/speckit-author-flow.mjs), whose subcommands print ASCII-only JSON for the workflow's conditions; agent steps only run Spec Kit commands and write the files it validates under the gitignored run folder `.specify/workflows/runs/<run>/`. Every gate is a top-level step (or alone in a top-level `if`) and names its verdict input after its id (`publish-verdict` → `publish_verdict`), because resuming a paused nested step reruns its parent's whole body; loops are therefore unrolled (three clarify rounds, three analyses). Input `mode=unattended` takes every recommended choice and stops instead of asking. Gates only stop where a person improves the spec or decides what is authored or published (the active spec, the candidates, the clarification questions, missing tooling, the analysis fixes, and the publish gate); the run moves from spec to plan to tasks to analysis without asking. To rework an existing spec, run it again with `-i feature=<folder> -i stage=<stage> -i feedback="…"`; `stage` (`clarify`, `plan`, `tasks`, or `analyze`, at most the folder's next step) chooses where it starts again, and `feedback` reworks that stage. Input `stamp` (`YYYYMMDD-HHMMSS`) gives a new folder that UTC time prefix instead of the current time. Command steps run `copilot -p … --yolo`; on Windows use the standalone `copilot.exe`, because `cmd.exe` mangles prompts passed to an npm `.cmd` shim. Its last step writes `result.json` in the common shape of the gha workflows.
- The `gha` extension also ships the implementation workflows `implement-task` (one task through `/speckit-implement`), `converge` (`/speckit-converge` with its drift hook, once every task is checked), `repair` (implemented tasks whose verification failed), and `resolve` (the conflicts of a base branch merge that is already in progress), run with `specify workflow run <id> -i folder=<folder> …` (see the extension README). They never commit, push, or check a task's box, measure the change against the working tree at their start, and check it with the validators of the GitHub land jobs before an optional review gate (interactive mode only; `revise` prints how to run again with `-i feedback="…"`). Every decision comes from [`.github/scripts/speckit-implement-flow.mjs`](.github/scripts/speckit-implement-flow.mjs). All gha workflows follow one design (extension README, "Workflow Design"; shared code in [`.github/scripts/speckit-flow.mjs`](.github/scripts/speckit-flow.mjs)): a deterministic helper per workflow, `start` → agent step → `check` → optional review gate → `result`, and `result.json` in one shape in the run folder. On GitHub the read-only work job of `Spec Kit implement task` runs them through the composite action `.github/actions/speckit-workflow` (unattended, from the trusted tooling checkout through the `tooling` input, never resumed; the run is collected into the job's result folder as `agent-exit.txt`, `agent.jsonl`, `workflow.json`, and `workflow-run/`), and the jobs pass only inputs such as the folder, the task, and the guidance; the prompts live only in the workflow definitions. Every Spec Kit job of one GitHub run checks out the trusted tooling at `github.sha`. A local run resumed after its helper changed (for example through a merge) is refused and must be started again.
- [`.specify/memory/constitution.md`](.specify/memory/constitution.md) governs every spec, plan, and task list. Amend it with `/speckit-constitution` and keep it consistent with this file.
- Feature artifacts live in `specs/<YYYYMMDD-HHMMSS>-<short-name>/` folders created by `/speckit-specify` (`feature_numbering` is `timestamp` to avoid collisions between developers). The prefix MUST be the current UTC time; Spec Kit's helper scripts use local time, so run them with `TZ=UTC`. The prefix carries no dependency meaning: spec twin issue dependencies define the automation order. `specs/README.md` is a stable authoring guide that lists no specs; the spec twin issues (label `speckit:spec`) are the index, so never add a row per spec there.

Never move a spec folder by hand, and link to archived specs under `specs/archive/`.
- The helper scripts are Python (`.specify/scripts/python/`) and run as `python` from the repository root.
- `.github/skills/speckit-*` and everything under `.specify/` except the constitution, `.specify/extension-src/`, and `.specify/.gitignore` are managed by the `specify` CLI. Do not hand-edit them; refresh them through the `specify` CLI upgrade flow.
- The `gha` extension ships its Spec Kit workflows (`author`, `implement-task`, `converge`, `repair`, `resolve`) in `.specify/extension-src/gha/workflows/<id>/`. Spec Kit extensions cannot declare workflows, so after reinstalling the extension, which copies the folders to `.specify/extensions/gha/workflows/<id>/`, register each from there with `specify workflow add --dev .specify/extensions/gha/workflows/<id>` and normalize the backslashes Windows writes into the registry's `source` paths (the extension README has the loop); that generates `.specify/workflows/<id>/workflow.yml` and the entries in `.specify/workflows/workflow-registry.json`, which are committed like the generated skills and never edited by hand otherwise. A drift test in `speckit-author-flow.test.mjs` fails when a copy or the registry differs from the source. Never run `specify workflow remove <id>` on an in-place install: it deletes the folder it was installed from. They are the repository's only Spec Kit workflows: the bundled `speckit` workflow (specify → plan → tasks → implement) is removed, and `specify workflow remove speckit` removes it again if a Spec Kit upgrade restores it.
- `.specify/extension-src/gha/` is the source of the repository-local Spec Kit extension `gha`. After changing it, reinstall with `specify extension add .specify/extension-src/gha --dev --force`, replace any generated `.github/skills/speckit-gha-*/SKILL.md` symbolic links with regular files as described in its README, register its workflow again with `specify workflow add --dev .specify/extensions/gha/workflows/author`, and commit the source together with the generated `.specify/extensions/`, `.specify/extensions.yml`, `.specify/workflows/`, and skill files.
- Do not run `/speckit-taskstoissues`. Features, not tasks, are mirrored to GitHub as spec twins by `.github/workflows/speckit-prepare.yml`.
- `/speckit-tasks` ends with the `gha` extension's mandatory `after_tasks` hook `/speckit-gha-refine`, which makes the `[P]` groups of `tasks.md` safe: consecutive unchecked `[P]` tasks under one heading run in parallel, so their predicted file changes (including registrations, project files, and shared configuration) must not overlap. It changes only `tasks.md`, separates groups with `###` or `####` headings (never `##`, which starts a phase), and for a spec already being implemented only fixes conflicting groups without moving or renumbering tasks. `node .github/scripts/speckit-tasks-groups.mjs <folder>` prints the task order as the workflow plans it.
- `/speckit-plan` ends with the `gha` extension's mandatory `after_plan` hook `/speckit-gha-architecture`, which writes the `## Architecture Updates` section of `plan.md` (affected narratives, design updates applied now, status statements to correct at merge) and requires an outcome-based documentation task; `speckit-author.mjs status` refuses to publish without the section, or, unless it says `None`, without a task that references `docs/architecture/`. `/speckit-converge` starts with the mandatory `before_converge` hook `/speckit-gha-drift`, a read-only check of `docs/architecture/` against the implementation whose findings become convergence tasks. Implementation branches created before a hook existed get it when the chain next merges the base branch (before a phase, the convergence, or the merge). Diagnosis amendments never edit `docs/architecture/`; they carry a changed design decision into an unchecked documentation task.

## Spec Twins

- The goal of the workflow automation is to get pull requests merged by giving people the best guidance to reach that goal. Every handoff to a person must prominently recommend exactly one concrete next action, explain why it is the best way forward and what it triggers, and identify the target pull request. Provide a ready-to-paste comment or `/speckit` command with actual guidance (no placeholders) when that is the action; explicitly recommend review and merge when the pull request is ready. Keep alternatives collapsed. Findings that automation can correct must trigger correction, not just a report; while automation is running, say what it is doing and that no action is needed yet. Never recommend merging on a failed or missing analysis, or bypassing required verification to reach the goal.
- `/speckit sync [guidance]` is a required synchronization barrier: it merges the latest PR base branch regardless of `SPECKIT_SYNC_BASE` or earlier best-effort skips and stops for attention on failure instead of continuing on the old base, preserving checked tasks, pending repair scope, and repair attempt limits. Automatic diagnoses replace the removed `diagnose` and `resume` commands. A diagnosis for a fix already on the base branch classifies it as `outside` and recommends `sync`; inconsistent diagnosis recommendations are rejected at publication, and a recommended command that already failed the same way on the unchanged branch (`repeatedFailure`) is moved to the other options with `/speckit author` as the fallback. When a diagnosis recommends `/speckit retry` (category `retry`, confidence medium or high) or `/speckit sync` (category `outside`), the tooling posts that command itself, at most once after each action of a person and never for a repeated failure (marker `speckit-implement:auto-continue`; repository variable `SPECKIT_AUTO_CONTINUE=false` turns it off). The verification reruns failing .NET tests once (at most 10) and Playwright tests once; a test that passes on the rerun is reported as flaky (marker `speckit-implement:flaky`), and a test flaky in `SPECKIT_FLAKY_THRESHOLD` (default 3) pull requests within 14 days gets one `/speckit author` run that does not block the implementation it is started on. Guidance only steers the next agent prompt; [Where AI runs and where guidance applies](.github/workflows/README.md#where-ai-runs-and-where-guidance-applies) lists every place. [Comment commands](.github/workflows/README.md#comment-commands) in the workflows README is the canonical description of every command, its flags, and its guidance; its table is generated from `PR_COMMANDS`.

- Each feature folder under `specs/` or `specs/archive/` on the default branch has one twin issue labelled `speckit:spec`; twins of archived specs are closed as completed, labelled `implemented`, and link to the archive. Its generated `**Spec**` link line is its identity; the workflow regenerates the title and description, so change the spec, never the twin body.
- Twins are pointers, not trackers. The repository is authoritative for spec content; native GitHub issue dependencies between twins are authoritative for the order in which GitHub automation may implement features, and do not constrain local work.
- `speckit:deps-pending` marks twins whose dependencies Copilot CLI has not yet inferred. Inference runs once per new twin; after that, humans maintain the dependencies on GitHub.
- `speckit:stage:*` labels (`specified`, `planned`, `tasked`, `implement`, `implementing`, `implemented`, `discarded`) are generated from the files on the default branch and the implementation request, and only the GitHub bot sets or removes them: `Spec Kit prepare` restores any stage label a person adds or removes and explains it once in a comment. The `**Status**` line in `spec.md` is not maintained or used.
- Implementation is requested only with the comment command `/speckit implement` on the spec twin issue (people with write access), which also documents who requested it: every non-archived twin ends with a copyable `/speckit implement` code block. The command is accepted only for an open twin whose computed stage is `tasked` and whose checklists are all checked on the default branch; it posts a record comment (who and when) and the bot sets `speckit:stage:implement`, a "ready to act" request for the `Spec Kit orchestrate` workflow. `/speckit-gha-request` and choosing GitHub when `/speckit-implement` asks (the `gha` extension's `before_implement` hook) post that comment with the user's token. A hand-set `implement` label is removed with a comment recommending the command. Open blockers do not invalidate the request; the workflow waits for them. Requested twins move through `implement` (waiting to start) >> `implementing` (set by `Spec Kit orchestrate` once the implementation pull request is open) >> `implemented` (merged). `Spec Kit prepare` keeps a valid `implementing` stage like the request and revokes either one when its conditions no longer hold; who requested it and when comes from the record comment (the label history for requests made before the command existed). `implementing` is also the computed stage of a folder whose tasks are partly checked on the default branch (local implementation), which is not an implementation request.
- When running `/speckit-implement` without a person to answer the routing question, set `SPECKIT_IMPLEMENT_MODE=local` or `SPECKIT_IMPLEMENT_MODE=remote`; inside GitHub Actions the hook always implements locally.
- `Spec Kit orchestrate` owns the `speckit/<folder>` branches and their draft pull requests. Each draft pull request closes its twin when merged, carries the task list as checkboxes, and reports status through the `Spec Kit implementation` check run and progress through comments. An open pull request means the spec is in progress; closing it without merging returns the twin to its computed stage. Do not push to `speckit/**` branches or edit those pull requests by hand unless you take over the implementation or resolve a problem the automation asked for; such a push continues the implementation automatically.
- `Spec Kit orchestrate` is the scheduler: it starts implementations (at most `SPECKIT_MAX_ACTIVE_SPECS` at a time) and continues a broken chain. Once no spec is left that a person can request with `/speckit implement` (a non-archived folder at the computed stage `tasked` with every checklist item checked, whose twin is open and not requested or not created yet), it starts `Spec Kit backlog` (`speckit-backlog.yml`; repository variable `SPECKIT_BACKLOG_SPECS`, default 5, at most 10, `0` turns it off; one at a time, and a day after a refill that did not succeed): it does what `/speckit-gha-author --repeat <n>` does in autopilot (n unattended runs of the Spec Kit workflow `author` without a feature, each committing its spec, stopping at the first failure) in a read-only job, and its land job checks that the commits only add new spec folders and change `docs/architecture/`, pushes them straight to the default branch without a pull request, and dispatches `Spec Kit prepare` for their twins; implementation still needs `/speckit implement`. Each spec is implemented by its own chain of runs, each named `Spec Kit implement spec #<twin> · <title> · <what it works on>` and run by the workflow of its kind of work: `Spec Kit implement group` (`speckit-implement-group.yml`), `Spec Kit implement verify` (`speckit-implement-verify.yml`), `Spec Kit implement repair` (`speckit-implement-repair.yml`), or `Spec Kit implement merge` (`speckit-implement-merge.yml`); a run without work (a stop at an attempt limit, a failure, a finished implementation, or work it cannot tell) runs in `Spec Kit implement decide` (`speckit-implement-decide.yml`), which reports the stop, starts the diagnosis, or marks the implementation done. Every run prepares itself with the reusable `Spec Kit implement prepare` (`speckit-implement-prepare.yml`: merge the base branch, decide what comes next), does one unit, and starts the next run in the workflow of its kind (`predictNextRun`); a run that finds work of another kind (the state changed after it was started) hands it over before it starts any attempt. The units are a sequential group (the consecutive unchecked tasks without `[P]` of a phase, a matrix with `max-parallel: 1`), a parallel group (consecutive unchecked `[P]` tasks under one heading, also a single one, a matrix with `max-parallel: 5`; group sizes are not capped), the verification of a finished phase (a run of its own, recorded as a `verify` attempt), a writer-approved post-landing verification repair, `/speckit-converge` as the acceptance gate once all tasks are checked and verified, a conflict resolution, or the merge (archive, verify, land). Each task, the convergence, a repair, and a conflict resolution run in the reusable `Spec Kit implement task` (`speckit-implement-task.yml`, a read-only work job and a write-isolated land job). Its land job alone ticks a task: it checks the box after the verification passed, so the agent does not edit `tasks.md` (its own correct tick is still accepted). Multi-task groups are verified together only when a landing had to merge a sibling's edits to the same files three-way (the landing names those files in its commit message): then the affected tests of the group's changes run, and on failure the landed tasks remain checked while durable repair state blocks later work until diagnosis guidance is approved and the repair passes reverification. Without combined edits, each task's own verification and the phase verification cover the group. Every run first pulls the base branch through its job `sync` ("Merge the base branch") when the next work is a phase that has not started, the convergence, or the merge (repository variable `SPECKIT_SYNC_BASE`, default `true`); retries and other continuations of a started phase preserve that phase's base; a conflict is resolved by the Copilot CLI conflict resolution in the same run. Before a phase or the convergence that is best effort and never stops the implementation (refused merges, conflicts in protected paths, and resolutions that fail twice are left to the final merge); before the merge it is required. Agents only run in read-only jobs; a separate job that never executes agent-written code validates, commits, and pushes. When working on tasks there, implement only the named task, leave `tasks.md` alone (the land job ticks the task), and do not change `.github/`, `.specify/`, or other files under `specs/` (the environment action folders are the only exception, and only in environment specs); repair changes already-landed code without changing `tasks.md`, convergence may only append a convergence section to `tasks.md`, and conflict resolution may only change the conflicted files, the files the implementation branch changed itself, and new files (so it can fix clashes without a textual conflict, such as two migrations with the same number), plus, when the merged result needs it, the smallest change to other files of the base branch (never deleting them or weakening a test), which the land job records on the pull request and which hold the final merge for a person's review. Conflicts under `specs/` that the archive's reference rewrites cause are resolved by the archive script (`resolveSpecConflicts`) before any agent, so they never wait for a person; conflicts in the implementation's own spec artifacts that remain go to the conflict resolution, which must keep every task and checked box, and hold the final merge for review. Outside its own spec folder an implementation may change `specs/` only by reference rewrites of the archive (`referenceOnlySpecChanges`, checked by the merge verification). Other changes fail the attempt. Each task, convergence, conflict resolution, and merge gets at most two failed attempts (`MAX_TASK_ATTEMPTS`), counted from the attempt markers in the pull request comments (merges from their check runs), before the person who requested the implementation is asked; every failed repair attempt stops for a person, and every restart gets a fresh repair attempt. A stop is reported once.
- Verified, converged implementations are squash-merged into their base branch (the implementation pull request's base, the branch `speckit/<folder>` was created from; currently always the default branch) without human review unless the repository variable `SPECKIT_AUTO_MERGE` is `false`; people are only asked when automation cannot continue, and a push by them to the implementation branch continues it.
- Implementation, amendment, and authored spec pull requests that wait for a person (stopped without a running diagnosis, a diagnosis or authored spec outcome to decide on, presented for review, or held for review) carry GitHub's default `help wanted` label (`ATTENTION_LABEL` in `.github/scripts/speckit-implement-core.mjs`); the tooling removes it once a person's action puts automation back to work or the pull request is merged or closed. Never rely on it instead of the check runs and comments.
- Every label the tooling puts on a pull request comes with a comment that explains it: `help wanted` only with a comment that recommends exactly one next step (never while a diagnosis runs), and the custom `blocked` label (`BLOCKED_LABEL`, set through `setBlocked` with an explanation) only with a **Blocked** comment that names what the implementation waits for and how it is unblocked. A blocked implementation never carries `help wanted`, and the scheduler does not continue its chain while it waits.
- When an implementation stops for a person, the `Spec Kit diagnose` agentic workflow (`.github/workflows/speckit-diagnose.md`, GitHub Agentic Workflows) diagnoses it automatically whenever the implementation stops; the stop links to the diagnosis workflow while it runs. It follows the `/speckit-gha-diagnose` skill: classify the stop (`artifacts`, `retry`, `outside`, `decision`, `unknown`), never weaken requirements or tests, and propose an amendment of the spec artifacts only when they are the cause, as a draft pull request `speckit-amend/<folder>` → `speckit/<folder>` that may only change the spec folder (`specs/<folder>/`, or `specs/archive/<folder>/` once the branch archived it for the merge) and never check a task. `Spec Kit analyze` (`speckit-analyze.md`) checks every amendment with an independent, read-only `/speckit-analyze` of the whole folder; findings of every severity, LOW included, lead to correction rounds that continue while they resolve previous findings (at most 3 rounds without progress, 10 in total; once only LOW findings remain, a round that resolves none of them ends the correction, and LOW findings never make an amendment inconsistent) before the amendment is handed to the requester for review. People merge the amendment pull request to apply it, comment or review it (*Comment* or *Request changes*) to have it reworked, or close it to discard it; amendments only merge into their implementation branch, and Spec Kit pull requests are never stacked (a guard resets the base and dissolves stacks); on the implementation pull request they use the comment commands `/speckit retry` (restarts with a fresh attempt count while preserving the current phase base), `/speckit author`, and `/speckit help` (writers only), handled by `Spec Kit commands`. While the implementation is stopped, `retry` is refused after 2 restarts in a row that left the implementation branch at the same commit, so nobody restarts the same failure endlessly; a push, diagnosis-guided retry, or `/speckit author` changes something first, and `/speckit retry --force` insists. Every comment that waits for a person recommends exactly one command that fits the diagnosis category and can be posted as it is (no placeholders), says why it helps and what it does, and lists the other options collapsed. When the remedy is a change only a push to the implementation branch can make (another spec's folder, a protected path, the change a person's decision needs), a `decision` diagnosis recommends a ready-to-post `@copilot` prompt instead (the option's `copilot` field; `renderCopilotRequest` adds the fixed scope): GitHub Copilot's cloud agent pushes the change to the pull request's branch, and, like any push that is not by `github-actions[bot]`, it continues the implementation; a refused `/speckit retry` recommends the latest diagnosis' `@copilot` request; `node .github/scripts/speckit-diagnose.mjs check-report <report.json>` checks a diagnosis report the same way. `PR_COMMANDS` in `.github/scripts/speckit-implement-core.mjs` is the single source for the commands: the command router and `/speckit help`, which commands a diagnosis may recommend and for which categories, and the "Commands you can recommend" reference in every diagnosis' evidence (`node .github/scripts/speckit-diagnose.mjs commands` prints it) are derived from it. Add, change, or remove a command only there; the diagnose drift tests then require the diagnose skill (`.specify/extension-src/gha/commands/speckit.gha.diagnose.md`, reinstalled into the gha extension) to name every recommendable command and flag and no unknown one. Fix artifact defects through this flow, not with code patches around them. A cause outside the stopped spec (another feature's code or tests on the base branch, or the environment actions) is fixed through an ordinary new spec: `/speckit author [guidance]` has the regular workflow `Spec Kit author` (`speckit-author.yml`, no agent of its own) let one decision step write `decision.json` (reuse, refuse, or a feature description) and then run the Spec Kit workflow `author` unattended (every recommended choice, `publish=commit`, the request's time stamp as `stamp`; its agent steps call Copilot CLI through `speckit-copilot.mjs exec` with a `models.json` level and the Spec Kit deny-list) to author a complete spec in `specs/<UTC timestamp>-<short-name>/`; its job `land` (write token, never runs agent-written code) pushes it, proposed as a draft pull request `speckit-spec/<folder>` → the default branch that may only change that folder and `docs/architecture/` (legacy `speckit-fix/<folder>` pull requests keep working). One cause gets one spec: when an open or merged spec already removes the cause, the decision step writes nothing and the implementation depends on that spec instead (`reuse`). It is assigned to the person who posted the command. Correction rounds (`fix`) and reworks after review (`revise`) run the same workflow on the spec branch, from the stage (`clarify`, `plan`, `tasks`) of the earliest artifact the findings or feedback name. It goes through the same analysis and correction rounds as an amendment; once consistent it is merged automatically, unless it changes `docs/architecture/` (then the **Design decisions** comment lists each decision of its plan's `## Architecture Updates` and it waits for a person's review) or a person pushed to it. Once merged it is an ordinary spec twin with ordinary dependency inference, and the stopped twin is made to depend on it (never creating a cycle); nothing requests its implementation automatically. Blocking is generic: a running implementation whose twin has open blocked-by twins (from `/speckit author`, inference, or a person) gets the `blocked` label, is not continued, and retries by itself with a fresh attempt count once the last blocker is implemented; its **Blocked** comment recommends `/speckit implement` on each blocker that is not requested yet and links the open implementation pull request of each blocker that has one (posted again when a blocker's implementation pull request opens). Every requested twin that blocks a running implementation starts ahead of `SPECKIT_MAX_ACTIVE_SPECS`. Merges dispatch `Spec Kit orchestrate`, which lifts the blocks (events of the workflow token start no workflows, so the merge and every dispatched Spec Kit prepare run dispatch orchestrate; its schedule is a fallback only). After editing `speckit-diagnose.md` or `speckit-analyze.md`, recompile with `gh aw compile`; never edit the generated `.lock.yml` files.
- Every pull request comment command has the form `/speckit <command> [flags] [guidance]`: flags start with `--`, directly follow the command, and are declared per command in `PR_COMMANDS` (`.github/scripts/speckit-implement-core.mjs`, parsed by `parseCommandArguments`; case and trailing punctuation such as `--force;` are tolerated, and a bare `--` ends the flags). A flag the command does not support refuses the command instead of becoming guidance. Currently only `retry` has a flag, `--force`.
- Writer-supplied text after `/speckit retry`, `/speckit sync`, or `/speckit author` and their flags is called guidance: normalized, capped at 4,000 characters, and applied only to the first continued work (see [Guidance](.github/workflows/README.md#guidance)).
- Solution-specific setup and verification for Spec Kit implementation belong in the optional composite actions `.github/actions/environment-setup` and `.github/actions/environment-verify`, not in the Spec Kit workflows or scripts. Keep both actions in line with the documented build and test commands.
- New frameworks, SDKs, or tools reach these actions only through a standalone environment spec: a spec whose implementation changes nothing but the two action folders (plus its own `tasks.md` ticks). Agents may change the action folders only in such a spec; mixing them with other changes fails the task. Environment specs are always held for a person's review, and the merge first self-tests the changed actions. Specs that need the new tooling must name the environment spec as a dependency, so they start only after it is merged. Checks added to `environment-verify` add their paths to `COVERED` only when their project exists and skip while it does not exist yet.
- Changed files that no check covers are listed in the task comments and hold the pull request for review instead of an automatic merge. So do changes a conflict resolution made to files that only the base branch owns.
- Spec Kit workflows that work on one spec take its twin as the input `issue` (never `twin`) and check it first with the step "Check the spec issue" (`speckit-issue.mjs check`: an issue labelled `speckit:spec`, not a pull request); their writing jobs run only after it passed.
- All Spec Kit workflows refuse to run from branches other than the default branch. The tooling never assumes the default branch is named `main`: workflows pass it as `SPECKIT_DEFAULT_BRANCH`, local scripts ask GitHub, and every merge, comparison, and link of an implementation uses the pull request's base branch instead. Keep that guard, the `pull_request_target` trigger, and the separate tooling checkout when changing them, and never give a job that runs agent-written code a token that can write.
- Tooling lives in `.github/scripts/speckit-*.mjs`. Run `node --test .github/scripts/speckit-*.test.mjs` after changing it, and keep a readable `name:` on every workflow job and step.
- Every Copilot CLI run in the Spec Kit workflows goes through the composite action `.github/actions/speckit-copilot`, loaded from the trusted tooling checkout. Callers pass a strength level (`light`, `standard`, `strong`); `.github/actions/speckit-copilot/models.json` is the only place to change models or add a level (see `.github/workflows/README.md`, "Copilot CLI and model levels"). Do not call `copilot` directly in a workflow.
