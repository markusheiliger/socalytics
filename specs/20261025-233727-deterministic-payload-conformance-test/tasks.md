## Phase 3: User Story 1 - The conformance test fails only when published messages are wrong (Priority: P1) 🎯 MVP

**Goal**: The test passes whenever every published analysis message of a finalized run conforms to its schema and the analyst jobs carry their scope identity, however slowly the publisher runs, and fails only when that behavior is broken.

**Independent Test**: Run the class repeatedly alone and under CPU load: every run passes; with the publication of one message deliberately delayed it still passes; each of three probes makes the named test fail on its assertions; an unpublishable row makes it fail naming the row.

### Implementation for User Story 1

- [x] T006 [US1] In `src/platform/Tests/SocAlytics.Platform.Integration.Tests/Analysis/PayloadConformanceTests.cs`, replace `WaitForReadyWorkAsync` with a wait on the database-observable publication state of the run (data-model.md): the run exists, the run's set of expected ready-work messages is complete, and no outbox row of the run's message set is `pending`. The run's message set is the outbox rows with `run_id` (nullable, migration 0010) = the run's id and `message_type` in (`analysis.ready-work`, `analysis.run-state-changed`), the primary attribution key, with the fallback join through `socalytics.analysis_logical_jobs` kept only if T005 found ready-work or run-state rows with a null `run_id`; other outbox rows are ignored. The expected set is complete when every node of the run's pinned snapshot has its logical job row in `socalytics.analysis_logical_jobs` (so the wait cannot return before the segment-scoped node's job exists) and every logical job is settled: a job is settled only when it is Ready (`socalytics.analysis_readiness_occurrences`) with its published `analysis.ready-work` row, or it waits on an upstream node result of the same run (a dependency on another node's accepted result); a job that waits on segment materialization (or whose segment association is not yet pinned) is never settled, and a job not yet evaluated by the readiness worker is unsettled too; the wait continues until that job is Ready and published, and does not exit while the run's segment-scoped node has no Ready job; the tables, columns, and states that identify these cases are the ones recorded in `PayloadConformanceEvidence.md` by T005, which this task references by name. The wait observes a cancellation token linked to the test token and the fact timeout (the hang guard stays a limit, not the success condition) and catches the `OperationCanceledException` raised by the cancelled test token to throw a failure that lists every row of the run's message set still `pending` (id, `message_type`, `subject`, `attempt_count`, `failure_category`, `next_attempt_at`). A row of the set in state `failed` or `discarded` fails the test at once, naming the row's id, `message_type`, `subject`, `failure_category`, and `attempt_count` (`discarded` fails only because this test's single run has no supersession or cancellation). The wait still advances the single fake clock to drive the publisher and its exit is that condition (no `for` bound of 360 iterations; if a fixed-delay poll remains it is only the pacing of the condition check, not the success condition). Both facts of the class get an explicit `[Fact(Timeout = ...)]`, with an initial value derived from the T002 baseline of the unchanged class (at least ten times the observed maximum, recorded in `research.md`; T010 re-checks it against the fixed test) and documented in a code comment as a hang guard only, not as a longer timeout that fixes anything (FR-002, FR-004, plan Design step 2).
