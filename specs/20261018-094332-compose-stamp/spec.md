# Feature Specification: Compose Stamp Composition for Self-Hosted Evaluation

**Feature Branch**: `20261018-094332-compose-stamp`

**Created**: 2026-10-18

**Status**: Draft

**Input**: User description: "Compose Stamp Composition for Self-Hosted Evaluation: the architecture makes Docker Compose the initial deployment mechanism and the self-hostable profile: one Compose project namespace is one deployment stamp; it composes the platform API and Web UI containers, PostgreSQL, NATS JetStream, and S3-compatible storage on durable stamp-dedicated volumes and internal networks, plus the Migrator as a one-shot service that every API service depends on with `condition: service_completed_successfully`; only declared ingress crosses the stamp boundary; and host, ports, DNS, certificates, secret source, volume paths, replicas, and resource sizes are profile values that stay Open / Blocking until approved with evidence (docs/architecture/platform-implementation.md#source-and-runtime-baseline, docs/architecture/production-operations.md#versioned-production-profile and #scope-and-invariants, docs/architecture/tenancy-and-technology.md#initial-production-profile). Nothing of it exists; the Aspire AppHost remains the supported local entry point. This feature adds a committed Compose definition for one stamp that an operator can use to evaluate a self-hosted stamp on one host: the services above using spec 1's images and pinned infrastructure images by digest, the Migrator one-shot ordering, healthchecks and dependency conditions, internal networks with only the Web UI's declared ingress published, named volumes, the NATS JWT authentication the platform requires outside Development and Test (operator, stamp account, and system account keys and the platform's existing configuration, generated by an documented setup step rather than committed), database roles as the existing local initialization script defines them, object storage bucket provisioning, the Mailpit-free behavior when no SMTP relay is configured or an explicit placeholder relay, and an environment file template that names every required value without defaults for secrets; values the architecture leaves open stay explicit placeholders and the documentation states plainly that this is not a production profile and passes no production preflight. Automated evidence starts the composition with disposable values, waits for the Migrator to complete and the API to report healthy, signs in through the Web UI's one origin as a seeded development Club Admin or via the existing bootstrap path, and tears it down without leaking volumes; it also proves that a second project name yields an isolated stamp. Out of scope: production preflight, backup and restore, TLS termination and certificates, Azure Container Apps, Analyst Managers (they connect from hosts), registries and publishing, monitoring stacks, scaling beyond one replica, production values. Depends on `specs/archive/20261018-092503-oci-images` (batch sibling), Platform Persistence Foundation, Analyst Manager Work Execution (NATS JWT authentication), Recording Lineage and Upload (object storage), Member Email Addresses and Pending-Request Notifications (SMTP configuration) (merged; archived). Implements the Compose parts of docs/architecture/platform-implementation.md#source-and-runtime-baseline and docs/architecture/production-operations.md (composition only; values Open / Blocking)."

## Clarifications

### Session 2026-10-18

- Q: How should a stamp become healthy, given that the existing readiness rule requires a resolvable default analysis workflow that a fresh stamp running in the production environment does not have? → A: The readiness rule stays unchanged and nothing in the composition waits for the API to be healthy (the Web UI starts once the API has started); the documentation explains that the stamp reports healthy once its Registry holds a resolvable default workflow; the evidence arranges one in the stamp database after the Migrator completed, as the image evidence of `specs/archive/20261018-092503-oci-images` does, and then waits for healthy.
- Q: How should the browser's direct recording uploads reach object storage, given that only the Web UI's ingress crosses the stamp boundary? → A: They are not available in the evaluation stamp: object storage stays on the internal network, the Web UI gets no object storage origin, and the documentation names this limitation; a later feature decides a public object storage endpoint.
- Q: How does the composition obtain the API, Migrator, and Web UI images? → A: The environment file names the three image references as required values without defaults, built with the documented commands of `specs/archive/20261018-092503-oci-images`; the definition builds no image itself, while infrastructure images stay pinned by digest in the definition.
- Q: What does the documented setup step produce? → A: Every secret of one stamp (PostgreSQL administrator, migrator, and application role passwords, object storage keys, the NATS operator, stamp account, and system account keys with the matching NATS server configuration, and the first Club Admin's initial credential) into a new stamp directory outside the repository, refusing to overwrite an existing one; the operator fills the non-secret values.
- Q: On which host interface is the Web UI's ingress published, given that TLS is out of scope? → A: On the host's loopback interface only, at an operator-chosen port that is a required value; exposing a stamp beyond the loopback interface needs TLS and stays out of scope.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Bring up one evaluation stamp on one host (Priority: P1)

An operator who wants to evaluate SocAlytics self-hosted has one host with a container engine and the built images of
one release. The operator runs the documented setup step, which produces the stamp's secrets and NATS trust material
in a new stamp directory outside the repository, fills the remaining required values of the environment file
(including the three image references and the published port), and starts the committed
composition under a project name of their choice. The database, messaging, and object storage start on stamp-dedicated
volumes and internal networks, the Migrator runs once and finishes, the API starts only afterwards, and the Web UI is
the only service reachable from outside the stamp, on the host's loopback interface. The stamp reports healthy once its
Registry holds a resolvable default analysis workflow, as the existing readiness rule defines.

**Why this priority**: The architecture names Compose as the initial and self-hostable profile, but no composition
exists; without it nobody can run a stamp outside the developer-only Aspire AppHost.

**Independent Test**: Start the composition with disposable values under one project name and observe that every
service reaches its expected state in dependency order, that the Migrator completed successfully before the API
started, that the API reports alive, and that only the Web UI's ingress is published on the host.

**Acceptance Scenarios**:

1. **Given** the built images of one release and an environment file with every required value, **When** the operator
   starts the composition, **Then** PostgreSQL, NATS JetStream, and object storage report healthy, the Migrator applies
   the migrations and exits successfully, and only then does the API start.
2. **Given** the Migrator fails (for example because a database credential is wrong), **When** the composition starts,
   **Then** the API is not started and the failure is visible in the Migrator's exit code and log.
3. **Given** the started stamp, **When** the host's published ports are listed, **Then** only the Web UI's declared
   ingress is published, bound to the host's loopback interface, and PostgreSQL, NATS, object storage, the Migrator,
   and the API accept connections only from inside the stamp.
4. **Given** the environment file lacks a required value, **When** the operator starts the composition, **Then** the
   start fails before any container runs and names the missing value, instead of using a default for a secret.
5. **Given** a running stamp, **When** the operator stops and starts it again without removing volumes, **Then** the
   stamp keeps its club, accounts, and data, and the Migrator applies nothing on the second start.
6. **Given** a started stamp whose Registry holds no resolvable default analysis workflow, **When** its readiness is
   probed, **Then** the API reports alive but not healthy, exactly as the existing readiness rule defines, and once a
   resolvable default workflow exists, it reports healthy without a restart.

### User Story 2 - Sign in to the evaluation stamp through one origin (Priority: P1)

The operator opens the Web UI's published origin in a browser and signs in as the stamp's first Club Admin, created by
the existing club bootstrap from the configured initial credential, changes the required password, and reaches the
member navigation. Every API call goes through the Web UI's origin, so sessions and anti-forgery work as in local
development.

**Why this priority**: A stamp that cannot be signed in to proves nothing about self-hosting; this is the smallest end
to end value of the composition.

**Independent Test**: With a started stamp, sign in through the published Web UI origin with the bootstrap Club Admin
account and its initial credential, complete the required password change, and read the member's own profile.

**Acceptance Scenarios**:

1. **Given** a started stamp, **When** the operator requests the Web UI's origin, **Then** the installable Web UI shell
   of the release is served and API requests through the same origin reach the API.
2. **Given** the bootstrap Club Admin account name and initial credential from the environment file, **When** the
   operator signs in through the origin, **Then** a session is established and the required password change is
   requested, exactly as the existing sign-in flow defines.
3. **Given** the password change is completed, **When** the operator signs in again with the new password, **Then** the
   member reaches the Club Admin navigation.

---

### User Story 3 - Run several isolated stamps side by side (Priority: P2)

An operator evaluates two stamps (for example two clubs) on the same host. Each stamp is started from the same committed
composition under its own project name and its own environment file. Each stamp has its own volumes, networks,
credentials, database, streams, and bucket; neither can reach the other's services, and removing one leaves the other
intact.

**Why this priority**: The architecture permits shared hosts only when stamps stay isolated and independently testable;
isolation must be evident before anyone relies on the composition for more than one club.

**Independent Test**: Start two stamps with different project names and different disposable values, observe that each
bootstraps its own club, that services of one stamp cannot reach services of the other, and that tearing down one
stamp removes only its own containers, networks, and volumes.

**Acceptance Scenarios**:

1. **Given** two stamps started under different project names, **When** their resources are listed, **Then** every
   container, network, and volume belongs to exactly one stamp, and no name is shared.
2. **Given** both stamps run, **When** a service of one stamp tries to reach the database, messaging, storage, or API
   of the other, **Then** the connection cannot be established.
3. **Given** both stamps run, **When** one stamp is torn down with its volumes, **Then** the other stamp keeps running,
   and its club and data are unchanged.

---

### User Story 4 - Know exactly what the evaluation stamp is and is not (Priority: P2)

An operator or reviewer reads the composition's documentation and environment file template and learns which values
they must supply, which values are placeholders for decisions the architecture leaves open, and that the stamp is an
evaluation composition that is not a production profile and passes no production preflight.

**Why this priority**: The architecture keeps every production profile value Open / Blocking; documentation that blurs
evaluation and production would present unapproved values as adopted.

**Independent Test**: Read the documentation and template and check that every required value is named, no secret has a
default, every open profile value is an explicit placeholder, and the non-production statement is present.

**Acceptance Scenarios**:

1. **Given** the environment file template, **When** it is read, **Then** every value the composition requires is
   named with a description, and no secret has a default value.
2. **Given** the documentation, **When** it is read, **Then** it states that the composition is for self-hosted
   evaluation, is not a production profile, passes no production preflight, and leaves host, ports, DNS, certificates,
   secret source, volume paths, replicas, and resource sizes Open / Blocking.

### Edge Cases

- The setup step is run again for an existing stamp directory: it refuses to write and changes nothing, so existing
  secrets and trust material are never overwritten.
- A second stamp uses the same published port as a running stamp: the second start fails with a port conflict and the
  running stamp is unaffected.
- NATS restarts while the API runs: the API reconnects with its stamp credentials; JetStream state survives on its
  volume.
- The Migrator is started again on an up-to-date database: it applies nothing and exits successfully, so the API starts.
- No SMTP relay exists for the evaluation: the stamp still starts, and email delivery attempts fail and are recorded
  without blocking sign-in.
- The API reports alive but not healthy because the stamp's Registry holds no resolvable default analysis workflow: the
  existing readiness rule is unchanged, nothing in the composition waits for the API to be healthy, and the
  documentation explains what makes the stamp healthy.
- A member starts a recording upload in the evaluation stamp: the direct upload to object storage cannot reach the
  internal object storage, and the documentation names this limitation of the evaluation stamp.
- A volume of a removed stamp would be reused by a new stamp with the same project name: the documented teardown
  removes the stamp's volumes so no data of an earlier stamp leaks into a new one.

## Requirements *(mandatory)*

### Functional Requirements

#### Composition

- **FR-001**: The repository MUST contain one committed Compose definition for one deployment stamp that composes the
  platform API, the Web UI, the Migrator, PostgreSQL, NATS JetStream, and S3-compatible object storage, as the
  architecture's initial profile describes.
- **FR-002**: The composition MUST run the platform API, Migrator, and Web UI from the images defined by the batch
  sibling feature Cloud-Neutral OCI Images (`specs/archive/20261018-092503-oci-images`), honoring their image contract
  (non-root users, read-only root filesystem with a writable temporary location, configuration through environment
  variables, the one-origin forwarding of the Web UI image). The three image references MUST be required values of the
  environment file without defaults, and the definition MUST NOT build images itself.
- **FR-003**: Every infrastructure image the composition uses MUST be pinned by an immutable digest.
- **FR-004**: The Migrator MUST run as a one-shot service, and every API service MUST depend on its successful
  completion, so migrations complete once per deployment before any API replica starts; the Migrator MUST NOT be
  restarted after success.
- **FR-005**: Each infrastructure service MUST declare a health check, and services that use it MUST wait for it to be
  healthy before starting. Nothing in the composition MUST wait for the API to be healthy: the Web UI MUST start once
  the API has started, and the API's existing readiness rule (including its resolvable default analysis workflow)
  MUST stay unchanged.
- **FR-006**: One Compose project name MUST identify one stamp: every container, network, and volume MUST be scoped to
  the project name, and the definition MUST NOT fix any global container, network, or volume name.
- **FR-007**: PostgreSQL data, JetStream state, and object storage data MUST live on named volumes dedicated to the
  stamp.
- **FR-008**: Service-to-service traffic MUST use stamp-internal networks; only the Web UI's declared ingress MUST be
  published to the host, bound to the host's loopback interface at the operator-chosen port, and only the egress the
  API requires (the configured SMTP relay and other configured external endpoints) MAY leave the stamp; the Web UI
  container forwards only to the stamp's API. Object storage
  MUST NOT be published, so the browser's direct recording uploads are not available in the evaluation stamp.
- **FR-009**: The composition MUST run one replica of each service.

#### Credentials and configuration

- **FR-010**: The API MUST authenticate to NATS with the platform's existing JWT authentication; NATS MUST trust the
  stamp's operator, stamp account, and system account, and the API MUST receive the matching keys through the existing
  options.
- **FR-011**: A documented setup step MUST produce every secret of one stamp (the PostgreSQL administrator, migrator,
  and application role passwords, the object storage keys, the NATS operator, stamp account, and system account keys
  with the matching NATS server configuration, and the first Club Admin's initial credential) into a new stamp
  directory outside the repository, and MUST refuse to write into an existing stamp directory. No secret and no NATS
  trust material MUST be committed to the repository.
- **FR-012**: PostgreSQL MUST provision the migrator and application database roles exactly as the existing local
  initialization script defines them; the Migrator MUST use the migrator role and the API the application role.
- **FR-013**: The stamp's object storage bucket MUST exist before the API serves uploads, without manual steps.
- **FR-014**: The composition MUST NOT include a mail catcher; the API MUST be configured with an operator-supplied
  SMTP relay, and when the operator has none, an explicit placeholder relay documented as never delivering mail.
- **FR-015**: The repository MUST contain an environment file template that names every value the composition
  requires, with a description each, and without default values for secrets.
- **FR-016**: Values the architecture leaves open (host, published ports, DNS, certificates, secret source, volume
  paths, replicas, resource sizes) MUST appear as explicit placeholders or documented evaluation choices, never as
  adopted production values.
- **FR-017**: The API MUST run in its production hosting environment with every required option supplied, and the
  composition MUST NOT relax any check that the platform restricts to the Development or Test environments.

#### Documentation

- **FR-018**: The documentation MUST describe how to build or obtain the images, run the setup step, fill the
  environment file, start, inspect, stop, and tear down a stamp, and how to run a second stamp under another project
  name.
- **FR-019**: The documentation MUST state that the composition is for self-hosted evaluation, is not a production
  profile, passes no production preflight, and does not replace the Aspire AppHost as the supported local entry point,
  and MUST name the evaluation stamp's limitations: loopback-only ingress without TLS, no browser recording uploads,
  and readiness that waits for a resolvable default analysis workflow.

#### Evidence

- **FR-020**: Automated tests MUST start the composition with disposable values, wait for the Migrator to complete,
  arrange a resolvable default analysis workflow in the stamp database as the image evidence of
  `specs/archive/20261018-092503-oci-images` does, wait for the API to report healthy, sign in through the Web UI's origin as
  the bootstrap Club Admin, and tear the stamp down leaving no container, network, or volume of the stamp behind.
- **FR-021**: Automated tests MUST prove that the composition publishes only the Web UI's ingress and that a second
  project name yields an isolated stamp whose services cannot reach the first stamp's services.
- **FR-022**: The evidence MUST use only disposable values and resources and MUST fail visibly when the container
  runtime or its Compose support is unavailable, as the repository's other container-backed tests do.

### Key Entities

- **Stamp composition**: the committed definition of one stamp's services, networks, volumes, dependency order, and
  health checks.
- **Stamp**: one running instance of the composition, identified by its project name, with its own volumes, networks,
  credentials, club, and data.
- **Stamp environment file**: the operator's values for one stamp, derived from the template: the three image
  references, the published port, the relay, the club bootstrap values, and the secrets and NATS trust material of the
  setup output.
- **Setup output**: the stamp directory that the setup step creates outside the repository, holding every secret and the
  NATS trust material of one stamp.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: From built images and a filled environment file, an operator brings up a stamp with one start command
  and reaches the sign-in page within 5 minutes on a host that already has the images.
- **SC-002**: In 100% of evidence runs, the API starts only after the Migrator completed successfully, reports alive
  within 3 minutes of the start command, and reports healthy within 1 minute after a resolvable default analysis
  workflow exists.
- **SC-003**: Exactly one published host port per stamp (the Web UI's ingress, on the loopback interface); zero
  published ports for the database, messaging, object storage, Migrator, and API.
- **SC-004**: After teardown, zero containers, networks, and volumes of the stamp remain.
- **SC-005**: Two stamps on one host share zero containers, networks, volumes, and credentials, and zero connection
  attempts from one stamp to the other's services succeed.
- **SC-006**: Zero secrets and zero NATS trust material are committed; every secret in the template has no default.

## Assumptions

- Dependencies: Cloud-Neutral OCI Images (batch sibling `specs/archive/20261018-092503-oci-images`, authored, not yet merged)
  provides the API, Migrator, and Web UI images and their contract; Platform Persistence Foundation
  ([archived](../archive/20261005-130700-platform-persistence-foundation/spec.md)) provides the Migrator, the roles, and
  readiness; Analyst Manager Work Execution ([archived](../archive/20261012-141233-manager-work-execution/spec.md))
  provides NATS JWT authentication; Recording Lineage and Upload
  ([archived](../archive/20261005-130702-recording-lineage-upload/spec.md)) provides object storage configuration; and
  Member Email Addresses and Pending-Request Notifications
  ([archived](../archive/20261013-140140-email-notifications/spec.md)) provides the SMTP configuration.
- Production preflight, backup and restore, TLS termination and certificates, Azure Container Apps, Analyst Managers,
  registries and publishing, monitoring stacks, scaling beyond one replica, and production values are out of scope; the
  profile values stay **Open / Blocking** as
  [Production Deployment and Operations](../../docs/architecture/production-operations.md#versioned-production-profile)
  defines.
- The first Club Admin is created by the existing club bootstrap from configured values; no development seed is used.
- The evidence runs on the build host's CPU architecture with the container engine and Compose support the repository's
  verification environment provides.
