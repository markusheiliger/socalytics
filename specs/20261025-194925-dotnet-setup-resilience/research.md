# Research: Resilient .NET Environment Setup

All Technical Context items are resolved; no `NEEDS CLARIFICATION` remains. Limits are development values, not production commitments.

## R1: Primary source and retry mechanism

- **Decision**: Keep `actions/setup-dotnet` with `global-json-file: <workspace>/src/platform/global.json` as the primary source, pinned to the full commit of its `v5` tag (`26b0ec14cb23fa6904739307f278c14f94c95bf1`, comment `# v5`), and unroll it into three attempts (`continue-on-error: true`, `timeout-minutes: 3`), each running only when the previous attempt did not succeed, with a `sleep 10` step before attempt 2 and `sleep 30` before attempt 3.
- **Rationale**: A composite action has no loop construct, so bounded retries must be unrolled; the existing convention unrolls (see the Spec Kit workflows). Reusing `setup-dotnet` keeps `global-json-file` honouring version, roll-forward, and prerelease policy on every attempt (FR-001) and keeps the primary path identical to today's. Pinning to a commit meets FR-011 (the current `@v5` is a floating tag).
- **Alternatives considered**: Retrying inside one Bash step with the install script (rejected: replaces the primary path and its global.json handling); a third-party retry action such as `nick-fields/retry` (rejected: another unpinned-risk dependency, and it cannot wrap `uses:` steps anyway).

## R2: Candidate acceptance rule

- **Decision**: A pure function `satisfies(version, requirement)` implements the `global.json` rules for `rollForward` (`patch`, `feature`, `minor`, `major`, `latestPatch`, `latestFeature`, `latestMinor`, `latestMajor`, `disable`) and `allowPrerelease`, and `resolve` accepts a candidate only if it satisfies the requirement of **both** `src/platform/global.json` and `src/analysts/manager/global.json`. At run time the helper additionally runs `dotnet --version` with the working directory set to each pinned folder (for the alternative source and for a runner SDK under another root, with the candidate's install directory first on `PATH` and `DOTNET_ROOT` set to it in the child environment, so the muxer cross-checked is the one later steps will use) and requires the version the muxer reports to satisfy every requirement through `acceptable` (not to equal the candidate: runner images preinstall SDKs, so `latestPatch` roll-forward may legitimately resolve a higher installed patch than the one just downloaded). The muxer-reported version is the resolved `dotnet-version` published and shown in the summary, so the real muxer is the final authority and a non-satisfying muxer result rejects the candidate (never accepts it).
- **Rationale**: Offline-testable logic (FR-009) plus a runtime cross-check never loosens anything (FR-003, FR-004); new pin values apply without editing logic (User Story 2, scenario 3). Disagreeing pin files fail visibly naming both files.
- **Alternatives considered**: Only the muxer cross-check (rejected: untestable offline); only the pure function (rejected: could diverge from the muxer on an edge case and accept a non-resolving SDK).

## R3: Fallback order and sources

- **Decision**: After the primary attempts fail (or yield an SDK that fails the acceptance rule), the helper tries, in order: (1) **runner toolchain**: SDKs already installed on the runner (`dotnet --list-sdks` of the `dotnet` on `PATH`, `DOTNET_ROOT`, and `/usr/share/dotnet`), choosing the highest version that satisfies both pinned files; (2) **alternative official feed**: the official `dotnet-install.sh`, installing the latest SDK of the pinned band (`--channel` derived from the pinned major.minor and feature band, `--quality ga`) from the official feed `https://ci.dot.net/public` instead of the primary origin (the helper passes `--azure-feed https://ci.dot.net/public` and `--uncached-feed https://ci.dot.net/public` so the script's own built-in feed fallbacks do not reach the primary origin, and never passes a primary-origin URL), into `$RUNNER_TEMP/dotnet-fallback`; the downloaded install script is verified against a SHA-256 digest committed in `dotnet-resolve.mjs`, and the SDK archive by the install script's own checksum verification against the feed's published checksums. Each candidate then passes the acceptance rule; a rejection moves on to the next source.
- **Rationale**: The spec's clarification requires the primary source first and the runner SDK only as a fallback (FR-002). The runner toolchain needs no network, so it comes before the second download. The install script is the official, documented channel to .NET feeds other than the one `setup-dotnet` uses; the persistent failure is a primary-origin condition. Because the exact version may differ, `--channel` with the latest GA of the band, validated afterwards, satisfies "any SDK that satisfies both pinned files" (clarification 2).
- **Alternatives considered**: Package-manager SDKs (`apt`; rejected: distribution lags, different layout, root install); a repository-side SDK cache (rejected: adds storage, an expiry policy, and a cache population job outside this spec's scope); pinning an exact fallback version (rejected by clarification 2); skipping the digest of the script (rejected: executes downloaded code on the work job).
- **Residual risk**: Whether `ci.dot.net/public` serves the band at run time cannot be proven offline, and neither can its independence from the origin `setup-dotnet`'s own install script consults: if the origins overlap, the fallback adds no resilience against a primary-origin outage (HTTP 409). The offline test only proves that no primary-origin URL is passed; independence is checked manually (quickstart step 4). If it does not, failure stays visible (User Story 3) and the implementation records the check as a quickstart manual step. The unresolved risk is explicit in the action README rather than assumed away.

## R4: Limits (FR-008)

- **Decision**: Primary: 3 attempts × 3 min, pauses 10 s and 30 s. Runner toolchain check: seconds. Alternative feed: 1 attempt, `timeout 240`. The values live as named constants in `dotnet-resolve.mjs` (alternative feed) and as step values in `action.yml` (primary attempts), and the README lists them.
- **Rationale**: A persistent fast-failing response (HTTP 409) ends in about 1 minute plus the fallback; the absolute worst case with every step hanging is 3 x 3 min + 10 s + 30 s + 240 s = about 13.7 minutes plus helper overhead, about 14 minutes, in minutes rather than tens of minutes. The bound is a development value, not tied to a measured healthy install duration; lowering the attempt `timeout-minutes` to 2 is possible if installs complete well inside that on the runner. The attempt count and pauses are small enough not to extend a healthy run.
- **Alternatives considered**: Exponential backoff with more attempts (rejected: pushes the worst case past the bound); a single global deadline step (rejected: unrolled steps cannot share one).

## R5: Output, reporting, and failure

- **Decision**: The decision step keeps `id: dotnet` and sets the output `dotnet-version` to the resolved SDK version, so `CACHE_DOTNET_VERSION: ${{ steps.dotnet.outputs.dotnet-version }}` stays as it is. The helper appends a "`.NET SDK`" table to `$GITHUB_STEP_SUMMARY` (source, fallback used yes or no, attempts, resolved version, and each rejected or failed source with its cause) and logs the same lines. On total failure it exits non-zero with one block: every source tried, the cause of each, and one `Recommended action`. A later step never runs because the composite step failed.
- **Rationale**: Meets FR-005 to FR-007 and SC-005. The outcomes of the primary attempts reach the helper through `env` (`steps.dotnetN.outcome`, `steps.dotnetN.outputs.dotnet-version`), so no state files are needed. Messages contain no credentials; no source needs one.
- **Alternatives considered**: Emitting the summary from YAML (rejected: untestable).

## R6: Install path effects

- **Decision**: A fallback SDK installed by the script goes to `$RUNNER_TEMP/dotnet-fallback`; the helper appends it to `GITHUB_PATH` and sets `DOTNET_ROOT` through `GITHUB_ENV`, nothing else; the cross-check of R2 runs with that directory first on `PATH` and `DOTNET_ROOT` set in the child environment, because these effects only reach later steps, not the helper process. A runner SDK needs no change. `install-tools: "false"` is untouched because the decision step has no `if` (FR-010); later `dotnet tool install` for Kiota keeps using whichever `dotnet` is first on `PATH`.
- **Alternatives considered**: Installing into `~/.dotnet` (rejected: could shadow the runner SDK before acceptance).

## R7: Verification coverage

- **Decision**: Add `${{ github.action_path }}/../environment-setup/dotnet-resolve.test.mjs` to `ENVIRONMENT_TESTS` in `environment-verify/action.yml`. No check is removed, skipped, or relaxed (FR-012).
- **Rationale**: The existing list names `toolchain.test.mjs` the same way; without the entry the new offline tests never run in verification, which would leave FR-009 unproven in CI.
