# Research: Analyst Manager Headless Server Profile

## R1. A separate headless executable without Avalonia

- **Decision**: Add the console project `src/analysts/manager/SocAlytics.Analysts.Manager.Server` (assembly `socalytics-manager-server`) that references only `SocAlytics.Analysts.Manager.Core`. Its `Program` does what the tray `Program` does up to `host.Start()` (command detection, `SingleInstanceGuard`, `ManagerHost`, the local-control server, `SIGTERM` → safe exit) and then waits for the host's shutdown instead of starting Avalonia. It refuses to start on Windows and macOS (FR-001).
- **Rationale**: The architecture's headless profile is "the Core worker without Avalonia". A flag in the tray executable would still ship and load Avalonia assemblies and native dependencies a minimal server does not have. A separate executable lets an architecture test prove the absence (no Avalonia reference in the project or its assembly closure).
- **Alternatives considered**: `socalytics-manager --headless` (rejected: Avalonia stays in the process and the package); a second Generic Host per profile (rejected: one Core worker is the architecture's rule).

## R2. The CLI moves into Core

- **Decision**: Move `SocAlytics.Analysts.Manager/Cli/ManagerCli.cs` into `SocAlytics.Analysts.Manager.Core/Cli/` (namespace `SocAlytics.Analysts.Manager.Cli`, kept) and move the `System.CommandLine` package reference with it. Both executables call `ManagerCli.IsCommand` and `ManagerCli.RunAsync`; `AttachParentConsole` stays a Windows-only no-op elsewhere. The command set does not change.
- **Rationale**: The CLI has no Avalonia dependency (it uses `System.CommandLine`, local control, and registration types only); the headless executable must offer the identical commands (FR-002, SC-002), so both share one parser.
- **Alternatives considered**: Duplicating the parser (rejected: drift between profiles); referencing the tray project from the server (rejected: pulls in Avalonia).

## R3. The application profile inside the Core worker

- **Decision**: A Core enum `ApplicationProfile { Tray, HeadlessServer }` with API names `tray` and `headless-server`. Each executable registers its profile when it builds the host (`ManagerHost.CreateBuilder(args, ApplicationProfile.HeadlessServer)`); it is not configuration, so it cannot be changed by a settings file. The profile is used by pairing (claim), the lingering check, the account rule, the autostart registrar choice, and the status output.
- **Rationale**: The profile is a property of the executable a host operator installs, not a setting.

## R4. Lingering check

- **Decision**: At start in the headless profile, check whether `/var/lib/systemd/linger/<user name>` exists (the file `loginctl enable-linger` creates; readable without administrator rights). Missing → log a warning and write it to standard error at start, naming `sudo loginctl enable-linger <user>`; the CLI `status` output shows `lingering: off` with the same hint. The check never stops the Manager (FR-005). The root path is injectable for tests.
- **Rationale**: The file is systemd's documented lingering marker and needs no D-Bus session; `loginctl show-user` needs a running logind session API and fails in minimal containers.
- **Alternatives considered**: `loginctl show-user --property=Linger` (kept out; extra process and D-Bus dependency).

## R5. The systemd user unit through `autostart on|off`

- **Decision**: In the headless profile, the existing `autostart on|off` command installs or removes the user unit instead of the XDG desktop entry: `SystemdUserUnitRegistrar` (an `IAutostartRegistrar`) writes `$XDG_CONFIG_HOME/systemd/user/socalytics-analyst-manager.service` (default `~/.config/systemd/user/`) and runs `systemctl --user daemon-reload` and `systemctl --user enable` (or `disable` and removal). The unit: `Type=exec`, `ExecStart=<absolute path of the running executable>`, `Restart=on-failure`, `RestartSec=10s`, `KillSignal=SIGTERM`, `TimeoutStopSec=` the Manager's `Operating:DrainTimeout` plus 30 seconds, `WantedBy=default.target`. The unit text is generated by a pure function (like `AutostartEntryFormats.DesktopEntry`) and documented in the Manager README; `systemctl` runs through an injectable process runner.
- **Rationale**: The architecture says the enabled user unit replaces desktop autostart; reusing the `autostart` command keeps the command set identical across profiles (FR-002, FR-004). `SIGTERM` already maps to the safe exit in the tray `Program`; the stop timeout leaves the drain room before systemd kills the process.
- **Alternatives considered**: Only documenting a unit file to copy by hand (rejected: error-prone path to the executable); a system-wide unit (rejected by the architecture).

## R6. Account rule

- **Decision**: `RuntimeProbe` gains `DaemonAccess` (`rootless`, `rootful-group`, or `null` when the adapter cannot tell). In the headless profile, `PreflightRunner` adds the check `account-isolation`: it fails when `DaemonAccess` is `rootful-group` and the account's login shell is not a no-login shell, with the detail "a rootful container runtime reached through group membership requires a dedicated non-login service account" and a remediation that names the README section. A failed check makes preflight fail, which already turns the operating state into runtime-unavailable with the reason (FR-016, clarification). The login shell comes from `getpwuid_r` through P/Invoke on Linux; no-login shells are `/usr/sbin/nologin`, `/sbin/nologin`, `/bin/false`, and `/usr/bin/false`. The simulated adapter gains `Runtime:Simulated:DaemonAccess` to exercise the rule; the Docker Desktop adapter of the in-progress spec reports `null` (Docker Desktop runs in a VM, not through the `docker` group).
- **Rationale**: Preflight is where runtime facts become "runtime unavailable", so the rule reuses the existing state, status report, and fleet display without new states.
- **Alternatives considered**: Reading `/etc/passwd` directly (kept as the fallback when `getpwuid_r` fails); checking group membership of `docker` (rejected: the adapter knows how it reaches the daemon; group membership alone does not imply a rootful daemon).

## R7. The claimed profile on the wire and in storage

- **Decision**: `deviceMetadata` in the v1 pairing request gains the optional field `claimedApplicationProfile` (`tray` | `headless-server`). The Managers of this feature always send it. The platform validates it (unknown values and `headless-server` with `os` other than `linux` are refused with a validation reason) and stores it inside the existing `device_metadata` jsonb column; no migration is needed. An absent claim (a Manager built before this feature) is recorded as not reported, shown as "not reported", and treated like `tray` for the software-key policy. Registration list, detail, fleet, and the Registrar's request views return the field when present.
- **Rationale**: `contracts-and-compatibility.md` makes a newly required input a breaking change that needs a v2 identity; an optional field keeps v1 additive while every current Manager sends it. Treating an absent claim like `tray` keeps the stricter key rule for unknown Managers. This keeps FR-008 as clarified: Managers of this feature always send the claim, and the platform accepts its absence from older Managers.
- **Alternatives considered**: A required field in v1 (rejected: breaking); a `registry/v2` pairing contract (rejected: disproportionate for one additive field); a new column (rejected: the claim belongs with the other claimed device metadata).

## R8. The software key policy replaces `AllowSoftwareKeys`

- **Decision**: `RegistryOptions.AllowSoftwareKeys` (bool) becomes `RegistryOptions.SoftwareKeys` with the values `Refused` (default), `HeadlessServerOnly`, and `All` (configuration `Registry:SoftwareKeys`). Start-up validation refuses `All` outside the Development and Test environments (FR-015). `StartPairing` refuses a software-backed claim unless the policy allows it for the claimed profile (an absent profile counts as `tray`) and audits the refusal with the claimed profile and protection (FR-013, FR-018). Stamp discovery keeps `softwareKeysAllowed` (true only for `All`, its old meaning for Managers that know no profiles) and adds `softwareKeysAllowedFor`, the list of profiles for which software keys are accepted (FR-014). The AppHost and the test hosts move from `AllowSoftwareKeys=true` to `SoftwareKeys=All`.
- **Rationale**: Three values match the architecture exactly and make the production restriction checkable at start.
- **Alternatives considered**: A second boolean `AllowSoftwareKeysForHeadlessServers` (rejected: two flags allow the meaningless combination and hide the precedence).

## R9. The Manager's pre-pairing refusal

- **Decision**: Before it requests a pairing code, the Manager reads `softwareKeysAllowedFor` from stamp discovery (falling back to `softwareKeysAllowed` when the field is absent) and passes "software keys allowed for my profile" to `IDeviceKeyProvider.CreateKeyAsync`, which already refuses the software fallback when it is false. The refusal reason names hardware-backed key storage and, in the headless profile, the stamp's headless-only setting (FR-014).
- **Rationale**: It reuses the existing decision point and avoids creating a pairing request that the platform would refuse.

## R10. Web UI

- **Decision**: The Registrar's request views (`PairingPage.tsx`, `MyRequestPage.tsx`), the Club Admin decision view (`RegistrationPage.tsx`), and the fleet (`FleetPage.tsx`) show "Profile (claimed)" next to "Key protection (claimed)", with `Headless server`, `Tray`, or `Not reported`; the existing claimed-value warning covers both. The Kiota client is regenerated from the updated OpenAPI snapshot.
- **Rationale**: FR-010; the views already render the claimed key protection with the warning, so the profile joins the same group.

## R11. Verification and tooling

- **Decision**: Automated tests run on the existing Linux CI: Manager unit tests for the server `Program` (no Avalonia in the closure; refusal on Windows and macOS through an injectable OS check), the lingering check, the unit text and registrar with a fake process runner, the account rule with the simulated adapter and an injectable account lookup, and the claimed profile in pairing; the golden fixtures gain the profile; platform Integration tests for the policy, validation, discovery, audit, and read responses; Host tests for start-up validation and the OpenAPI snapshot; Web UI unit and simulated Playwright tests for the views. The real systemd behavior on Ubuntu Server 22.04 and 24.04 LTS (boot without a session, lingering, restart, stop) is a manual validation in [quickstart.md](quickstart.md) that a person performs after the merge; the documentation task describes it and records it as open evidence, not as passed.
- **Rationale**: The CI runners have no systemd user session; the boot behavior can only be shown on a real host. No new SDK, framework, or tool is needed: .NET 10, SoftHSM2, Kiota, Playwright, and Docker are already provided by the environment actions, so no environment feature is needed.
