# Feature Specification: Analyst Evaluation Harness

**Feature Branch**: `20261023-082736-analyst-evaluation-harness`

**Created**: 2026-10-23

**Status**: Draft

**Input**: User description: "Maintainers and Analyst authors get a repeatable, deterministic way to evaluate one Analyst
capability against a labelled test set and a declared trivial or rules-only comparator, so that a baseline can only be
called promotable on recorded evidence instead of by assertion. A Python evaluation harness in a new project under
`src/analysts/` reads a corpus manifest (clip identifiers, content digests, source profile `fixed` or `broadcast`, and
labelled expectations, with the rights and provenance fields the catalog requires), runs a capability's Analyst entry
point through the Analyst SDK on each clip, compares the written facts with the labels, and writes a versioned,
content-addressed evaluation report (per-profile metrics, comparator result, repeat-run determinism check, OCI image
digest and capability version lineage). The first corpus is a small synthetic, rights-free fixture set generated by the
repository's own scripts, and the first evaluated capability is the implemented `reference-media-probe` (and the
shot-boundary baseline once it exists)."

## Clarifications

### Session 2026-10-23

- Q: How should the harness execute the capability under evaluation, and how does an author name it on the command
  line? → A: Both: a capability reference is either an image digest reference (container run) or a local command
  (subprocess run), and the report records which mode was used.
- Q: How is the comparator declared and executed: as a built-in rule inside the harness, or as another capability run
  through the same Analyst interface? → A: Both: built-in named trivial rules and, additionally, any capability
  reference run through the Analyst interface.
- Q: Which metrics does the report compute per source profile, and what exactly does 'the capability beat the
  comparator' mean? → A: Precision, recall, and F1 per label kind; 'beat' means strictly higher on a primary metric
  that the evaluation configuration names for each label kind.
- Q: How do failed clips affect the per-profile metrics, given that a failed clip 'must not count as agreement'? → A: A
  failed clip's labels count as misses in the metrics, and the comparison gate for that profile is also not evidenced
  while any clip failed.
- Q: Where does a capability declare the tolerance for the determinism check, and what applies when it declares none?
  → A: In the evaluation configuration, per label kind or fact kind; with no declaration the facts must be
  byte-identical.
- Q: How should the report state precision, recall, and F1 when a ratio has no denominator, for example precision for a
  trivial comparator that predicts nothing, or recall for a profile and label kind with no labels? → A: Record the
  value as undefined (null with a stated reason); an undefined primary metric is never 'strictly higher', so it cannot
  beat or be beaten, and the comparison gate for that profile and label kind is not evidenced.
- Q: When the capability is executed several times for the determinism check, which run's facts are compared with the
  labels to compute the metrics? → A: The first run only; the repetitions only feed the determinism check.
- Q: When does a written fact count as matching a label, in particular how close in match time must it be and must its
  payload be compared? → A: Same fact kind and a position within a tolerance that the evaluation configuration
  declares per label kind (default zero); the payload is compared only when the label carries a payload expectation.
- Q: May the harness pull a container image from a registry when the capability reference is an image digest reference
  that is not present locally? → A: No; the image must already be in the local container engine, and a missing image is
  a refused configuration.
- Q: Which process exit result should the command line return when the evaluation ran on every clip without a failed
  clip, but a gate is failed or not evidenced (for example no comparator was declared, or the determinism check
  failed)? → A: Success: the exit result reports only whether the evaluation ran, and the gate statuses are read from
  the report.
- Q: When a profile has several label kinds, does the capability beat the comparator on that profile only if it is
  strictly higher on the primary metric of every label kind, or is the verdict reported per label kind? → A: Report
  the verdict per profile and label kind; the profile-level verdict is 'beat' only when every label kind with a
  defined primary metric is strictly higher, 'did not beat' when any is not higher, and 'not evidenced' when any is
  undefined or incomplete.
- Q: How are facts paired with labels when several facts fall within the tolerance of one label, or one fact falls
  within the tolerance of several labels? → A: One-to-one pairing: each fact matches at most one label and each label
  at most one fact (closest position first, ties broken by order); a surplus fact is a false positive and a surplus
  label a miss.
- Q: How does a label that carries a position range, rather than a single match-second, match a written fact? → A: The
  fact's position must lie inside the label's range widened by the declared tolerance on both ends.
- Q: When the first run of a clip succeeds but a determinism repetition fails (non-zero exit, invalid result, or
  time-limit overrun), how is that recorded and which exit result does the command line return? → A: The clip stays
  evaluated for the metrics, the determinism check is recorded as failed and names the clip and the failure category,
  and the exit result is success (the evaluation ran on every clip).
- Q: Which built-in named trivial comparator rules must the harness provide in this feature? → A: Exactly two:
  'predict-nothing' (writes no facts) and 'predict-everything' (writes one fact of every label kind at every covered
  match-second).

## User Scenarios & Testing *(mandatory)*

The users are platform maintainers, who need the Wave 0 metrics harness of the
[Analyst Capability Catalog](../../../docs/architecture/analyst-capability-catalog.md#implementation-waves) to exist as an
executable, repeatable tool; and Analyst authors, who need to evaluate a capability against labels and a declared
comparator before anyone calls it a promotable baseline. No platform member, Club Admin, or Coach uses the harness, and
it changes no platform behavior.

### User Story 1 - Evaluate a capability on a labelled corpus and get a report (Priority: P1)

An Analyst author points the harness at a corpus manifest and at one capability reference: either an image digest
reference (a container run) or a local command (a subprocess run), together with the capability version it is evaluated
as. The harness validates the manifest, executes the capability on every clip through the Analyst SDK's job and
attempt-context interface exactly as a Manager would stage it, reads the facts the capability wrote, compares them with
each clip's labelled expectations, and writes an evaluation report. The report states per-profile metrics (precision,
recall, and F1 per label kind; `fixed` and `broadcast` separately, never one aggregate score), the execution mode used
(container or subprocess), the capability version and image digest that were evaluated, and the corpus identity.

**Why this priority**: It is the feature's purpose; without a recorded, per-profile measurement nothing can be promoted
on evidence. Every other story refines or relies on this report.

**Independent Test**: Generate the synthetic corpus, run the harness on `reference-media-probe`, and read the report: it
lists one result per clip, per-profile metrics for both profiles, and the lineage fields, and it can be verified by
recomputing the metrics by hand from the labels and the written facts.

**Acceptance Scenarios**:

1. **Given** a valid corpus manifest with clips of both source profiles, **When** an author evaluates a capability,
   **Then** the report contains metrics for `fixed` and `broadcast` computed separately, and no combined score.
2. **Given** a clip whose written facts exactly match its labels, **When** it is evaluated, **Then** its result records
   full agreement; **Given** a clip with a missing, extra, or misplaced fact, **Then** the result records each
   discrepancy against the label that it violates.
3. **Given** a capability that fails on a clip (a non-zero exit or an invalid result), **When** the corpus is
   evaluated, **Then** the clip is recorded as failed with the failure category the SDK reports, the other clips are
   still evaluated, the report does not count the failed clip as agreement, its labels count as misses in the
   profile's metrics, and the comparison gate for that profile is not evidenced.

---

### User Story 2 - Compare against a declared trivial or rules-only comparator (Priority: P1)

A baseline is only meaningful relative to something simpler. The evaluation names a comparator declared in the
evaluation configuration before the run: either a built-in named trivial rule (for example, one that predicts nothing or
a constant) or any capability reference (a rules-only implementation) run through the Analyst interface. The harness
evaluates the comparator on the same clips with the same labels and metrics, and the report states for each source
profile whether the capability beat the comparator (the verdict is reported per profile and label kind, strictly higher on the primary metric
that the evaluation configuration names for each label kind; the profile-level verdict is `not evidenced` if any label kind is not evidenced, any clip of the profile failed, or no comparator is declared; otherwise `did not beat` if any label kind is not strictly higher; otherwise `beat`) and by how much.

**Why this priority**: "Beat its declared trivial or rules-only comparator" is a validation gate of the catalog; the
gate cannot be evidenced without it. It is equal in priority to Story 1 because a report without the comparison cannot
support a promotion claim.

**Independent Test**: Evaluate a capability and a deliberately weaker comparator and a deliberately stronger comparator
on the synthetic corpus; the report says "beat" for the first and "did not beat" for the second, on each profile
independently.

**Acceptance Scenarios**:

1. **Given** an evaluation that declares no comparator for a capability, **When** it runs, **Then** the report records
   the comparator as `not declared` and the comparison gate as not evidenced, never as passed.
2. **Given** a comparator the capability does not beat on the `broadcast` profile but beats on `fixed`, **When** the
   report is written, **Then** the two profile verdicts differ and neither is hidden by the other.
3. **Given** a comparator that cannot be run on a clip, **When** the evaluation runs, **Then** the comparator result is
   recorded as incomplete and the comparison gate is not evidenced.
4. **Given** a comparator declared as a built-in named trivial rule, and another declared as a capability reference,
   **When** each is evaluated, **Then** both are scored with the same clips, labels, and metrics, and the report
   records which kind of comparator was used.
5. **Given** a profile on which any clip failed (for the capability or the comparator), **When** the report is
   written, **Then** the comparison gate for that profile is not evidenced even if the metrics favor the capability.

---

### User Story 3 - Determinism check and content-addressed lineage (Priority: P2)

The harness repeats the capability's execution on every clip a declared number of times, in fresh isolated working
directories, and reports whether the written facts are byte-identical, or, where the capability declares a tolerance,
within the tolerance that the evaluation configuration declares per label kind or fact kind (with no declaration, the
facts must be byte-identical). The report is content-addressed: its identity is derived from its content, so the same
corpus, capability, image digest, comparator, and configuration yield a report that is byte-identical across runs and
machines apart from clearly separated, non-identity fields (such as run time). The report records the corpus identity,
the capability id and version, the OCI image digest it was evaluated as, the SDK version, and the toolchain versions.

**Why this priority**: Determinism and lineage are two further gate criteria, but a first report is already useful
without them, so they follow the core measurement and comparison.

**Independent Test**: Run the same evaluation twice and compare the two reports: they have the same identity and
identical content outside the declared non-identity fields; then run a capability fixture that writes a different fact
on its second run and see the determinism check fail for exactly that clip.

**Acceptance Scenarios**:

1. **Given** a deterministic capability, **When** the harness repeats its execution, **Then** the report records the
   determinism check as passed with the number of repetitions.
2. **Given** a capability whose repeated runs differ beyond the tolerance declared in the evaluation configuration (or
   differ at all when none is declared for that kind), **When** the check runs, **Then** the report names the clips and facts that differ and records the check as
   failed.
3. **Given** a report, **When** its content is changed by one byte, **Then** the verification of its identity fails.
4. **Given** an evaluation without a resolvable OCI image digest (for example, a local command run), **When** the
   report is written, **Then** the digest is recorded as `not evaluated as an image` and the lineage gate is recorded as
   not evidenced.

---

### User Story 4 - A rights-free synthetic corpus the repository generates itself (Priority: P2)

A maintainer runs the repository's own generation script and obtains a small corpus: synthetic clips for both source
profiles together with their manifest, whose digests match the generated clips, whose labels are known by construction,
and whose rights and provenance fields state that the content is synthetic and free of third-party rights. The same
script run twice produces the same corpus manifest identity.

**Why this priority**: The harness needs a first corpus to be demonstrable, and the corpus is the least valuable part:
real corpora are out of scope. It is P2 because the harness's behavior is defined against any valid manifest.

**Independent Test**: Run the generation script twice into two empty directories and compare the manifests and clip
digests; then validate the manifest with the harness.

**Acceptance Scenarios**:

1. **Given** an empty directory, **When** the generation script runs, **Then** it writes the clips and a manifest that
   the harness accepts and whose every clip digest matches the clip content.
2. **Given** a clip changed after generation, **When** the manifest is validated, **Then** the harness refuses to
   evaluate it and names the clip whose digest does not match.

---

### User Story 5 - Evaluate the shot-boundary baseline when it exists (Priority: P3)

When the Shot-Boundary Media Context Analyst has been implemented, the same harness evaluates it on a corpus whose
labels are shot-boundary positions, without a change to the harness itself, only by adding a label kind and a matching
rule for it.

**Why this priority**: It is an optional later subject. This feature depends on no unimplemented spec, and its first
evidence is the reference capability.

**Independent Test**: Not part of this feature's acceptance; the harness's extension point for a new label kind and its
matching rule is tested with a test-only capability.

**Acceptance Scenarios**:

1. **Given** a new label kind with a declared matching rule, **When** a corpus uses it, **Then** the harness compares
   facts of that kind with those labels and reports the same per-profile metrics.

---

### Edge Cases

- A corpus manifest without one of the required rights or provenance fields, with an unknown source profile, with
  duplicate clip identifiers, or with a clip whose digest is not a content digest is refused before any clip is run,
  with every problem listed.
- A corpus with clips of only one source profile is evaluated, but the report states the missing profile as not
  evidenced rather than passed.
- A clip with no labelled expectations (all expected facts absent) is valid and measures false positives.
- A clip file that is missing or unreadable is a validation failure of the corpus, not a capability failure.
- A capability that writes facts of a kind the labels do not cover has them recorded as unlabelled, not as errors.
- Several facts within the tolerance of one label, or one fact within the tolerance of several labels, are paired
  one-to-one (closest position first, ties broken by order); the surplus fact is a false positive and the surplus
  label a miss.
- A determinism repetition that fails (non-zero exit, invalid result, or time-limit overrun) after a successful first
  run leaves the clip evaluated for the metrics and fails the determinism check, naming the clip and the failure
  category; the command line still exits with success.
- A capability that hangs is bounded by a declared per-clip time limit; the clip is recorded as failed.
- Different Analyst entry points need not be in the same Python environment as the harness; the harness invokes them
  as a container run from an image digest reference or as a subprocess run of a local command through the SDK's
  interface, and does not require importing the capability.
- A failed clip contributes its labels as misses (false negatives) to the profile's metrics and contributes no
  predicted facts; it never raises precision or recall, and the profile's comparison gate is not evidenced.
- A capability reference that is neither a valid image digest reference nor a runnable local command is a refused
  configuration, not a failed clip.
- Production quality thresholds are unresolved: the report states metrics and comparator outcomes, and any threshold
  verdict appears only when a threshold is supplied in the configuration and is labelled as an evaluation-local
  threshold, never as a promotion decision.
- The harness never reads real match footage, network resources, or model weights, and never writes outside its output
  directory.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The harness MUST read a corpus manifest that identifies every clip by an identifier, a content digest, and
  a source profile of exactly `fixed` or `broadcast`, and that carries per-clip labelled expectations.
- **FR-002**: The corpus manifest MUST carry, for the corpus and for each clip, the rights and provenance fields that
  the catalog requires (origin, license or rights statement, and how the clip and its labels were produced), and the
  harness MUST refuse a manifest where any of them is missing.
- **FR-003**: The harness MUST verify every clip's content digest before evaluation and MUST refuse to evaluate a
  corpus with a mismatching or missing clip, listing every problem at once.
- **FR-004**: The harness MUST run the capability's Analyst entry point on each clip through the Analyst SDK's job and
  attempt-context interface, with the clip staged the way a Manager stages segment media, and MUST NOT require a
  platform, Manager, registry, or network. A capability reference MUST be either an image digest reference (executed
  as a container run) or a local command (executed as a subprocess run), and the report MUST record which execution
  mode was used. The harness MUST NOT pull an image from a registry: an image digest reference whose image is not
  present in the local container engine is a refused configuration.
- **FR-005**: The harness MUST read the facts the capability wrote and compare them with the clip's labelled
  expectations by a declared, per-label-kind matching rule, recording every agreement and every discrepancy. A fact
  matches a label when it has the same fact kind and a position within the tolerance that the evaluation configuration
  declares per label kind (default zero); for a label with a position range, the fact's position must lie inside the
  range widened by the tolerance on both ends; the payload is compared only when the label carries a payload
  expectation. Pairing is one-to-one: each fact matches at most one label and each label at most one fact (closest
  position first, ties broken by order); a surplus fact is a false positive and a surplus label a miss. The metrics
  are computed from the facts of the first run only; the repetitions only feed the determinism check (FR-009).
- **FR-006**: The harness MUST compute precision, recall, and F1 per label kind for each source profile and MUST NOT
  produce an aggregate score across profiles. A ratio without a denominator (for example precision of a comparator that
  predicts nothing, or recall for a profile and label kind without labels) MUST be recorded as undefined (null with a
  stated reason), never as zero or one.
- **FR-007**: The harness MUST support a declared comparator evaluated on the same clips, labels, and metrics, and the
  report MUST state per profile whether the capability beat the comparator. A comparator is either a built-in named
  trivial rule or any capability reference run through the Analyst interface (FR-004), and the report MUST record which
  kind was used. The built-in named trivial rules are exactly two: `predict-nothing` (writes no facts) and
  `predict-everything` (writes one fact of every label kind at every covered match-second). The report MUST state the
  verdict per profile and label kind: the capability is strictly higher or not on the primary metric that the
  evaluation configuration names for that label kind; a label kind without a named primary metric makes the
  configuration refused. An undefined primary metric is never strictly higher, so it can neither beat nor be beaten,
  and the verdict for that profile and label kind is not evidenced. The profile-level verdict is `not evidenced` if any
  label kind is not evidenced, any clip of the profile failed (for the capability or the comparator), or no comparator
  is declared; otherwise it is `did not beat` if any label kind is not higher, and otherwise `beat`. The kind-level
  verdict is `beat` when the primary metric of the label kind is defined for both and the capability is strictly
  higher.
- **FR-008**: The report MUST record the comparison gate as not evidenced when no comparator is declared, the
  comparator result is incomplete, or any clip of that profile failed (for the capability or the comparator), and MUST
  never present such a state as passed.
- **FR-009**: The harness MUST repeat the capability's execution a declared number of times on every clip in isolated
  working directories and report byte-identity, or equality within a tolerance the evaluation configuration declares
  per label kind or fact kind, with the differing clips and facts named on failure. Where no tolerance is declared for
  a kind, its facts MUST be byte-identical. When the first run of a clip succeeds but a repetition fails (non-zero
  exit, invalid result, or time-limit overrun), the clip stays evaluated for the metrics, and the determinism check is
  recorded as failed naming the clip and the failure category.
- **FR-010**: The report MUST be versioned (a report schema version) and content-addressed: its identity is derived
  from its content excluding the declared non-identity fields, and an identity check MUST detect any change.
- **FR-011**: The report MUST record the lineage of the evaluation: corpus identity, capability id and version, OCI
  image digest (or an explicit statement that the capability was not evaluated as an image), execution mode,
  comparator identity and kind, SDK version, toolchain versions, and the evaluation configuration.
- **FR-012**: A clip on which the capability or the comparator fails MUST be recorded as failed with the SDK's failure
  category, MUST NOT stop the evaluation of the other clips, MUST NOT count as agreement, and MUST count its labels as
  misses in the profile's metrics.
- **FR-013**: The harness MUST bound each execution by a declared time limit and record an overrun as a failure.
- **FR-014**: The harness MUST evidence a gate as passed only on recorded results; every gate that it cannot evidence
  (missing profile, comparator, determinism repetitions, or image digest) MUST be reported as not evidenced.
- **FR-015**: The harness MUST NOT decide promotion, MUST NOT carry production quality thresholds, and MAY apply a
  threshold only when it is supplied in the configuration, labelling its verdict as evaluation-local.
- **FR-016**: The repository MUST provide a generation script that produces the synthetic, rights-free corpus (clips
  of both profiles, manifest, and labels known by construction) deterministically, so that two runs yield the same
  manifest identity and clip digests.
- **FR-017**: The harness MUST evaluate the implemented `reference-media-probe` against the generated corpus with a
  declared comparator, as the first end-to-end proof, with labels the capability's documented facts can be checked
  against.
- **FR-018**: New label kinds and their matching rules MUST be addable without changing the report schema's per-profile
  structure, so that the shot-boundary baseline can later be evaluated.
- **FR-019**: The harness MUST be runnable from the command line with a corpus manifest, a capability reference, an
  evaluation configuration, and an output directory, and MUST exit with distinct results for a successful evaluation,
  a refused manifest or configuration, and an evaluation that ran with failed clips. An evaluation that ran on every
  clip without a failed clip MUST exit with success even when a gate is failed or not evidenced (for example no
  comparator was declared, or the determinism check failed, including a failed repetition of an otherwise evaluated
  clip); the exit result reports only whether the evaluation ran,
  and the gate statuses are read from the report.
- **FR-020**: The harness MUST use the existing Python 3.12 and `uv` tooling and the pinned FFmpeg and ffprobe of the
  Analyst and media verification environment, and MUST add no new framework or SDK.
- **FR-021**: The feature MUST NOT change the platform API, Web UI, registry, Manager, or any contract that they use,
  and MUST NOT publish a package or an image.

### Key Entities

- **Corpus manifest**: Identifier, version, rights and provenance statement, and the list of clips; its identity is
  content-derived.
- **Clip**: Identifier, content digest, source profile (`fixed` or `broadcast`), its own rights and provenance, and its
  labelled expectations.
- **Label**: An expected fact of a kind, with its expected match-time position or range (a fact matches a range label
  when its position lies inside the range widened by the tolerance on both ends) and optional payload expectation; its
  matching rule is declared by its kind.
- **Capability subject**: Capability id, version, capability reference (an image digest reference or a local command),
  the execution mode (container or subprocess), and the OCI image digest it is evaluated as, when evaluated as an
  image.
- **Comparator**: A declared built-in named trivial rule (exactly `predict-nothing` and `predict-everything`), or a
  capability reference run through the Analyst interface, evaluated with the same inputs and metrics.
- **Evaluation configuration**: Repetition count, time limit, the primary metric per label kind, the matching
  tolerance per label kind (default zero), the determinism
  tolerance per label kind or fact kind (none means byte-identical), optional evaluation-local thresholds, and the
  comparator declaration.
- **Evaluation report**: Versioned, content-addressed record of per-clip results, per-profile metrics, comparator
  result, determinism check, gate statuses (passed, failed, not evidenced), and lineage.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An author evaluates `reference-media-probe` on the generated corpus with one command and obtains a report
  in under 10 minutes on a standard development machine.
- **SC-002**: Two evaluations of the same corpus, capability, comparator, and configuration yield reports with the
  same identity, and a changed byte in either report is detected in 100% of tested cases.
- **SC-003**: For a corpus with known planted discrepancies, 100% of them are reported, each against the label it
  violates, and none is reported for clips that agree.
- **SC-004**: 100% of gates for which the evidence is missing (no comparator, one profile only, no repetition, no image
  digest) are reported as not evidenced, and none as passed.
- **SC-005**: The harness's verdicts on the comparison gate differ by profile in a test with a comparator that is
  better on one profile and worse on the other.
- **SC-006**: Two runs of the corpus generation script produce identical clip digests and manifest identity.
- **SC-007**: A reviewer can trace each reported metric to the clips, labels, and written facts that produced it
  without running the capability again.

## Assumptions

- The harness is development and maintainer tooling: it is not a catalog capability, never runs in a production
  workflow, and gives no deployment or production-readiness evidence.
- The harness executes the capability by the SDK's Analyst container interface (job, attempt context, staged inputs,
  result writing, and entry point), in a local working directory or a container the author supplies; a Docker-backed
  run supplies the OCI image digest, a local run records it as not evaluated as an image.
- The report's schema is a machine-readable contract owned by the harness project; it is not a platform contract and is
  not added to the platform's `contracts/` folder unless the plan finds that a shared contract is required.
- The synthetic corpus is small (a handful of short clips per profile); the `fixed` and `broadcast` profiles are
  synthesized as stand-ins and make no claim about the visual properties of real footage.
- The reference capability's labels are the facts its documentation defines (a fact per covered match-second with a
  decoded frame count), so the first evaluation proves the harness, not the capability's quality.
- The harness carries no real quality thresholds, model weights, accelerator measurement, CPU or throughput budgets,
  or promotion decisions; those stay `Provisional` or unresolved as the catalog states.
- The harness lives in a new executable project under `src/analysts/` next to the SDK and capabilities; its exact
  location and name are decided in the plan, and the `src/analysts/` first-level boundary is unchanged.
- Depends on the implemented Python Analyst SDK and Reference Analyst specs; it names the Shot-Boundary Media Context
  Analyst as an optional later subject and depends on no unimplemented spec.
