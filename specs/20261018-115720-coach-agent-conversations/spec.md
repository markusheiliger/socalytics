# Feature Specification: Coach Agent Direct Conversations

**Feature Branch**: `20261018-115720-coach-agent-conversations`

**Created**: 2026-10-18

**Status**: Draft

**Input**: User description: "Coach Agent Direct Conversations: the architecture defines Coach Agents as disclosed AI simulations inspired by a named coach's documented public philosophy that apply that perspective when prioritizing SocAlytics facts without impersonating the person, fabricating quotations or private knowledge, or implying endorsement; every CA profile contains integer weights for every dimension of its dimension-set version that total 100; context modifiers are bounded, evidence-backed, and budget-neutral and never change evidence or confidence; Hermes renders the complete base vector, modifier policy, and any evidence-backed applied modifiers into the system-prompt context (supplying only a profile id is insufficient) and fails on an invalid or incompatible profile; advice lineage retains the applied modifiers; direct `User -> CA` requests are a supported route; Wave 3 introduces direct Coach Agents (docs/architecture/terminology-and-principles.md Coach Agent, philosophy dimension set, base and applied philosophy profiles; docs/architecture/intelligence-agent-catalog.md Coach Agent Catalog, Coach Philosophy Weighting, Dimension Set, Base Philosophy Profiles, Context Modifiers, Adding Or Revising A Coach Agent, Rendered CA Prompt Context, the first-draft CA prompts, Implementation Waves, Validation And Promotion Gates; docs/architecture/intelligence-and-agents.md direct invocations and Hermes profile rendering). This feature enables direct conversations with Coach Agents end to end: the platform accepts enabling approved Coach Agent versions (spec 4's records) and offers them as triage participants alongside Specialists, the direct `User -> CA` route is accepted by Agent Orchestration, Hermes validates and renders the pinned dimension set, base profile, and modifier policy into the Coach Agent's system context exactly as the catalog's Rendered CA Prompt Context defines, applies only evidence-backed, budget-neutral context modifiers derived from accepted evidence obtained through MCP within the policy's bounds, records the applied philosophy profile and modifiers in lineage, and every Coach Agent response carries the required simulation disclosure; the Web UI shows Coach participants with their disclosure and, where the platform returns it, the applied emphasis. A Development and Test seed registers the catalog's first-draft Coach Agents (dimension set, base profiles, modifier policies, prompts) as validated records. Evaluation suites (factual consistency across personas, disclosure, non-impersonation, differentiation) stay required production promotion evidence and are not claimed; automated tests use Hermes' scripted provider to prove rendering, validation failures, modifier bounds, disclosure, and lineage. Out of scope: CA→SA consultations (spec 10), CA→CA interactions (rejected by the architecture), new dimensions or profile changes, evaluation suites and promotion, real provider calls in tests, production values. Depends on `specs/20261018-113729-hermes-runtime`, `specs/archive/20261018-101517-agent-catalog-registry`, `specs/archive/20261018-103316-web-ui-agent-catalog`, `specs/20261018-104924-agent-evidence-tools`, `specs/archive/20261017-204332-agent-orchestration-invocations` (#155), `specs/archive/20261017-210231-web-ui-triage-conversations` (#156). Implements the Coach Agent parts of the sections named above (Wave 3 functionality without its evaluation gates)."

## Clarifications

### Session 2026-10-18

- Q: How does a Coach Agent attempt arrive at the context modifiers it applies, given that the modifier policy declares only bounds and permitted categories, not rules? → A: After consulting evidence, the model may propose one set of modifiers through a Hermes-local proposal function that is not an MCP tool; Hermes validates it against the pinned policy and the attempt's answered tool calls and, when valid, renders the profile block again before the final answer.
- Q: How is the rendered profile and modifier snapshot retained for attempts that fail or expire, as the architecture requires for every successful or failed attempt? → A: Hermes records each rendered snapshot (the initial one and the one after applied modifiers) in a profile checkpoint that the platform validates and appends to the lineage; the completion repeats the attempt's last recorded snapshot.
- Q: How does every Coach Agent response carry the simulation disclosure? → A: The platform attaches the pinned agent version's disclosure statement to every Coach Agent advice in its reads; the advice text is not altered and is not required to contain it.
- Q: Does the Development and Test seed approve and enable the Coach Agents, and when does it apply? → A: It registers approved and enabled versions of all three Coach Agents, once, when the catalog holds no Coach Agent artifacts, independently of the specialist seed; otherwise it is skipped.
- Q: What does a context modifier's reason contain? → A: Plain text of at most 300 characters written by the model, kept only in the lineage and accepted advice and never in logs, audit events, or telemetry.
- Q: How do browser tests against the running platform prove Coach Agents, given that the platform's browser-test composition produces no completed analysis run to start a conversation from? → A: The running-platform browser test proves that the Agent Catalog area shows the seeded Coach Agents enabled and offered in conversations; the ask-and-answer flow is proven against the simulated API, and the platform's own tests prove it with the simulated agent workload; no test-only platform hook is added.

## User Scenarios & Testing *(mandatory)*

The actors are the Coach (or Club Admin) who owns a triage conversation and asks a Coach Agent for a whole-match perspective, the Club Admin who enables Coach Agent versions as catalog operator, and the Hermes agent runtime that executes the work. A Coach Agent is a disclosed AI simulation inspired by a named coach's documented public philosophy ([Architectural Principles](../../docs/architecture/terminology-and-principles.md)); its perspective changes the order of investigation, the priority of recommendations, and the framing of tradeoffs, never the facts, evidence availability, or confidence ([Coach Philosophy Weighting](../../docs/architecture/intelligence-agent-catalog.md#coach-philosophy-weighting)). Conversations, participants, submission, attempts, and lineage come from [Agent Orchestration Direct Invocations](../archive/20261017-204332-agent-orchestration-invocations/spec.md); Coach Agent versions and their dimension set, base philosophy profile, and context-modifier policy are registered, validated, approved, and pinned by the [Agent Catalog Registry](../archive/20261018-101517-agent-catalog-registry/spec.md), which left their enablement to this feature; the runtime is the [Hermes Agent Runtime](../20261018-113729-hermes-runtime/spec.md), which so far executes only direct Specialist Agent invocations; evidence comes only through the [MCP Server](../20261018-111804-mcp-server/spec.md) and the [Agent Evidence Tools API](../20261018-104924-agent-evidence-tools/spec.md); members use the [Web UI Match Triage Conversations](../archive/20261017-210231-web-ui-triage-conversations/spec.md) and Club Admins the [Web UI Agent Catalog Administration](../archive/20261018-103316-web-ui-agent-catalog/spec.md).

### User Story 1 - A Coach asks a Coach Agent for a whole-match perspective (Priority: P1)

A Club Admin enables an approved version of `coach-pep-guardiola`. A Coach of the team opens a triage conversation for an analysed match, adds the Coach Agent next to a specialist, and asks it why the team struggled to progress the ball. Hermes claims the invocation, validates the pinned dimension set, base philosophy profile, and context-modifier policy, renders the complete profile block into the Coach Agent's system context, consults evidence through the attempt's MCP session, and completes with advice that follows the shared response contract. The Coach reads the advice next to the simulation disclosure, and the lineage shows the pinned philosophy artifacts and the applied profile.

**Why this priority**: It delivers Wave 3's direct Coach Agent conversations end to end; every other story refines or hardens this path.

**Independent Test**: With the Development and Test seed, enable a Coach Agent version, create a conversation, add the Coach Agent, submit a question, and let Hermes execute it with the scripted provider (scripted to call `get_match` and answer); confirm that the invocation's route is `User -> CA`, that its pins include the agent version, prompt template, model selection, tool policy, safety policy, dimension set, base profile, and modifier policy, that the system context Hermes sent to the scripted provider contains the profile block with every element the catalog requires, and that the owner's reads show the advice with the simulation disclosure and the applied profile in the lineage.

**Acceptance Scenarios**:

1. **Given** an approved Coach Agent version whose model selection is permitted in the environment, **When** a Club Admin enables it with the enablement state they last saw, **Then** it becomes the agent's single enabled version, the change is audited, and the agents available for conversations include it with its group, display name, version, and simulation disclosure statement.
2. **Given** an enabled Coach Agent, **When** the owner of a conversation adds it as a participant and submits a question to it, **Then** the platform creates an invocation with the route `User -> CA` and pins the agent version, every artifact it references, and the dimension set its profile references, under the same rules as for Specialist Agents.
3. **Given** a claimed `User -> CA` attempt, **When** Hermes prepares it, **Then** it reads the pinned artifacts, validates the profile against its pinned dimension set and the prompt's and modifier policy's dimension-set major version, and renders into the system context the dimension-set identifier and version, the profile identifier, version, and digest, every dimension identifier with its base weight, the permitted context categories and modifier constraints, any applied modifiers with reasons and evidence references, the resulting applied vector, and the instruction that weights affect priority but never facts or confidence.
4. **Given** a rendered Coach Agent context, **When** the model works, **Then** it reaches evidence only through the attempt's MCP session and the pinned tool policy, exactly as for Specialist Agents, and no consultation of another agent is offered or executed.
5. **Given** a model answer, **When** Hermes completes the attempt, **Then** the advice contains the five response-contract sections in order and the completion declares the execution references and the applied philosophy profile, which the platform checks against the pins before accepting the advice.
6. **Given** a succeeded Coach Agent invocation, **When** its owner reads the conversation turns, the invocation, or its lineage, **Then** the advice is attributed to the Coach Agent and shown with its simulation disclosure, and the lineage shows the dimension-set, profile, and modifier-policy references with digests, the base and applied vectors, and the applied modifiers.

### User Story 2 - Philosophy context adapts only to evidence, within bounds (Priority: P2)

The Coach Agent's emphasis may shift with the match context — for example the score state or the match period — but only when accepted evidence the attempt obtained through MCP shows that context, only within the pinned modifier policy's bounds, and never by inventing, hiding, or reweighting facts. Every applied modifier is recorded with its reason, evidence references, policy version, and before and after values; modifiers without complete evidence-backed lineage are omitted.

**Why this priority**: Context modifiers are the part of the profile most at risk of becoming unsupported persona behavior; bounding and recording them makes the Coach Agent's emphasis auditable. It builds on Story 1.

**Independent Test**: With the scripted provider, run Coach Agent attempts whose proposed modifiers are within bounds and reference answered tool calls of the attempt, exceed the per-dimension bound, exceed the total positive movement, do not sum to zero, make a weight negative, use a context category the policy does not permit, reference no evidence, reference an "analysis unavailable" answer, or reference a call of another attempt; confirm that only the first set is applied, rendered, and recorded, and that every other set is omitted without changing the base vector, the evidence, or the advice's facts.

**Acceptance Scenarios**:

1. **Given** a proposed set of modifiers whose context categories the pinned policy permits, whose integer deltas stay within its per-dimension bound and total positive movement, sum to zero, keep every applied weight non-negative and the total at 100, and whose every modifier references at least one tool call of the same attempt that answered from accepted evidence, **When** Hermes evaluates it, **Then** the modifiers are applied, the profile block is rendered again with them and the resulting applied vector, and the completion records them.
2. **Given** a proposed set that violates any of these rules, **When** Hermes evaluates it, **Then** no modifier of the set is applied, the base vector stays the applied vector, the attempt continues, and the omission is recorded without content.
3. **Given** a context that is unknown or whose evidence is unavailable, **When** the attempt runs, **Then** no modifier is applied and missing dimension evidence is treated as unavailable, never as zero, and causes no redistribution of weights.
4. **Given** a completion whose applied profile differs from the pinned base vector plus the declared modifiers, whose modifiers violate the pinned policy, or whose evidence references do not name answered tool calls of the same attempt, **When** the platform receives it, **Then** the completion is refused, nothing is recorded, and the attempt stays active.

### User Story 3 - Invalid or incompatible philosophy artifacts fail explicitly (Priority: P3)

If a pinned Coach Agent artifact is missing, does not match its digest, omits a dimension, violates the 100-point invariant, or is incompatible with the prompt's dimension-set major version — or the safety policy lacks the route or the disclosure rules — Hermes fails the attempt without calling a model or a tool and never falls back to another profile, a partial profile, or a Specialist Agent behavior.

**Why this priority**: The architecture forbids silent fallback for profiles; explicit failure keeps members from receiving advice of a perspective the catalog did not approve. It builds on Story 1.

**Independent Test**: With a fake platform serving corrupted pinned artifacts (each violation once) and the scripted provider, confirm each attempt fails as not retryable with the documented reason and zero model and tool calls; with an envelope carrying any route other than `User -> SA` or `User -> CA`, confirm the attempt fails as an unsupported route.

**Acceptance Scenarios**:

1. **Given** a pinned profile, dimension set, or modifier policy that is missing, does not match its pinned digest, or fails its contract, **When** Hermes prepares the attempt, **Then** it fails the attempt as not retryable with reason "invalid artifact".
2. **Given** a profile that omits or adds a dimension of its dimension set, whose weights are not integers in `[0,100]` or do not total 100, or whose dimension-set major version differs from the prompt's or the modifier policy's, or a modifier policy whose bounds exceed the architecture's limits, **When** Hermes prepares the attempt, **Then** it fails the attempt as not retryable with reason "incompatible artifact".
3. **Given** a Coach Agent safety policy that does not permit `User -> CA` or lacks the simulation-disclosure, non-impersonation, or non-fabrication rules, or a Coach Agent version without a disclosure statement, **When** Hermes prepares the attempt, **Then** it fails the attempt as not retryable with reason "incompatible artifact".
4. **Given** any route other than `User -> SA` and `User -> CA`, **When** Hermes receives such an attempt, **Then** it fails it as not retryable with reason "unsupported route".

### User Story 4 - Members and Club Admins see Coach Agents for what they are (Priority: P4)

In the Web UI, Coaches see Coach Agents among the agents they can add to a conversation, labelled as Coach Agents with their simulation disclosure, and every Coach Agent advice is shown with that disclosure; where the platform returns the applied philosophy profile, the Coach can inspect the emphasis the advice applied. In the Agent Catalog area, Club Admins enable Coach Agent versions like Specialist versions, without the earlier warning that Coach Agents are not available in conversations.

**Why this priority**: Disclosure in front of the member is what makes a persona-inspired agent acceptable; the platform behavior of Stories 1 to 3 must be visible to its users. It needs Story 1.

**Independent Test**: Against the simulated API, add a Coach Agent, ask it, and confirm the participant list, the advice, and the lineage show the Coach Agent label, the disclosure statement, and the applied emphasis; in the Agent Catalog area, enable an approved Coach Agent version and confirm the confirmation no longer warns of refusal and that the overview reports the Coach Agent as offered in conversations; against the running platform with the Development and Test seed, confirm that the Agent Catalog area shows the seeded Coach Agents enabled and offered in conversations.

**Acceptance Scenarios**:

1. **Given** enabled Coach Agents, **When** the owner opens the add-participant choice, **Then** Coach Agents are listed separately from Specialist Agents with their display name, identifier, and simulation disclosure statement.
2. **Given** a Coach Agent advice, **When** it is shown, **Then** its disclosure statement is shown with it, and the advice text is shown unaltered as text.
3. **Given** an advice for which the platform returns the applied philosophy profile, **When** the owner asks to see the emphasis, **Then** the Web UI shows, for every dimension, its base weight, modifier, applied weight, and any modifier reasons and evidence references, and states that the weights change priority, not facts.
4. **Given** an approved Coach Agent version, **When** a Club Admin enables it, **Then** the confirmation reads like that of a Specialist Agent version, and the overview reports the agent as offered in conversations once the platform lists it.

### Edge Cases

- **Coach Agent disabled after submission**: Queued and running invocations keep their pins and finish with the pinned version; new participants and submissions are refused with "agent not available".
- **Several Coach Agents in one conversation**: They share the history like other participants; each answers only when the owner addresses it, and none invokes or debates another (`CA -> CA` is rejected by the architecture).
- **Earlier Coach Agent advice in the history**: It is attributed to its Coach Agent, never presented as the current agent's own words or as a statement of the named coach.
- **Question asks the Coach Agent to speak as the real person or quote them**: The safety policy's non-impersonation and non-fabrication rules apply and the advice states the refusal as the response contract requires; the platform's disclosure is shown regardless.
- **Question asks to compare philosophies or inspect weights**: The rendered context contains the base vector, modifiers, applied vector, evidence availability, and reasons, so the agent can answer with the table the catalog defines; otherwise the response contract is unchanged.
- **Coach Agent suggests consulting a specialist**: Consultations are not available; the suggestion can appear only under "Next questions or consultations" for the human coach, who may ask the specialist directly.
- **Profile distance below 0.10**: Approval already requires the differentiation acknowledgement of the catalog registry; enablement does not repeat it.
- **Simulated model provider outside Development and Test**: Enabling a Coach Agent version whose model selection uses the simulated provider is refused there, as for Specialist Agents.
- **Modifier proposal repeated**: Only one set of modifiers is evaluated per attempt; later proposals in the same attempt are ignored and recorded as omitted.
- **Retry of a Coach Agent invocation**: Each attempt evaluates its own modifiers from its own tool calls; modifiers of an earlier attempt are never carried over.
- **Simulated agent workload**: The Development and Test stand-in executes `User -> CA` invocations too, declaring the base vector without modifiers and marking its advice as simulated.
- **Invocations submitted before this feature**: They keep the route `User -> SA` and their pins unchanged.

## Requirements *(mandatory)*

### Functional Requirements

#### Enablement and participants

- **FR-001**: Club Admins MUST be able to enable exactly one approved Coach Agent version per Coach Agent identifier and to disable a Coach Agent, under the same conditional, audited rules and refusals as for Specialist Agent versions ([Agent Catalog Registry](../archive/20261018-101517-agent-catalog-registry/spec.md), FR-016 and FR-017 there); the refusal "Coach Agent enablement not supported" MUST no longer occur.
- **FR-002**: The read of the agents available for conversations MUST list enabled Coach Agents with their identifier, group, domain, display name, enabled version, and the simulation disclosure statement of the enabled version.
- **FR-003**: The conversation owner MUST be able to add enabled Coach Agents as participants under the same rules as Specialist Agents ([Agent Orchestration Direct Invocations](../archive/20261017-204332-agent-orchestration-invocations/spec.md), FR-004 there); a conversation MAY hold several Coach Agents.

#### Submission and pinning

- **FR-004**: A valid submission to a Coach Agent participant MUST create an invocation with the route `User -> CA` and otherwise follow the submission rules of Agent Orchestration Direct Invocations; the work notification and execution envelope MUST carry that route under versioned, backward-compatible contract changes.
- **FR-005**: For a Coach Agent, the submission MUST pin, in the same atomic step as the catalog registry's pinning, the agent version, every artifact it references, and the dimension set referenced by its philosophy profile, so that the execution envelope, the attempt-scoped artifact read, completion checks, and lineage use exactly those records.
- **FR-006**: Routes other than `User -> SA` and `User -> CA` MUST NOT be accepted for submission.

#### Hermes execution of Coach Agents

- **FR-007**: Hermes MUST execute `User -> CA` invocations of Coach Agent versions in addition to `User -> SA` invocations, with the same intake, lease, checkpoint, MCP session, tool restriction, provider, bound, failure, stale-disposition, shutdown, and logging rules as the [Hermes Agent Runtime](../20261018-113729-hermes-runtime/spec.md) defines; any other route MUST end the attempt as not retryable with reason "unsupported route".
- **FR-008**: Before any model or tool call, Hermes MUST validate the pinned Coach Agent artifacts: each matches its contract and pinned digest; the profile contains exactly one integer weight in `[0,100]` for every dimension of its pinned dimension-set version and no other key, totalling exactly 100; the prompt's, profile's, and modifier policy's dimension-set major versions are equal; the modifier policy stays within `[-3, +3]` per dimension and 10 total positive points and permits only the architecture's context categories; the prompt declares exactly one profile-rendering slot; the safety policy belongs to the Coach Agent group, permits `User -> CA`, and contains the simulation-disclosure, non-impersonation, and non-fabrication rules; and the agent version carries a disclosure statement. A missing, digest-mismatched, or contract-invalid artifact MUST end the attempt as not retryable with reason "invalid artifact"; every other violation with reason "incompatible artifact"; Hermes MUST NOT fall back to another or a partial profile.
- **FR-009**: Hermes MUST render into the Coach Agent's system context, at the prompt's profile-rendering slot, a profile block versioned with Hermes that contains exactly the elements of [Rendered CA Prompt Context](../../docs/architecture/intelligence-agent-catalog.md#rendered-ca-prompt-context): the dimension-set identifier and version; the profile identifier, version, and digest; every dimension identifier with its meaning and base weight; the permitted context categories and modifier constraints; any applied modifiers with their reasons and evidence references; the resulting applied vector; and the instruction that weights affect investigation order, consultation suggestions, recommendation priority, and tradeoff framing but never facts, evidence availability, or confidence. Numeric weights MUST come only from the pinned profile.
- **FR-010**: Hermes' runtime section for Coach Agents MUST additionally state the agent version's disclosure statement, the safety policy's simulation-disclosure, non-impersonation, and non-fabrication rules, that the agent must not consult or address another agent, and that comparison or weight-inspection questions are answered with a table of dimension, base weight, modifier, applied weight, evidence availability, evidence references, and effect on recommendation priority ([Context Modifiers](../../docs/architecture/intelligence-agent-catalog.md#context-modifiers)).
- **FR-011**: Hermes MUST offer Coach Agents no consultation capability and no tools other than the attempt's MCP session tools and the modifier mechanism of FR-012.

#### Context modifiers

- **FR-012**: After the model has consulted evidence, Hermes MUST let it propose at most one set of context modifiers per attempt through a Hermes-local proposal function that is not an MCP tool and reads no evidence. Hermes MUST apply the proposed modifiers only when every modifier (a) belongs to a context category the pinned modifier policy permits, (b) has an integer delta per dimension within the policy's per-dimension bound, (c) references at least one tool call of the same attempt that answered from accepted evidence, and (d) has a plain-text reason of 1 to 300 characters; and when the whole set sums to zero, moves at most the policy's total positive points, and keeps every applied weight non-negative and the applied total at 100. A set that fails any rule MUST be omitted completely and the omission recorded as a content-free checkpoint naming the violated rule; omission MUST NOT end the attempt.
- **FR-013**: Unknown or insufficient context MUST produce no modifier; an "analysis unavailable" answer, a refusal, or missing dimension evidence MUST NOT back a modifier and MUST NOT redistribute weights.
- **FR-014**: When modifiers are applied, Hermes MUST render the profile block again with the applied modifiers and the resulting applied vector before the model continues, and MUST evaluate modifiers at most once per attempt.

#### Completion, lineage, and disclosure

- **FR-015**: Every completion of a `User -> CA` attempt MUST declare, in addition to the execution references, the applied philosophy profile: the dimension-set, profile, and modifier-policy references with digests, the profile-block rendering version, the base vector, every applied modifier with its context category, per-dimension deltas, reason, and evidence references (the call identifiers of the attempt's tool calls), and the applied vector; completions of `User -> SA` attempts MUST NOT declare one.
- **FR-016**: The platform MUST refuse a `User -> CA` completion, with a specific reason, without recording anything and with the attempt staying active, when the applied profile is missing, its references differ from the pins, its base vector differs from the pinned profile, its modifiers violate the pinned modifier policy or the rules of FR-012, its evidence references do not name tool calls of the same attempt that answered from accepted evidence, its applied vector differs from the base vector plus the modifiers, or it differs from the attempt's last recorded profile checkpoint.
- **FR-016a**: Hermes MUST record every applied philosophy profile it renders — the initial one before the first model call and, when modifiers are applied, the one after them — as a profile checkpoint carrying the same structured snapshot as FR-015; the platform MUST validate it with the rules of FR-016 (except the last-checkpoint rule), refuse an invalid one as a malformed checkpoint without recording it, and append a valid one to the lineage, so that failed, expired, and fenced attempts retain their rendered profile and modifier snapshot.
- **FR-017**: The accepted advice and the lineage MUST retain the applied philosophy profile, so that the owner's invocation and lineage reads show the dimension-set, profile, and modifier-policy identifiers, versions, and digests, the base and applied vectors, and the applied modifiers with reasons and evidence references.
- **FR-018**: The platform MUST attach the simulation disclosure statement of the pinned agent version to every Coach Agent advice in every owner read that returns the advice (turns, invocation, and lineage); the advice text MUST NOT be altered and is not required to contain the statement.
- **FR-019**: The platform's agent tool operations and the MCP server MUST serve `User -> CA` attempts exactly as `User -> SA` attempts (attempt binding, pinned tool policy, limits, scope loss, and tool-call lineage).
- **FR-020**: The simulated agent workload MUST execute `User -> CA` invocations in Development and Test with deterministic simulated advice that names itself as simulated and declares a valid applied philosophy profile.

#### Web UI

- **FR-021**: The triage conversation views MUST offer enabled Coach Agents as participants, labelled as Coach Agents and listed separately from Specialist Agents with display name, identifier, and simulation disclosure statement, and MUST address questions to them like to any participant.
- **FR-022**: Every Coach Agent advice MUST be shown with its simulation disclosure statement in addition to the AI-generated advice disclosure, attributed to the Coach Agent by name and identifier, with its text shown unaltered as text.
- **FR-023**: Where the platform returns an applied philosophy profile for an advice, the owner MUST be able to see it with every dimension's base weight, modifier, and applied weight, the modifier reasons and evidence references, the dimension-set, profile, and modifier-policy versions, and the statement that weights change priority, not facts; the lineage view MUST show the pinned philosophy references.
- **FR-024**: The Agent Catalog area MUST treat enabling an approved Coach Agent version like enabling a Specialist Agent version, without the warning that the platform may refuse, and MUST report what conversations offer for every agent only as the platform's read of the agents available for conversations reports it.
- **FR-025**: All new user-facing text MUST come from translation keys with English as the only shipped language, MUST be rendered as text, and MUST keep the views' keyboard operability, announcements, and automated WCAG 2.2 AA rule checks.

#### Seed, audit, and interfaces

- **FR-026**: In Development and Test only, the platform MUST seed the catalog's first-draft Coach Agents as validated records: the dimension set `coach-philosophy-dimensions/1.0.0`, the three provisional base profiles of [Base Philosophy Profiles](../../docs/architecture/intelligence-agent-catalog.md#base-philosophy-profiles), a context-modifier policy within the architecture's bounds, prompt templates derived from the [First-Draft System Prompts](../../docs/architecture/intelligence-agent-catalog.md#first-draft-system-prompts) whose weight tables are replaced by the profile-rendering slot and whose consultation instruction is replaced by suggestions for the human coach until consultations exist, the "All CAs" tool policy, Coach Agent safety policies, the simulated model selection, and approved and enabled Coach Agent versions with disclosure statements for all three Coach Agents. The Coach Agent seed MUST apply once, when the catalog holds no Coach Agent artifacts, independently of the Specialist Agent seed, and MUST be skipped otherwise; this replaces the catalog registry's rule that its seed registers no Coach Agent artifacts.
- **FR-027**: Audit events and telemetry for submissions, claims, completions, and failures MUST distinguish the route; enablement audit events MUST cover Coach Agent versions; profile weights, modifier reasons, prompt text, question text, and advice text MUST NOT appear in audit events, logs, or telemetry.
- **FR-028**: Changed member and workload operations MUST appear in the platform's OpenAPI document with typed schemas, the committed OpenAPI snapshot MUST be refreshed, and the Web UI MUST reach the platform only through its application-owned adapters over the generated client; every changed machine-readable contract MUST gain a backward-compatible release with valid and invalid golden fixtures.

#### Evidence

- **FR-029**: Automated tests MUST run without model services, network access beyond locked dependency installation, or secrets, using Hermes' scripted provider, and MUST cover: Coach Agent enablement and refusals, participants, the `User -> CA` route, pinning including the dimension set, every Hermes validation failure, the rendered profile block's content, modifier acceptance and every omission rule, the profile checkpoints and the completion's applied-profile checks and every refusal, lineage and owner reads, disclosure in every read, the simulated agent workload, the tool operations for Coach Agent attempts, the seed, the Web UI views and the complete ask-and-answer flow against the simulated API, and a browser test against the running platform that shows the seeded Coach Agents enabled and offered in conversations in the Agent Catalog area, without a test-only platform hook.
- **FR-030**: An automated cross-process test MUST run the platform API, the MCP server, and Hermes as separate processes and prove that a member's question to a Coach Agent is claimed by Hermes, calls at least one tool through the MCP server, and completes with the simulation disclosure and the applied philosophy profile visible through the owner's reads.

### Key Entities

- **Coach Agent enablement**: The stamp's single enabled Coach Agent version per Coach Agent identifier, or none.
- **Coach Agent invocation**: A logical invocation with route `User -> CA`, pinned to a Coach Agent version, its artifacts, and the profile's dimension set.
- **Profile block**: Hermes' versioned rendering of the pinned dimension set, base profile, modifier policy, applied modifiers, and applied vector inside the Coach Agent's system context; never persisted or logged by Hermes.
- **Context modifier**: An evidence-backed, bounded integer shift of dimension weights for one permitted context category, with reason and evidence references.
- **Applied philosophy profile**: The base vector, the applied modifiers, the applied vector, and the pinned philosophy references, recorded in profile checkpoints, declared with a completion, and retained in the lineage and accepted advice.
- **Simulation disclosure**: The agent version's statement that the Coach Agent is an AI simulation inspired by documented public philosophy, presented with every Coach Agent advice.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: In the cross-process test, a member's question to a Coach Agent is answered with accepted advice, its disclosure, and its applied philosophy profile within 60 seconds of submission.
- **SC-002**: In automated tests, 100% of rendered Coach Agent contexts contain every element of the catalog's rendered profile context with weights equal to the pinned profile, and 0 contexts contain weights from any other source.
- **SC-003**: In automated tests, 100% of invalid or incompatible philosophy artifacts end the attempt with 0 model or tool calls, and 0 attempts complete with a profile other than the pinned one.
- **SC-004**: In automated tests, 100% of modifier sets that violate a bound, the budget-neutral rule, the permitted categories, or the evidence rule are omitted, and 100% of accepted Coach Agent advice has an applied vector that totals 100 and equals the base vector plus its recorded modifiers.
- **SC-005**: 100% of Coach Agent advice in owner reads and in the Web UI is shown with its simulation disclosure.
- **SC-006**: 0 audit events, logs, or telemetry records in the tests contain profile weights, modifier reasons, prompt text, question text, or advice text.

## Assumptions

- **Platform and runtime authority**: Conversations, invocations, attempts, leases, stale dispositions, scope loss, retries, accepted advice, and lineage are those of [Agent Orchestration Direct Invocations](../archive/20261017-204332-agent-orchestration-invocations/spec.md); records, validation, approval, pins, and the attempt-scoped read are those of the [Agent Catalog Registry](../archive/20261018-101517-agent-catalog-registry/spec.md); execution is that of the [Hermes Agent Runtime](../20261018-113729-hermes-runtime/spec.md); this feature changes them only as its requirements state.
- **Wave 3 without its gates**: This feature implements the direct Coach Agent functionality of [Implementation Waves](../../docs/architecture/intelligence-agent-catalog.md#implementation-waves) Wave 3; the evaluation suites of [Validation And Promotion Gates](../../docs/architecture/intelligence-agent-catalog.md#validation-and-promotion-gates) (factual consistency across personas, disclosure, non-impersonation, differentiation) remain required production promotion evidence, remain open, and are not claimed. Approval and enablement record accountable decisions only; profile values, prompt drafts, and model choices stay Provisional design inputs.
- **No consultations**: `CA -> SA` consultations come with the later Delegated Coach-to-Specialist Consultations feature; `CA -> CA`, `SA -> SA`, and SA-initiated `SA -> CA` stay rejected by the architecture.
- **Configured values**: Reason bounds, the rendering version, and development values follow the existing runtime and orchestration configuration; production values remain open ([Production Deployment and Operations](../../docs/architecture/production-operations.md)).
- **Out of scope**: consultations; new dimensions, dimension-set major versions, or profile changes; evaluation suites, promotion gates, and A/B evidence; real provider calls in automated tests; streaming; production values.
- **Evidence**: Passing tests are development evidence only and do not establish model quality, behavioral fidelity, deployment support, or production readiness.
