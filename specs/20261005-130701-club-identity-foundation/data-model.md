# Data Model: Club and Identity Foundation

**Feature**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md) |
**Research**: [research.md](research.md)

All tables live in the application schema `socalytics` of the stamp database.
No table or column carries a club identifier: the single `club` row is the
implicit root. Identifiers are UUIDv7 values generated by the application.
Timestamps are `timestamptz` in UTC. The persistence foundation's names are
used as published in its
[migration-authoring contract](../20261005-130700-platform-persistence-foundation/contracts/migration-authoring.md):

- Each versioned root has a `version bigint not null default 1` column and
  calls `CALL socalytics.attach_version_trigger('socalytics.<root>')`, which
  attaches the trigger function `socalytics.advance_version()`.
- Each child table calls
  `CALL socalytics.attach_aggregate_child_triggers('socalytics.<child>', 'socalytics.<root>', '<child_key>')`.
  This attaches the trigger function `socalytics.touch_aggregate_root()`, so
  changing the child advances its root's version.
- Every table without a `version` column is classified in
  `Tests/SocAlytics.Platform.Integration.Tests/Structure/PersistedTableClassifications.cs`
  as `ChildOf(…)`, `Immutable`, or `Unversioned(reason)`.

## Entities

### member_account

The local identity and membership of one person. Maps to the internal Identity
user type `IdentityMemberAccount` in Infrastructure.

| Column | Type | Rules |
| --- | --- | --- |
| `id` | `uuid` | Primary key |
| `account_name` | `text` | As entered; 3 to 64 chars from letters, digits, and `.` `_` `-` `@`; immutable |
| `normalized_account_name` | `text` | Upper-invariant form; unique |
| `password_hash` | `text` | Null until the first password is set; Identity PBKDF2 hash only |
| `security_stamp` | `text` | Not null; rotated on password set, change, or reset, on deactivation, when sessions are ended by an admin, and by break-glass recovery |
| `lockout_enabled` | `boolean` | Not null, default `true` |
| `lockout_end` | `timestamptz` | Null when not locked |
| `access_failed_count` | `integer` | Not null, default `0`, check `>= 0` |
| `two_factor_enabled` | `boolean` | Not null, default `false`; MFA readiness only (FR-022) |
| `password_change_required` | `boolean` | Not null, default `false`; `true` for the first Club Admin created by bootstrap (FR-051) and after break-glass recovery (FR-050); cleared by the holder's own password change |
| `membership_status` | `text` | Not null, check in (`active`, `deactivated`), default `active` |
| `membership_changed_at` | `timestamptz` | Not null |
| `created_at` | `timestamptz` | Not null |
| `created_by_account_id` | `uuid` | Null only for the bootstrap administrator; FK `member_account(id)` |
| `version` | `bigint` | Advanced by trigger; also advanced by role child rows |

Validation rules:

- Only Club Admins create accounts (FR-015). A new account is `active` with no
  roles and no password, and a set-password credential is issued in the same
  unit of work (FR-016).
- Sign-in requires `membership_status = 'active'`, a non-null `password_hash`,
  and no active lockout. Every failure looks identical and costs exactly one
  password-hash verification. The verification uses the stored hash, or a
  dummy hash when the account is unknown or has no password, and it runs
  before any refusal decision. A locked account's counter is not incremented
  (FR-018, research R6).
- When `password_change_required` is `true`, a successful sign-in creates a
  restricted session. `SessionInfo.passwordChangeRequired` is `true`, and only
  `getSession`, `getCurrentMember`, `changeOwnPassword`, and `signOut` are
  allowed. Every other operation returns `403 password-change-required`, and
  no club or team role authorizes anything. `changeOwnPassword` clears the
  flag in the same unit of work, so the session becomes unrestricted on its
  next request.
- The account can never be deleted in this feature.

State transitions (lifecycle actions; no `If-Match`):

```text
active --deactivate--> deactivated   (revokes all roles, rotates stamp, ends sessions,
                                      revokes own open credentials and, if Club Admin,
                                      every open credential the member issued)
deactivated --reactivate--> active   (no roles restored)
```

Any other request is rejected with `409 invalid-state-transition`.
Deactivating the last active Club Admin is rejected with
`409 last-club-admin` (FR-034).

Lockout fields (`lockout_end`, `access_failed_count`) are maintained by
Identity. Unlock clears both and is allowed in any membership state.
Break-glass recovery also clears both (see
[recovery_directive_use](#recovery_directive_use)).

### club

The singleton organizational root of the stamp (FR-001).

| Column | Type | Rules |
| --- | --- | --- |
| `id` | `uuid` | Primary key |
| `singleton` | `boolean` | Not null, default `true`, `check (singleton)`, unique |
| `display_name` | `text` | 1 to 100 chars after trimming |
| `bootstrap_admin_account_id` | `uuid` | Not null; FK `member_account(id)`; detects conflicting bootstrap configuration (FR-003) |
| `created_at` | `timestamptz` | Not null |
| `version` | `bigint` | Advanced by trigger |

Rules:

- The row is created only by the bootstrap command. The API offers no create
  operation, and `POST /api/v1/club` is not mapped. The singleton constraint
  rejects a second row at the database.
- Bootstrap creates the first Club Admin with
  `password_change_required = true` (FR-051). Once the club row exists,
  bootstrap never reads `ClubBootstrap:FirstClubAdmin:InitialPassword`. The
  operator removes that secret from the deployment configuration after the
  first sign-in and password change.
- Settings edits (`display_name`) require `If-Match` (FR-042).

### season

| Column | Type | Rules |
| --- | --- | --- |
| `id` | `uuid` | Primary key |
| `name` | `text` | 1 to 100 chars after trimming |
| `state` | `text` | Check in (`draft`, `active`, `archived`); default `draft` |
| `created_at` | `timestamptz` | Not null |
| `activated_at` | `timestamptz` | Null unless the season has been activated |
| `archived_at` | `timestamptz` | Null unless the season has been archived |
| `version` | `bigint` | Advanced by trigger |

Constraints:

- A partial unique index `ux_season_single_active` on `((true))` where
  `state = 'active'` enforces at most one active season (FR-007).
- Check: `draft` implies `activated_at` and `archived_at` are null; `active`
  implies `activated_at` is set and `archived_at` is null; `archived` implies
  both are set.

State transitions (Club Admin only; no `If-Match`):

```text
draft --activate--> active      (rejected with 409 season-already-active if another season is active)
active --archive--> archived    (season, teams, and matches become read-only)
```

Any other transition is rejected with `409 invalid-state-transition`.

### team

| Column | Type | Rules |
| --- | --- | --- |
| `id` | `uuid` | Primary key |
| `season_id` | `uuid` | Not null; FK `season(id)`; immutable (FR-009) |
| `name` | `text` | 1 to 100 chars after trimming |
| `created_at` | `timestamptz` | Not null |
| `version` | `bigint` | Advanced by trigger |

Index: `ix_team_season` on `(season_id)`.

Rules:

- Creating a team requires an existing season that is not `archived`. A
  missing season returns `404`, and an archived one returns
  `409 season-archived`.
- Editing the name requires `If-Match`. The write locks the season row
  `FOR SHARE` and rejects `archived`.

### match

| Column | Type | Rules |
| --- | --- | --- |
| `id` | `uuid` | Primary key |
| `team_id` | `uuid` | Not null; FK `team(id)`; immutable (FR-010) |
| `opponent_name` | `text` | 1 to 100 chars; captured at creation; immutable (FR-011) |
| `kickoff_at` | `timestamptz` | Not null |
| `home_away` | `text` | Check in (`home`, `away`, `neutral`) |
| `competition` | `text` | Null or 1 to 100 chars |
| `created_at` | `timestamptz` | Not null |
| `created_by_account_id` | `uuid` | Not null; FK `member_account(id)` |
| `version` | `bigint` | Advanced by trigger |

Index: `ix_match_team_kickoff` on `(team_id, kickoff_at, id)`.

Rules:

- Coaches of the owning team and Club Admins create and edit matches, and
  Viewers read them (FR-036). Creating or editing a match locks the season row
  of the team `FOR SHARE` and rejects `archived` (FR-008).
- Edits change only `kickoff_at`, `home_away`, and `competition`, and require
  `If-Match`. A body that names `opponent` or `teamId` is rejected with
  `400 validation-failed` and field code `immutable`.

### club_role_assignment

| Column | Type | Rules |
| --- | --- | --- |
| `member_account_id` | `uuid` | FK `member_account(id)` |
| `role` | `text` | Check in (`club-admin`, `registrar`) |
| `assigned_at` | `timestamptz` | Not null |
| `assigned_by_account_id` | `uuid` | Null only for the bootstrap assignment |

Primary key: `(member_account_id, role)`. The table is classified
`ChildOf(member_account)`, so insert and delete advance the account version
through `socalytics.touch_aggregate_root()`.

Rules:

- Assignment requires an `active` membership; otherwise it is rejected with
  `409 membership-inactive`. `club-admin` implies all `registrar` authority
  (FR-032). Holding both is allowed and redundant.
- Revoking `club-admin` takes the `club-admin-invariant` advisory lock and
  rejects removal of the last active Club Admin (FR-034). A successful
  revocation also revokes every open one-time credential the member issued
  (`issuer-lost-authority`, FR-052).
- Registrar grants no team data access and no administration in this feature
  (FR-033).

### team_role_assignment

| Column | Type | Rules |
| --- | --- | --- |
| `member_account_id` | `uuid` | FK `member_account(id)` |
| `team_id` | `uuid` | FK `team(id)` |
| `role` | `text` | Check in (`coach`, `viewer`) |
| `assigned_at` | `timestamptz` | Not null |
| `assigned_by_account_id` | `uuid` | Not null |

Primary key: `(member_account_id, team_id)`, so a member has at most one role
per team (FR-035). Index `ix_team_role_team` on `(team_id)`. The table is
classified `ChildOf(member_account)`.

Rules: assignment upserts and replaces a different role, and is a no-op for the
same role. It requires an `active` membership and an existing team.

### member_session

A server-validated human session (FR-023 to FR-028).

| Column | Type | Rules |
| --- | --- | --- |
| `id` | `uuid` | Primary key; safe to reference in audit |
| `member_account_id` | `uuid` | FK `member_account(id)` |
| `token_hash` | `bytea` | SHA-256 of the cookie token; unique; the raw token is never stored |
| `security_stamp` | `text` | Stamp at issue, or updated by the holder's own password change |
| `created_at` | `timestamptz` | Not null |
| `last_seen_at` | `timestamptz` | Slid at most once per 60 seconds |
| `idle_expires_at` | `timestamptz` | `last_seen_at` plus the configured idle timeout |
| `absolute_expires_at` | `timestamptz` | `created_at` plus the configured absolute lifetime |
| `ended_at` | `timestamptz` | Null while live |
| `end_reason` | `text` | Null or one of `sign-out`, `password-changed`, `password-reset`, `deactivated`, `ended-by-admin`, `replaced`, `break-glass-recovery` |

Index: `ix_member_session_live` on `(member_account_id)` where
`ended_at is null`.

A session is valid only when all of these hold:

- `ended_at` is null;
- the current time is before both `idle_expires_at` and
  `absolute_expires_at`;
- the account is `active`;
- the account's `security_stamp` equals the session's `security_stamp`.

A valid session is restricted while the account's `password_change_required`
is `true` (see [member_account](#member_account)).

The anti-forgery token is not stored. It is derived per request as
`base64url(HMAC-SHA256(key = raw session token, message = "socalytics-csrf"))`
and compared in fixed time with `X-CSRF-Token` (research R3).

Retention and purge of ended sessions are deferred (POL-001, POL-002).

### one_time_credential

A single-use, time-limited set-password or reset credential (FR-016, FR-021).

| Column | Type | Rules |
| --- | --- | --- |
| `id` | `uuid` | Primary key |
| `member_account_id` | `uuid` | FK `member_account(id)` |
| `purpose` | `text` | Check in (`set-password`, `password-reset`) |
| `credential_hash` | `bytea` | SHA-256 of the raw credential; unique |
| `issued_at` | `timestamptz` | Not null |
| `issued_by_account_id` | `uuid` | Not null; the issuing Club Admin |
| `expires_at` | `timestamptz` | `issued_at` plus the configured lifetime |
| `consumed_at` | `timestamptz` | Set once on successful redemption |
| `revoked_at` | `timestamptz` | Set when the credential is revoked (see `revocation_reason`) |
| `revocation_reason` | `text` | Null unless revoked; one of `superseded`, `issuer-lost-authority`, `target-deactivated`, `break-glass-recovery` |

Indexes:

- `ix_one_time_credential_open` on `(member_account_id)` where
  `consumed_at is null and revoked_at is null`;
- `ix_one_time_credential_issuer_open` on `(issued_by_account_id)` where
  `consumed_at is null and revoked_at is null`.

Check: `revoked_at` and `revocation_reason` are both null or both set.

Issuance rules:

- `set-password` is allowed only while `password_hash` is null, and
  `password-reset` only while it is set. Otherwise the request is rejected
  with `409 credential-not-applicable`.
- Both purposes require an `active` membership; otherwise the request is
  rejected with `409 membership-inactive`.

Redemption locks the target account `FOR UPDATE` and consumes the credential
atomically together with the password change. The consuming `UPDATE` also
requires `member_account.membership_status = 'active'` (FR-052). Any
mismatch yields the generic `400 credential-invalid`.

Revocation rules (FR-052): each rule sets `revoked_at` and
`revocation_reason` and records one `credential.revoked` audit event per
credential, in the same unit of work as its trigger.

| Trigger | Credentials revoked | `revocation_reason` |
| --- | --- | --- |
| A newer credential is issued for the account | The account's other open credentials | `superseded` |
| `club-admin` is revoked from a member, or a Club Admin is deactivated | Every open credential with `issued_by_account_id` = that member | `issuer-lost-authority` |
| A member is deactivated | The member's own open credentials | `target-deactivated` |
| Break-glass recovery is applied | The account's open credentials | `break-glass-recovery` |

### recovery_directive_use

This table is the single-use ledger for break-glass recovery directives
(FR-050). Each applied recovery identifier gets exactly one row.

| Column | Type | Rules |
| --- | --- | --- |
| `recovery_id` | `text` | Primary key (unique); operator-chosen opaque identifier, 8 to 128 characters; not a secret |
| `member_account_id` | `uuid` | Not null; FK `member_account(id)`; the recovered account |
| `applied_at` | `timestamptz` | Not null |
| `correlation_id` | `text` | Not null; the correlation id of the start run that applied it |

The table is insert-only. Only successful applications are recorded, so a
refused directive does not consume its identifier.

#### Directive (protected configuration, not stored)

| Key | Rules |
| --- | --- |
| `BreakGlassRecovery:AccountName` | Required; must name an existing account |
| `BreakGlassRecovery:RecoveryId` | Required; 8 to 128 characters; single use |
| `BreakGlassRecovery:TemporaryCredential` | Required secret; must satisfy the configured password policy; never logged, audited, or echoed in diagnostics |

The directive is optional. When the section is absent, nothing happens. A
partially filled section is refused with `directive-incomplete`.

#### Application at API start

The directive is evaluated by `ClubBootstrapHostedService` after the
bootstrap step, in the same unit of work and under the same
`pg_advisory_xact_lock('club-bootstrap')`. Concurrently starting instances
therefore serialize, and at most one applies a given recovery identifier. The
others find the identifier used.

The evaluation runs in this order, and the first failing check refuses the
directive:

1. The section is incomplete: refused with reason `directive-incomplete`.
2. A `recovery_directive_use` row exists for the recovery id: refused with
   reason `recovery-id-used`.
3. The account name matches no account: refused with reason
   `unknown-account`.
4. The account is locked `FOR UPDATE`. A `deactivated` account is refused with
   reason `account-inactive`.
5. The temporary credential violates the password policy: refused with reason
   `password-policy`.
6. Otherwise the directive is applied, all in one unit of work:
   - set `password_hash` from the temporary credential through `UserManager`;
   - set `password_change_required = true`;
   - clear `lockout_end` and `access_failed_count`;
   - rotate `security_stamp`;
   - end all of the account's sessions with reason `break-glass-recovery`;
   - revoke the account's open one-time credentials
     (`break-glass-recovery`);
   - insert the `recovery_directive_use` row;
   - record `break-glass-recovery.applied`.

The recovery itself never assigns or removes roles. If the account holds no
`club-admin` role, it still holds none afterwards.

A refusal changes nothing in account, session, or credential state. It records
`break-glass-recovery.refused` with the reason code, logs a diagnostic that
names only the reason and the configuration key, and leaves readiness
unaffected. The `club-bootstrap` check reports only bootstrap state.

No API operation can trigger recovery. If the primary key on `recovery_id`
ever fires despite the lock, that unique violation is handled as
`recovery-id-used`, and the whole unit of work rolls back before the refusal
is recorded.

### security_audit_event

Append-only security evidence, kept separately from application logs (FR-044
to FR-048).

| Column | Type | Rules |
| --- | --- | --- |
| `id` | `uuid` | Primary key (UUIDv7, time-ordered) |
| `occurred_at` | `timestamptz` | Not null; from the application `TimeProvider` |
| `event_type` | `text` | Not null; see the catalog below |
| `action` | `text` | Not null (for example `create`, `assign`, `revoke`, `sign-in`) |
| `outcome` | `text` | Check in (`succeeded`, `unchanged`, `denied`, `failed`, `refused`) |
| `actor_kind` | `text` | Check in (`member`, `system`, `anonymous`) |
| `actor_account_id` | `uuid` | Null when the actor is unknown or the system |
| `session_id` | `uuid` | Null when no session exists |
| `resource_type` | `text` | Not null (`club`, `season`, `team`, `match`, `member`, `session`, `credential`) |
| `resource_id` | `text` | Null when the resource is unknown |
| `team_id` | `uuid` | Team scope when applicable |
| `data_class` | `text` | Not null, default `DAT-001` |
| `reason_code` | `text` | Null or a stable code (for example `wrong-password`, `last-club-admin`) |
| `details` | `jsonb` | Not null, default `{}`; allow-listed keys only, no free text |
| `correlation_id` | `text` | Not null; the W3C trace id of the request or background run |

There are no foreign keys, so evidence stays independent of mutable data.
Indexes: `ix_audit_occurred` on `(occurred_at)`, `ix_audit_actor` on
`(actor_account_id)`, and `ix_audit_resource` on `(resource_type,
resource_id)`.

Protection:

- The migration revokes `UPDATE`, `DELETE`, and `TRUNCATE` from
  `socalytics_app`, which keeps `INSERT` and `SELECT`.
- The trigger function `socalytics.reject_audit_mutation()` is attached as
  `BEFORE UPDATE OR DELETE FOR EACH ROW` and `BEFORE TRUNCATE FOR EACH
  STATEMENT`, and raises an exception.

The table must never contain a password, password hash, one-time credential,
break-glass temporary credential, session token or hash, anti-forgery token,
security stamp, or identity token (FR-046).

## Domain Types (Domain layer)

Domain types are pure and have no framework dependencies:

- `Club` (`DisplayName`)
- `Season` (`SeasonState`, transition rules `CanActivate` and `CanArchive`)
- `Team`
- `Match` with `MatchOpponent` (immutable snapshot)
- `MatchDetails` (`KickoffAt`, `HomeAway`, `Competition`)
- `MemberAccount` (`MembershipStatus`)
- `AccountName` (validation and normalization)
- `ClubRole` (`ClubAdmin`, `Registrar`)
- `TeamRole` (`Coach`, `Viewer`)
- `DisplayName` (1 to 100 chars after trimming)

| `AccessDecision` | `SocAlytics.Platform.Application.IdentityAccess` | `Granted(TeamScope?)`, `NotFound`, `Forbidden`; denials are already audited |
| `OperationResult<T>`, `OperationFailure` | `SocAlytics.Platform.Application.Abstractions` | Handler outcome mapped by the API to problem details (`Validation`, `NotFound`, `Forbidden`, `Conflict(code)`, `VersionRequired`, `VersionMismatch`, `Unauthenticated`, `PasswordChangeRequired`) |

This feature is the canonical owner of the names above, of the cookie
`__Host-socalytics-session`, of the header `X-CSRF-Token`, and of the problem
type scheme `urn:socalytics:problem:<code>`. Other features reuse them and do
not redefine them. Handlers use the persistence foundation's
`IUnitOfWork.BeginAsync` → `IUnitOfWorkScope` (`CommitAsync`,
`RollbackAsync`) and map `VersionedWriteResult` (`Applied`, `NotFound`,
`ConcurrencyConflict`) to `OperationFailure`.

API-internal building blocks reused by later features' endpoints:

- the authentication scheme `SocAlyticsSession`;
- the authorization policies `AuthorizationPolicyNames.ActiveMember` (valid,
  unrestricted session) and `AuthorizationPolicyNames.SessionHolder` (any
  valid session, including one restricted by `password_change_required`; used
  only by `getSession`, `getCurrentMember`, `changeOwnPassword`, and
  `signOut`);
- the endpoint filter `SessionAntiforgeryFilter`;
- the route group helper `MapMemberApi` (the `/api/v1` group with
  `ActiveMember` and the anti-forgery filter);
- `IfMatchHeader` parsing;
- `ProblemResults` mapping from `OperationFailure`.

## Migrations (Infrastructure `Persistence/Migrations/`)

Migrations are named by description. Sequence numbers are assigned at
implementation as the next free numbers, in this order:

1. `identityaccess_member_accounts`: the `member_account` table (including
   `password_change_required`), its unique normalized name, its checks, and
   `CALL socalytics.attach_version_trigger('socalytics.member_account')`.
2. `club_hierarchy`: `club`, `season`, `team`, and `match`, with the singleton
   and active-season indexes, foreign keys, and one
   `attach_version_trigger` call per table.
3. `identityaccess_role_assignments`: `club_role_assignment` and
   `team_role_assignment`, each attached with
   `CALL socalytics.attach_aggregate_child_triggers('socalytics.<child>', 'socalytics.member_account', 'member_account_id')`.
4. `identityaccess_sessions_and_credentials`: `member_session`,
   `one_time_credential`, and `recovery_directive_use`, plus
   `REVOKE UPDATE, DELETE, TRUNCATE ON socalytics.recovery_directive_use FROM socalytics_app`.
5. `identityaccess_security_audit`: `security_audit_event`, the
   `socalytics.reject_audit_mutation()` function and triggers, and the
   `REVOKE UPDATE, DELETE, TRUNCATE ... FROM socalytics_app` statement.

Each migration relies on the persistence foundation's default privileges for
`socalytics_app` (DML on application tables). Only the audit table and the
recovery ledger narrow them, so the runtime role can never delete a used
recovery id to make it reusable.
