# Feature Specification: Agent Catalog Registry

**Feature Branch**: `20261018-101517-agent-catalog-registry`

**Created**: 2026-10-18

**Status**: Draft

**Input**: User description: "Agent Catalog Registry: the architecture defines the Coach Agent and Specialist Agent catalog and its governance — catalog rules, prompt and advice governance, the semantically versioned philosophy dimension set, immutable base philosophy profiles with integer weights in `[0,100]` that total 100 for every dimension of their dimension-set version, bounded budget-neutral context-modifier policies, the per-agent MCP tool policy, and Wave 0's 'define prompt, model, tool-policy, and safety-policy artifact formats' (docs/architecture/intelligence-agent-catalog.md: Catalog Rules, Prompt And Advice Governance, Coach Philosophy Weighting with Dimension Set, Base Philosophy Profiles, Context Modifiers, Adding Or Revising A Coach Agent, Specialist Agent Catalog, MCP Tool Policy, Implementation Waves, Validation And Promotion Gates; docs/architecture/intelligence-and-agents.md: Hermes resolves the versioned prompt, model/deployment, tool-policy, safety-policy, and CA philosophy-profile artifacts for each invocation, and an invalid or incompatible profile fails the invocation). A Development and Test seed registers the first-wave direct specialists (`specialist-tactics`, `specialist-video-analysis`) from the catalog's first-draft prompts; Coach Agent definitions are registrable and validated but enabling them is left to spec 9. Out of scope: the Web UI (spec 5), evidence tools themselves (spec 6), Hermes and prompt rendering (spec 8), Coach Agent conversations (spec 9), consultations (spec 10), evaluation suites and promotion evidence, model provider secrets, production values. ## Clarifications

### Session 2026-10-18

- Q: What happens to invocations that were submitted before the catalog existed and therefore carry no pin? → A: They stay readable without a pin; an unfinished one is never executed with an unpinned envelope: its next claim is refused and it fails with reason "agent not available".
- Q: Should the conversation owner see the pinned agent version and digests in invocation and lineage reads? → A: Yes, the agent version and the artifact kinds, identifiers, versions, and digests, never artifact content.
- Q: Should the Development and Test seed also register the philosophy dimension set and the three provisional base profiles? → A: No; the seed registers only the records of the two direct specialists, and tests register Coach Agent artifacts from the contract fixtures.
- Q: Should catalog activity appear in the platform's telemetry? → A: Yes: counters of registrations (accepted and refused, by record kind), approvals, retirements, and enablement changes, without any record content.
- Q: How does the platform decide that a model selection carries no secret? → A: By shape: the provider is one of a fixed set, the model and deployment or configuration names must match a bounded name pattern (letters, digits, `.`, `-`, `_`, `/`, `:`; at most 128 characters), parameters are typed numbers or enumerations, and no other field is accepted.

## User Scenarios & Testing *(mandatory)*

The actors are Club Admins, who act as catalog operators until a stamp-operator role exists (as for the [Analyst Registry](../archive/20261012-152148-analyst-registry/spec.md)), the members who start triage conversations, and the stamp-local agent workload that executes agent work ([Intelligence and Agents → Client, Transport, And Runtime Protocol](../../docs/architecture/intelligence-and-agents.md#client-transport-and-runtime-protocol)). The catalog's content and governance rules are defined by the [Intelligence Agent Catalog](../../docs/architecture/intelligence-agent-catalog.md); this feature turns its design inputs into versioned, validated, immutable platform records and makes the platform the authority for which agent version an invocation uses. Agent conversations, invocations, claims, and lineage come from [Agent Orchestration Direct Invocations](../archive/20261017-204332-agent-orchestration-invocations/spec.md), where today the enabled Specialist Agent identifiers are configuration only and no artifact is versioned.

### User Story 1 - Register and approve a versioned Specialist Agent (Priority: P1)

A Club Admin registers the artifacts of a Specialist Agent — its prompt template, model and deployment selection, tool policy, and safety policy — and then an agent version that binds the agent identifier to exactly those artifacts. The platform validates every record, stores it immutably under a digest computed from its content, and refuses invalid records with a specific reason. The new agent version starts as a draft; a separately audited approval makes it eligible for enablement. Approved versions never change; a change needs a new version, and retiring a version keeps it in history but stops new enablement.

**Why this priority**: Every later step — enablement, pinning, the workload's read, Coach Agents, and evidence tools — rests on validated, immutable, versioned agent records. Without them the catalog stays configuration.

**Independent Test**: As a Club Admin, register a prompt template, model selection, tool policy, and safety policy for `specialist-tactics`, register an agent version referencing them, approve it, and confirm the stored digests, states, and audit events; then submit a tool policy with an unknown tool, a tool outside the agent's catalog baseline, a model selection with an extra field or a name outside the allowed pattern, and an agent version for an identifier outside the catalog, and confirm each is refused with a specific reason and nothing is stored.

**Acceptance Scenarios**:

1. **Given** a Club Admin, **When** they register a valid prompt template, model selection, tool policy, or safety policy with an identifier and semantic version, **Then** the record is stored immutably with a digest computed from its canonical content and returned with that digest.
2. **Given** a stored record, **When** the same identifier and version is registered again with equivalent content, **Then** the stored record is returned unchanged; **When** it is registered with different content, **Then** it is refused because versions are immutable.
3. **Given** registered artifacts, **When** a Club Admin registers an agent version for a catalog agent identifier that references them by digest, **Then** a draft agent version with its own content digest is stored.
4. **Given** a tool policy naming a tool that is not on the platform's tool allowlist, an agent version whose tool policy grants a tool outside the agent's catalog baseline, a model selection with an extra field, a name outside the allowed pattern, or an unknown provider, an agent identifier outside the catalog, an artifact that does not exist, or an artifact meant for the other agent group, **When** it is registered, **Then** it is refused with a problem response naming every violation, and nothing is stored.
5. **Given** a draft agent version, **When** a Club Admin (including its creator) approves it, **Then** it becomes approved in a separately audited operation that marks self-approval; **and When** anyone tries to change an approved version, **Then** the change is refused and a new version is required.
6. **Given** an approved agent version that is not enabled, **When** a Club Admin retires it, **Then** it can no longer be enabled, while invocations that pinned it are unaffected; retiring the currently enabled version is refused until another version is enabled or the agent is disabled.
7. **Given** a member who is not a Club Admin, **When** they try to register, approve, or retire, **Then** the request is refused and the attempt is audited.

### User Story 2 - Enable an agent version and pin it into every invocation (Priority: P2)

A Club Admin enables exactly one approved version per Specialist Agent identifier on the stamp, or disables the agent. The agents members can add to a triage conversation are exactly the enabled ones. When a member submits a question, the platform resolves the agent's currently enabled version and pins its version and every artifact digest into the invocation; retries, the execution envelope, completion, and lineage all use the pinned version, so later enablement changes, new versions, or retirements never alter running or historical invocations. The agent workload reads the pinned artifacts of the invocation it is executing through an authorized machine read and nothing else.

**Why this priority**: This is where the catalog replaces configuration and becomes the source of truth for agent execution; it needs approved versions (Story 1).

**Independent Test**: Enable an approved version of `specialist-tactics`, submit a question, and confirm that the invocation, the claimed execution envelope, and the lineage carry the version and artifact digests; read each pinned artifact as the workload with the current attempt and confirm the content matches its digest; enable a second version and confirm that a retry of the first invocation still uses the first version while a new submission pins the second; disable the agent and confirm that it disappears from the enabled-agents read and that new participants and submissions are refused.

**Acceptance Scenarios**:

1. **Given** an approved Specialist Agent version, **When** a Club Admin enables it with the enablement state they last saw, **Then** it becomes the agent's single enabled version, replacing any previously enabled version atomically, and the change is audited.
2. **Given** enabled agents, **When** an active member with Club Admin or a team role reads the agents available for conversations, **Then** they see exactly the enabled agents with identifier, group, domain, display name, and enabled version.
3. **Given** a draft or retired version or a Coach Agent version, **When** a Club Admin tries to enable it, **Then** the request is refused with a specific reason and the enablement is unchanged.
4. **Given** an enabled agent that is a participant of a conversation, **When** the owner submits a question to it, **Then** the invocation pins the enabled agent version and the digests of all its artifacts at submission.
5. **Given** a queued or running invocation, **When** the agent's enabled version changes, the agent is disabled, or its pinned version is retired, **Then** the invocation, its retries, its execution envelope, and its lineage keep the pinned version and digests.
6. **Given** a claimed attempt, **When** the workload receives the execution envelope, **Then** it contains the pinned agent version and the identifier, version, kind, and digest of every pinned artifact; **and When** the workload reads one of those artifacts with the current attempt, **Then** it receives the immutable content whose digest matches the pin.
7. **Given** an artifact not pinned by the attempt's invocation, an attempt that is no longer current, or a caller that is not a workload identity, **When** it tries the machine read, **Then** the read is refused without disclosing the artifact.
8. **Given** a completion whose declared prompt, tool-policy, or safety-policy references do not match the invocation's pinned digests, **When** the workload completes the attempt, **Then** the completion is refused and the attempt stays active.

### User Story 3 - Register and validate Coach Agent philosophy artifacts (Priority: P3)

A Club Admin registers the shared philosophy dimension set, immutable base philosophy profiles over it, context-modifier policies, and Coach Agent versions that bind a Coach Agent identifier to a prompt, model selection, tool policy, safety policy, profile, and modifier policy. The platform enforces every architectural invariant — one integer weight in `[0,100]` for every dimension of the profile's dimension-set version and a total of exactly 100, no unknown or private dimensions, per-weight rationale and provenance, bounded and budget-neutral modifiers, dimension-set compatibility between prompt, profile, and modifier policy, and simulation disclosure and non-impersonation requirements — and reports the profile's distance to every other approved Coach Agent profile. Coach Agent versions can be approved and retired, but enabling them is left to the later Coach Agent conversations feature.

**Why this priority**: Coach Agents are a later implementation wave, but their artifacts must be governed by the same authority from the start so the later feature only enables and executes them. It builds on Story 1's records and states.

**Independent Test**: Register `coach-philosophy-dimensions/1.0.0` and the three provisional base profiles, register a modifier policy and a Coach Agent version, approve it, and confirm the reported distances (Klopp–Guardiola 0.25, Klopp–Mourinho 0.25, Guardiola–Mourinho 0.31); then register profiles whose weights total 99, omit a dimension, add an unknown dimension, use a non-integer or out-of-range weight, or reference an incompatible dimension-set major version, a modifier policy that exceeds its bounds, and a Coach Agent version without disclosure, and confirm each is refused with every violation named.

**Acceptance Scenarios**:

1. **Given** a Club Admin, **When** they register a dimension set with identifier, semantic version, and dimensions (each with dimension identifier, meaning, and accepted evidence tool identifiers from the allowlist), **Then** it is stored immutably with its digest; a later minor or patch version that adds, removes, or renames a dimension is refused because that requires a major version.
2. **Given** a registered dimension set, **When** a Club Admin registers a base philosophy profile that references it and contains exactly one integer weight in `[0,100]` for each of its dimensions, keyed by dimension identifier, totalling exactly 100, with rationale and summarized public-source provenance for every weight, an author, and named architecture and football-domain reviewers, **Then** the profile is stored immutably with its digest and its normalized Manhattan distance to the profile of every approved, non-retired Coach Agent version over the same dimension-set identifier and major version is returned.
3. **Given** a profile whose weights total other than 100, that misses or adds a dimension, that uses a non-integer or out-of-range weight, that lacks rationale or provenance, or that references an unknown dimension set, **When** it is registered, **Then** it is refused naming every violation.
4. **Given** a context-modifier policy that declares its dimension-set major version, per-dimension bounds, total positive movement, and permitted context categories, **When** its bounds exceed `[-3, +3]` per dimension or 10 total positive points, or it names a context category the architecture does not permit, **Then** it is refused.
5. **Given** a Coach Agent version whose prompt, profile, and modifier policy do not share one dimension-set major version, whose prompt does not declare exactly one profile-rendering slot, or that lacks a simulation disclosure statement or a safety policy with disclosure, non-impersonation, and non-fabrication rules, **When** it is registered, **Then** it is refused.
6. **Given** a Coach Agent version whose profile is closer than 0.10 to the profile of another approved Coach Agent version, **When** a Club Admin approves it, **Then** approval requires an explicit acknowledgement of the differentiation review, which the audit event records.
7. **Given** an approved Coach Agent version, **When** a Club Admin tries to enable it, **Then** the request is refused because Coach Agent enablement is not yet supported.

### Edge Cases

- **Same content under a new version**: Registering otherwise identical content under a new version is allowed and creates a separate record whose digest covers its identifier and version.
- **Superseding a profile**: A profile may name the profile version it supersedes; the superseded profile must exist and have the same profile identifier; existing advice and pinned invocations keep their original profile lineage.
- **Dimension-set major version**: A profile or modifier policy that references dimension-set `2.x` cannot be combined with a prompt that declares major version 1; the agent version is refused, never silently adapted.
- **Concurrent enablement changes**: Two Club Admins change the same agent's enablement at once; one change wins and the other is refused as stale.
- **Enablement changed during submission**: A submission resolves either the old or the new enabled version completely, never a mix of artifacts.
- **Agent disabled while a conversation lists it as participant**: The participant stays in the conversation history, but new submissions to it are refused with "agent not available" until an approved version is enabled again.
- **Retiring an artifact**: Artifacts other than agent versions have no lifecycle of their own and are never deleted, so the artifacts of every agent version and every pin always remain readable.
- **Secrets in model selections**: A model selection names provider, model, deployment or configuration, and bounded parameters only; any additional field or a name outside the allowed pattern is refused, and provider secrets stay in the runtime's protected configuration.
- **Simulated provider outside Development and Test**: A model selection with the simulated provider can be registered anywhere but its agent version can only be enabled in Development and Test.
- **Seed versus existing catalog**: The Development and Test seed applies only to an empty catalog; when the catalog already holds records, the catalog wins and the seed is skipped.
- **Orchestration configuration**: The previously configured list of enabled specialists no longer decides availability; a configured list that names agents the catalog has not enabled has no effect and is reported at start in Development and Test.
- **Large prompts**: Prompt templates and rationales are bounded in length; oversized content is refused.
- **Invocations from before the catalog**: Invocations submitted before this feature carry no pin; they stay readable, and an unfinished one is never executed unpinned: its next claim is refused and it fails with reason "agent not available".

## Requirements *(mandatory)*

### Functional Requirements

#### Catalog contracts

- **FR-001**: The platform MUST define versioned machine-readable contracts in the repository's contract catalog for the agent version (agent definition) and each artifact kind — prompt template, model and deployment selection, tool policy, safety policy, philosophy dimension set, base philosophy profile, and context-modifier policy — and for the catalog baseline that lists the catalog's agent identifiers with group, domain, display name, and permitted-tool baseline from [Specialist Agent Catalog](../../docs/architecture/intelligence-agent-catalog.md#specialist-agent-catalog), [Coach Agent Catalog](../../docs/architecture/intelligence-agent-catalog.md#coach-agent-catalog), and [MCP Tool Policy](../../docs/architecture/intelligence-agent-catalog.md#mcp-tool-policy), each with valid and invalid golden fixtures validated by the contract tests. The catalog baseline is fixed by the architecture: it MUST be readable by Club Admins and MUST NOT be registrable or changeable through the platform.
- **FR-002**: The tool allowlist MUST be the versioned list of MCP tool identifiers named in [MCP Tools](../../docs/architecture/intelligence-and-agents.md#mcp-tools) and the catalog's tool policy table; tool policies and dimension evidence MUST reference only allowlisted identifiers.

#### Registration and validation

- **FR-003**: Club Admins MUST be able to register each artifact kind and agent version with an identifier and a semantic version; the platform MUST store each accepted record immutably with a digest computed from its canonical content, the registering member, and the registration time.
- **FR-004**: Registering an existing identifier and version with equivalent content MUST return the stored record unchanged; with different content it MUST be refused because versions are immutable.
- **FR-005**: Every registration MUST be validated against its contract and the catalog rules, and a refusal MUST be an explicit problem response that names every violation with a stable code and the offending field, storing nothing.
- **FR-006**: A tool policy MUST name one or more allowlisted tool identifiers and nothing else; an agent version MUST be refused when its tool policy grants a tool outside the catalog baseline for its agent identifier (for Coach Agents, the "All CAs" baseline).
- **FR-007**: A model selection MUST contain only the provider from the architecture's set (OpenAI API, GitHub Models, and a simulated provider for Development and Test), the model and the deployment or configuration name, each matching a bounded name pattern (letters, digits, `.`, `-`, `_`, `/`, `:`; at most 128 characters), and generation parameters that are typed numbers or enumerations within bounds; any other field MUST be refused, so that credentials, endpoints, and other secrets cannot be stored.
- **FR-008**: A prompt template MUST declare its agent group, the shared response contract it follows ([Prompt And Advice Governance](../../docs/architecture/intelligence-agent-catalog.md#prompt-and-advice-governance)), its bounded text, and its rendering slots from a fixed set; a Coach Agent prompt template MUST declare exactly one philosophy-profile rendering slot and its compatible dimension-set major version, and a Specialist Agent prompt template MUST NOT declare a profile slot.
- **FR-009**: A safety policy MUST declare its agent group, its permitted interaction routes from the supported set (`User -> CA`, `User -> SA`, Hermes-orchestrated `CA -> SA`), its hard boundaries, and its escalation and refusal categories; a Coach Agent safety policy MUST include the simulation-disclosure, non-impersonation, and non-fabrication rules of [Prompt And Advice Governance](../../docs/architecture/intelligence-agent-catalog.md#prompt-and-advice-governance).
- **FR-010**: A dimension set MUST contain uniquely identified dimensions, each with a meaning and one or more accepted evidence tool identifiers from the allowlist; a new minor or patch version of a dimension-set identifier MUST keep exactly the dimension identifiers of its major version, and only a new major version may add, remove, split, merge, or redefine dimensions ([Dimension Set](../../docs/architecture/intelligence-agent-catalog.md#dimension-set)).
- **FR-011**: A base philosophy profile MUST reference one registered dimension-set version and contain, keyed by dimension identifier, exactly one non-negative integer weight in `[0,100]` for every dimension of that version and no other key, totalling exactly 100, each with rationale and summarized public-source provenance of bounded length, plus author, named architecture and football-domain reviewers, and an optional superseded-profile reference to an earlier version of the same profile identifier ([Base Philosophy Profiles](../../docs/architecture/intelligence-agent-catalog.md#base-philosophy-profiles), [Adding Or Revising A Coach Agent](../../docs/architecture/intelligence-agent-catalog.md#adding-or-revising-a-coach-agent)).
- **FR-012**: On profile registration and on reads of a profile, the platform MUST report its normalized Manhattan distance `sum(abs(a_i - b_i)) / 200` to the profile of every approved, non-retired Coach Agent version over the same dimension-set identifier and major version, and flag every distance below 0.10 for differentiation review without refusing the profile.
- **FR-013**: A context-modifier policy MUST declare its dimension-set major version, a per-dimension bound no wider than `[-3, +3]`, a total positive movement no greater than 10, the budget-neutral rule (modifiers sum to zero and keep every applied weight non-negative and the total at 100), and permitted context categories only from score state, match period, player-number state, opponent phase behavior, and evidence availability ([Context Modifiers](../../docs/architecture/intelligence-agent-catalog.md#context-modifiers)).
- **FR-014**: An agent version MUST name one catalog agent identifier, its group, a display name, and the digest of exactly one prompt template, model selection, tool policy, and safety policy, whose prompt template and safety policy declare the same group; a Coach Agent version MUST additionally reference one base philosophy profile and one context-modifier policy and carry a simulation disclosure statement, and MUST be refused unless its prompt, profile, and modifier policy share one dimension-set major version; a Specialist Agent version MUST NOT reference a profile or modifier policy.

#### Lifecycle and enablement

- **FR-015**: Agent versions MUST move only through draft, approved, and retired; approval and retirement MUST be separately authorized, audited operations; the creator MAY approve, and the approval's audit event MUST mark self-approval; approved and retired versions MUST NOT change. Approving a Coach Agent version whose profile has a flagged distance MUST require an explicit differentiation-review acknowledgement recorded in the audit event.
- **FR-016**: Club Admins MUST be able to enable exactly one approved Specialist Agent version per agent identifier on the stamp, replacing any previously enabled version atomically, and to disable an agent; enablement changes MUST be conditional on the enablement state the caller last saw and audited. Enabling a draft or retired version, a version whose model selection uses the simulated provider outside Development and Test, or any Coach Agent version MUST be refused with a specific reason.
- **FR-017**: Retiring the currently enabled version of an agent MUST be refused until another version is enabled or the agent is disabled.
- **FR-018**: The enabled-agents read of [Agent Orchestration Direct Invocations](../archive/20261017-204332-agent-orchestration-invocations/spec.md) (FR-005 there) MUST be served from the catalog's enablement instead of configuration and MUST return, for each enabled agent, identifier, group, domain, display name, and enabled version; participant addition and submission MUST use the same enablement.

#### Pinning and execution

- **FR-019**: A valid submission MUST resolve the addressed agent's enabled version at submission time and record in the invocation, in the same atomic step, the agent version identifier, version, and digest and the kind, identifier, version, and digest of every artifact it references.
- **FR-020**: Retries, the execution envelope, completion, and lineage of an invocation MUST use only its pinned version and digests; later enablement changes, new versions, retirements, or disablement MUST NOT change queued, running, or ended invocations.
- **FR-021**: The execution envelope returned by a claim MUST carry the pinned agent version and artifact references, under a versioned contract change of the envelope that keeps every existing field.
- **FR-022**: The agent workload MUST be able to read the immutable content of an artifact pinned by the invocation of its current attempt, with that attempt's current fencing token and unexpired lease; any other artifact, an attempt that is not current, or a caller that is not a workload identity MUST be refused without disclosing the artifact, and member sessions MUST NOT be accepted for this read.
- **FR-023**: A completion whose declared prompt, tool-policy, or safety-policy references differ from the invocation's pinned digests MUST be refused with a specific reason and change nothing; the lineage and accepted advice MUST record the pinned references.
- **FR-023a**: The conversation owner's invocation and lineage reads MUST show the pinned agent version and every pinned artifact's kind, identifier, version, and digest, and MUST NOT include artifact content.
- **FR-023b**: An unfinished invocation without a pin (submitted before this feature) MUST NOT be executed: its claim MUST be refused and the invocation MUST end as `failed` with reason "agent not available"; ended unpinned invocations MUST stay readable unchanged.

#### Reads, audit, seed, and interfaces

- **FR-024**: Club Admins MUST be able to list and read every record kind with its identifier, version, digest, content, registering member, registration time, and, for agent versions, state, approval, retirement, and whether it is enabled; and to read the stamp's current enablement per agent identifier. Other members MUST be refused.
- **FR-025**: The platform MUST record security audit events for every registration (accepted, replayed, and refused), approval, retirement, enablement change, and refused unauthorized attempt, with the acting member, record kind, identifier, version, digest, and outcome; prompt text, rationale text, and provenance text MUST NOT appear in audit events, logs, or telemetry.
- **FR-025a**: The platform MUST emit telemetry counters of registrations (accepted and refused, by record kind), approvals, retirements, and enablement changes through its existing telemetry, without record content.
- **FR-026**: In Development and Test only, an empty catalog MUST be seeded once with approved and enabled versions of `specialist-tactics` and `specialist-video-analysis` built from the catalog's first-draft prompts ([First-Draft System Prompts](../../docs/architecture/intelligence-agent-catalog.md#first-draft-system-prompts)), the simulated model provider, tool policies equal to their baselines, and safety policies stating their hard boundaries; the seed MUST NOT register Coach Agent artifacts, and in any other environment no seed is applied.
- **FR-027**: All member operations MUST be authenticated `/api/v1` operations with the existing session, anti-forgery, conditional-request, and problem-details rules, and the workload read MUST be a versioned operation restricted to the workload identity; all MUST appear in the platform's OpenAPI document with typed schemas, and the committed OpenAPI snapshot MUST be refreshed.
- **FR-028**: Automated tests MUST cover every validation rule and refusal, idempotent and conflicting registration, the lifecycle and enablement rules with concurrency, pinning across enablement changes and retries, the envelope contract, the workload read authorization, completion reference checks, the owner's pin visibility, the refusal of unpinned invocations, the enabled-agents read, audit and telemetry content, the seed, and the contract fixtures.

### Key Entities

- **Catalog baseline**: The versioned list of the catalog's agent identifiers with group, domain, display name, and permitted-tool baseline, and the tool allowlist; it changes only with the architecture.
- **Prompt template**: An immutable, versioned prompt artifact with its agent group, response contract, bounded text, and declared rendering slots.
- **Model selection**: An immutable, versioned reference to one provider, model, deployment or configuration, and bounded parameters, without secrets.
- **Tool policy**: An immutable, versioned set of allowlisted tool identifiers.
- **Safety policy**: An immutable, versioned declaration of permitted routes, hard boundaries, escalation and refusal categories, and, for Coach Agents, disclosure and non-impersonation rules.
- **Dimension set**: An immutable, semantically versioned list of philosophy dimensions with meaning and accepted evidence tools.
- **Base philosophy profile**: An immutable, versioned vector of integer weights keyed by dimension identifier, totalling 100, with per-weight rationale and provenance, author, reviewers, and optional superseded reference.
- **Context-modifier policy**: An immutable, versioned declaration of modifier bounds and permitted context categories for one dimension-set major version.
- **Agent version**: An immutable, versioned, content-addressed binding of one catalog agent identifier to its artifacts; state draft, approved, or retired.
- **Agent enablement**: The stamp's single enabled agent version per agent identifier, or none.
- **Invocation pin**: The agent version and artifact references recorded in an invocation at submission and carried by its envelope and lineage.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of invocations submitted after this feature merges carry a pinned agent version and artifact digests that exist as approved records in the catalog; 0 invocations resolve agents from configuration.
- **SC-002**: 0 stored records or approved agent versions change after they are stored, across all tests.
- **SC-003**: 100% of the invalid records in the tests — unknown or out-of-baseline tools, extra fields or invalid names in model selections, missing or extra dimensions, weights out of range or not totalling 100, incompatible dimension-set versions, modifier bound violations, missing disclosure, and catalog identifier violations — are refused with every violation named and store nothing.
- **SC-004**: In the tests, an invocation's envelope and lineage are byte-identical in their pinned references before and after every enablement change, new version, retirement, or disablement of its agent.
- **SC-005**: 100% of state-changing catalog operations produce an audit event, and 0 audit events, logs, or telemetry records contain prompt, rationale, or provenance text.
- **SC-006**: A Club Admin can register, approve, and enable a new Specialist Agent version, and the next submission pins it, within 2 minutes using the documented operations locally.

## Assumptions

- **Actors**: Club Admins act as catalog operators until a stamp-operator role is defined, as for the Analyst Registry; no new role is introduced.
- **Approval meaning**: Approval records an accountable decision only; the evaluation suites, A/B evidence, expert review, and promotion thresholds of [Validation And Promotion Gates](../../docs/architecture/intelligence-agent-catalog.md#validation-and-promotion-gates) are out of scope and remain Provisional, and the catalog's prompt drafts, profile values, and model choices stay Provisional design inputs.
- **Agent identifiers**: Agent versions may only use the nine catalog identifiers of the catalog baseline; adding an agent requires an architecture change and a new catalog-baseline version. Philosophy profiles may use any profile identifier, so synthetic evaluation profiles can be registered.
- **Artifact lifecycle**: Only agent versions have draft, approved, and retired states; other artifacts are immutable on registration and never deleted, and an agent version's approval covers exactly the artifact digests it references.
- **Model providers**: Provider credentials stay in the agent runtime's protected configuration and are never part of the catalog; production provider, model, and deployment values remain open.
- **Rendering and execution**: Prompt rendering, profile rendering with applied modifiers, model execution, and failing an invocation on an invalid or incompatible profile at execution belong to the Hermes Agent Runtime; this feature guarantees that only validated, compatible records can be pinned.
- **Evidence tools**: Tool policies reference tool identifiers only; the evidence tools and their enforcement belong to the Agent Evidence Tools API.
- **Out of scope**: the Web UI for catalog administration; evidence tools; Hermes and prompt rendering; Coach Agent enablement and conversations; delegated consultations; evaluation suites and promotion evidence; model provider secrets; production values; deleting records; mutable aliases (an invocation always pins a concrete version).
- **Evidence**: Passing validation is development evidence only and does not establish deployment support or production readiness.
